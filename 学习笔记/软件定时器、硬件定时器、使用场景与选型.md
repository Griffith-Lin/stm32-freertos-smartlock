# 软件定时器、硬件定时器、使用场景与选型

> 一句话定位:**硬件定时器是"独立的秒表",软件定时器是"内核雇的一个伙计替你看表"**。前者准但数量有限、回调在中断里;后者数量随便但要过一层调度、回调在任务里。**选哪个,取决于回调里要干什么活。**

---

## 1. 先破一个误解:软件定时器不是"没有硬件"

"软件定时器"听着像是纯代码算出来的,其实不是。

FreeRTOS 的节拍(tick)来自 **SysTick** —— 那是 Cortex-M 内核自带的一个**硬件定时器**。`freertos/FreeRTOSConfig.h` 里的 `configTICK_RATE_HZ` 是 1000,就是这个硬件定时器被配成每 1ms 中断一次。

所以真实的分层是:

```
硬件定时器 SysTick  ──每 1ms 中断──▶  内核 tick 计数 +1
                                          │
                                          ▼
                                  软件定时器的"刻度"
```

**推论**:软件定时器的精度**不可能超过一个 tick**。你这里 1 tick = 1ms,想定 0.5ms 的软件定时器是做不到的 —— 不是内核不努力,是它脚下的尺子就只有那么细。

**这就是"拿软件定时器做时基"是循环依赖的原因**:时基本身要靠 tick,而 tick 要靠硬件定时器。

## 2. 三种"按时干活"的方案

嵌入式里想"定期做一件事",一共三条路。它们的形状差别很大:

### 方案 A:任务 + `vTaskDelay` / `vTaskDelayUntil`

```c
static void my_task(void *arg)
{
    TickType_t lastWake = xTaskGetTickCount();
    for(;;)
    {
        do_something();
        vTaskDelayUntil(&lastWake, pdMS_TO_TICKS(10));
    }
}
```

**对照你的工程**:`api/key.c` 的 `key_scan_task` 就是这一条 —— 每 10ms 扫一次按键状态机,`vTaskDelayUntil` 固定节拍不漂移。

### 方案 B:软件定时器

```c
static void my_cb(TimerHandle_t xTimer) { do_something(); }
xTimerCreate("t", pdMS_TO_TICKS(10), pdTRUE, NULL, my_cb);
```

**对照你的工程**:`api/soft_timer.c` 就是这一条 —— 两个自动重载定时器,回调跑在守护任务里。

### 方案 C:硬件定时器 + 中断

```c
void TIMx_IRQHandler(void) { /* 清标志; do_something(); */ }
```

**对照你的工程**:`api/tim.c` 的 `TIM10_Task_Config` + `TIM1_UP_TIM10_IRQHandler` —— TIM10 每 1ms 中断一次,中断里只做 `tim10_tick_ms++`。

## 3. 逐项对比

| | A. 任务 + vTaskDelay | B. 软件定时器 | C. 硬件定时器中断 |
|---|---|---|---|
| **最小分辨率** | 1 tick(你这里 1ms) | 1 tick(你这里 1ms) | 硬件级,可到**微秒甚至纳秒**(取决于时钟和预分频) |
| **谁来计时** | 内核 tick | 内核 tick | 独立硬件计数器,**不占 CPU** |
| **回调/周期体跑在哪** | 任务上下文 | **守护任务**上下文 | **中断上下文** |
| **能调 FreeRTOS API 吗** | 随便调 | 随便调 | 抢占优先级必须 **≥ 11** 才行,否则 `configASSERT` 死循环 |
| **能阻塞吗** | 能 | 能,但**会拖累所有软件定时器** | **绝对不能** |
| **抖动来源** | 调度延迟 | 调度延迟(含守护任务自身) | 中断延迟(临界区 + 更高优先级中断) |
| **数量** | 一个功能一个任务,费栈 | **想要多少有多少**(受堆限制) | 芯片上有几个用几个 |
| **额外内存开销** | 每个任务 1 份 TCB + 栈 | 一个守护任务(共用)+ 每个定时器几十字节 | 0 |
| **运行开销** | 一次上下文切换 / 周期 | 一次上下文切换 / 周期 | 一次中断进出,几微秒 |
| **能不能中途改周期** | 改 `vTaskDelayUntil` 的参数即可 | `xTimerChangePeriod` | 要改 PSC/ARR 寄存器 |
| **能不能半路停掉** | 要自己加 `if` 判断 | `xTimerStop` / `xTimerReset` | `TIM_Cmd(TIMx, DISABLE)` |

**表里最值钱的一行是"回调跑在哪"** —— 它直接决定了下面两行的答案。

## 4. 典型使用场景

上一节讲的是"性质",这一节讲"活儿"。同一条性质,在不同需求下的分量完全不同。

### 软件定时器的主场

判断标准只有一条:**回调里要干的事,在中断里干不了或者干不好。**

| 场景 | 为什么合适 | 具体长什么样 |
|---|---|---|
| **超时判定 / 超时重试** | "收到回应就取消"正是它最擅长的语义 —— `xTimerStart` 起表,`xTimerStop` 撤表 | 发一条指令出去,500ms 内没等到回执就判定超时、重发或报警 |
| **按键长按 / 连击** | 事件要在**阈值那一刻**产生,不能等松手(见 §7) | 长按 1 秒开锁;连按两次进设置 |
| **延时后自动恢复的临时状态** | 一次性定时器,到点自己跑回调,不需要专门养个任务去数时间 | 密码连错 3 次,锁定 30 秒后自动解锁;提示语显示 2 秒后自动回主界面 |
| **周期性业务动作,且动作里有耗时操作** | **这是最不可替代的一条**,理由见下 | 定期把数据落盘到 W25QXX —— `api/w25qxx.c` 的 `W25Qxx_Sector_Erase` 里是 `while (W25Qxx_Read_SR1_busy());`,扇区擦除要等几十毫秒 |
| **软件看门狗 / 心跳检查** | 各任务定期"喂"标志,定时器定期查,挂掉的那个能被点名 | 比"等硬件看门狗复位整个系统"温和得多,能只报警不重启 |

**为什么"动作里有阻塞"是最不可替代的一条**:写 Flash、`printf`、`xSemaphoreTake` 这些事,在中断上下文里**一个都不能干**(要么非法,要么会把中断堵死)。而软件定时器的回调跑在守护任务里 —— 任务能阻塞,所以它能坦然地干这些重活。

这就分出两类定时需求了:

- **"准时地做个判断"** → 软件定时器(回调轻,但可以是"业务级"的)
- **"准时地做个动作"** → 硬件定时器(回调必须极短)

### 硬件定时器的主场

判断标准也只有一条:**要么要求"准到微秒",要么要求"硬件自己干、CPU 别掺和"。**

| 场景 | 为什么只能用硬件 | 对照你的工程 |
|---|---|---|
| **系统时基** | tick 必须来自硬件,否则循环依赖(§6 问题④) | `api/tim.c` 的 TIM10 维护 `tim10_tick_ms`,SysTick 维护内核 tick |
| **PWM 输出** | 波形由硬件比较器自己产生,**CPU 一次中断都不用进** | `api/L9110S.c` 现在是 IO 翻转定方向;要调速就得再给它配一路 PWM |
| **微秒级时序** | 软件定时器的尺子是 1ms,连一格都够不着 | 你在 `api/delay.c` 的注释里算过 WS2812 那笔账:那个空转循环转 44 圈就是 1.18μs,而 '0' 码的高电平只允许 300ns 左右 —— 死循环延时**连一圈的误差都嫌大**,更别说还要被中断打断 |
| **输入捕获 / 测宽测频** | 硬件在边沿上记时刻,CPU 事后去读就行 | 超声波 HC-SR04 的 echo 高电平宽度、红外遥控的脉宽解码 |
| **DMA 的触发源** | 定时器到点自动触发一次搬运,全程无 CPU 参与 | `api/dma.c` 现在搬的是串口数据;换成"定时采样"时,触发源就换成定时器 |
| **编码器接口** | 硬件正交解码,CPU 只读计数 | 给小车装测速编码器时 |

### 两边最容易搞反的一个地方:PWM

很自然会想:"我用个 1ms 的软件定时器,回调里翻一下 IO,不就能给电机调速了?"

算一下就知道不行:1ms 的尺子,一个周期里最多翻两次(一高一低),所以 PWM 频率上限是 **500Hz**。而且软件定时器的抖动是**毫秒级**的 —— 占空比忽宽忽窄,L9110S 这类 H 桥会发热发烫,电机只会嗡嗡叫。**PWM 的频率和占空比必须是硬件稳定产生的方波**,这是硬件定时器的地盘,没得商量。

### 一句话记住

- **软件定时器 = 定时的"业务逻辑"**。要读写 Flash、要等锁、要发队列都行 —— 因为它跑在任务里。
- **硬件定时器 = 定时的"物理动作"**。产生波形、捕捉边沿、触发采样、维护时基 —— 这些要的是**准时**和**不占 CPU**,不要它"能干重活"。

## 5. 硬件定时器中断的"优先级两难"

这是选方案 C 时绕不过去的一个矛盾。

想让中断里调 `xQueueSendFromISR` / `xSemaphoreGiveFromISR` 之类的 API,**抢占优先级必须 ≥ 11**(`configMAX_SYSCALL_INTERRUPT_PRIORITY` 的高 4 位)。但一旦调到 ≥ 11:

- **好处**:能安全地动内核的数据结构了
- **代价**:它也落进了"内核临界区能屏蔽"的区间 —— `taskENTER_CRITICAL()` 会把它挡在门外,**响应延迟变大**

反过来,优先级留在 0~10:

- **好处**:不会被任何临界区挡住,响应最快
- **代价**:**一个 FreeRTOS API 都不能调**。碰一下就撞 `configASSERT`,而那个 `configASSERT` 是"关中断 + 死循环",串口再无输出,看起来像死机

**所以硬件定时器的中断里只有两种活法**:

1. **纯裸机逻辑** —— 翻 IO 口、置个 `volatile` 标志、喂个硬件看门狗。优先级留 0~10,响应最快
2. **只做"喊一嗓子"** —— 优先级调到 ≥ 11,中断里只 `Give` 一下信号量,活留给任务

**最怕的是第三种**:优先级留在 0~10,却在里面调了 FreeRTOS API。**每一次都卡死**,不是偶发。这个坑在你 `api/usart1.c` 的 `USART1_IRQHandler` 上踩过一次(原来是 3,要调 `xSemaphoreGiveFromISR` 就必须改成 15)。

## 6. 选型:按顺序问四个问题

```
① 需要微秒级(或更细)的时间精度吗?
   是 ──▶ 方案 C(硬件定时器)。软件定时器脚下只有 1ms 的尺子,做不到。

② 回调里要做的事,需要阻塞 / 等锁 / 调 FreeRTOS API 吗?
   是 ──▶ 方案 B(软件定时器)或方案 A(任务)。
          因为软件定时器的回调跑在**任务上下文**,这是它最大的价值。
          而硬件定时器中断里干这些事要么不可能,要么得把优先级调到 ≥ 11 牺牲响应速度。

③ 这件事需要"半路取消 / 重新计时 / 动态改周期"吗?
   需要 ──▶ 方案 B。xTimerStop / xTimerReset / xTimerChangePeriod 就是为这个设计的,
          「每来一个事件就 Reset 一次,只要事件不断回调就永不触发」这种**喂狗语义**
          用硬件定时器要写一堆寄存器操作。

④ 只是"数时间"当整个系统的时基吗?
   是 ──▶ 方案 C,而且**只能是 C**。时基靠 tick,tick 靠 SysTick(硬件定时器),
          用软件定时器做时基是循环依赖。
```

四个问题都答"否",那就是方案 A —— 最简单,一个任务一个循环,不用动定时器。

## 7. 对照你的工程

| 位置 | 属于哪条 | 为什么这么选 |
|---|---|---|
| `api/tim.c` 的 TIM10 | C | 它是**时基**:维护 `tim10_tick_ms`,`TIM10_delay` 和 L9110S 都靠它。时基只能是硬件定时器(§6 问题④) |
| `api/key.c` 的 `key_scan_task` | A | 每 10ms 扫一次状态机。频率低、逻辑简单、回调体不短(要跑状态机),用任务最直白 |
| `api/soft_timer.c` 的两个定时器 | B | 纯教学用,验证"共用一个守护任务" |
| 按键的长按判定 | A | 现在是"松手时拿 tick 差值算时长"。已经够好,但事件只能在**松手那一刻**产生 —— 见下 |

### 现状先看清楚:长按判定用的**不是**数拍子

`api/key.c` 里判定长按的代码是:

```c
uint32_t duration = xTaskGetTickCount() - key->press_start_time;
key->event_flag = (duration > LONG_PRESS_THRESHOLD) ? KEY_EVENT_LONG_PRESS : KEY_EVENT_SHORT_PRESS;
```

`LONG_PRESS_THRESHOLD` 在 `api/key.h` 里是 600,**单位是 ms**。

所以长按时长**已经和扫描周期解耦了**:把 `key_scan_task` 的 10ms 改成 5ms,长按还是 600ms,只是判定粒度变细了。

真正按"拍数"算的只有**消抖**那一句 `debounce_count >= 3` —— 3 拍 × 10ms = 30ms,这个才是"改扫描周期就会跟着变"的地方。

### 那软件定时器还能带来什么不同

一个实打实的区别:**事件产生的时刻**。

| | 现在的写法 | 换成软件定时器 |
|---|---|---|
| 按下 | 记录 `press_start_time` | 记录起始时间 **+ `xTimerStart(长按定时器, 0)`** |
| 按住期间 | 什么都不发生 | **600ms 到点,回调立刻触发** |
| 松开 | 算 duration,决定 SHORT 还是 LONG | `xTimerStop(长按定时器, 0)`,没到点就是短按 |

注意 `api/key.h` 里 `KEY_EVENT_LONG_PRESS` 的注释写着"**长按(释放时判定)**" —— 这就是现在这套的语义:**手指不松,长按事件永远不出现**。

对"长按 1 秒开锁"这种一次性动作,两种写法没区别。但对下面这些需求,**必须是后者**:

- 按住持续加速 / 连续移动(L9110S 小车很常见)
- 按住期间要有反馈(蜂鸣器响、LED 闪)
- 长按到点就要立刻动作,不能等用户松手

**代价**:多一个定时器对象(几十字节);回调跑在守护任务里,和 `key_scan_task` 是两个上下文,共享的按键状态变量得加保护(临界区或互斥量)。

## 8. 方案 B 的三个坑

软件定时器用起来最舒服,但有三条铁律,全因为它"所有定时器共用一个守护任务":

### 坑一:回调里 `vTaskDelay` 会拖垮**所有**定时器

你以为延的是"我自己",实际占住的是守护任务。别的定时器接下来都得晚。

**这不是理论** —— `api/soft_timer.c` 里的 `TIMER_SABOTAGE_ENABLED` 就是专门做这个实验的:在 100ms 的回调里塞一句 `vTaskDelay(300)`,然后观察**一行阻塞代码都没有**的 500ms 定时器,`dt` 也不再是稳定的 500。

**正确做法**:回调里只发通知(`xSemaphoreGive` / `xQueueSend`),真正耗时的活交给别的任务。

### 坑二:回调里 `xTimerStart(自己, portMAX_DELAY)` 会死锁

因为所有 `xTimerXxx` 都只是**往命令队列里塞一张纸条**:

```c
#define xTimerStart( xTimer, xTicksToWait ) \
    xTimerGenericCommand( ( xTimer ), tmrCOMMAND_START, ( xTaskGetTickCount() ), NULL, ( xTicksToWait ) )
```

你在回调里发命令给自己 = **自己等自己**。队列满的时候(长度是 `configTIMER_QUEUE_LENGTH`,你配的 10)就永远出不来。

**改法**:回调里要用 `xTicksToWait = 0`(塞不进就算了),或者用 `xTimerReset(自己, 0)`。

### 坑三:回调比周期还长,会"补课"变成连续触发

自动重载定时器**不会跳过**错过的周期。`freertos/src/timers.c` 的 `prvReloadTimer` 里有个 `while` 循环:发现下一次到期时刻也已经过去了,就**接着再回调一次**,直到追上当前时间。

**现象**:串口上看到同一个定时器的回调**连着打好几行**,间隔接近 0。

**危险在哪**:如果回调本身就很耗时(比如 300ms),而周期只有 100ms,那每次补课都会再欠新账 → 越欠越多,守护任务被彻底占死,其它定时器全部停摆。

**判断**:回调执行时间必须**远小于**周期。做不到就说明这件事不该用软件定时器做,或者周期该拉长。

## 9. 三个方案各自的"坑"汇总

| 方案 | 最大的坑 | 会看到什么现象 |
|---|---|---|
| A. 任务 + `vTaskDelay` | 用 `vTaskDelay` 而不是 `vTaskDelayUntil` | 周期越走越慢(误差累积),不是恒定间隔 |
| A. 任务 + `vTaskDelay` | 任务优先级太低 | 周期被高优先级任务拖长,抖动大 |
| B. 软件定时器 | 回调里阻塞 | **所有**软件定时器一起延误 |
| B. 软件定时器 | 回调比周期长 | 连续补课,守护任务被占死 |
| B. 软件定时器 | 回调里用 `portMAX_DELAY` 给自己发命令 | 死锁 |
| B. 软件定时器 | 守护任务栈不够 | 串口打出 `stack overflow Tmr Svc` |
| C. 硬件定时器 | 优先级 0~10 却调了 FreeRTOS API | **每次**都撞 `configASSERT` 关中断死循环 |
| C. 硬件定时器 | 优先级调到 ≥ 11 之后 | 会被内核临界区屏蔽,响应延迟变大 |
| C. 硬件定时器 | 中断里干耗时活 | 同级和更低优先级的中断全被堵住 |

<details>
<summary>答案(点开)</summary>

1. 因为软件定时器的刻度就是内核 tick,而 tick 由 SysTick 这个硬件定时器产生。`configTICK_RATE_HZ = 1000` 意味着尺子上最小一格是 1ms,量不出更细的东西。
2. 时基(as tick 计数)要靠 tick 中断维护;软件定时器本身又跑在 tick 之上。用软件定时器去维护 tick,等于要求"软件定时器先于 tick 存在"。
3. **不能**。优先级 1 低于门槛 11,在那里调任何 FreeRTOS API(包括 `...FromISR` 版)都会撞 `vPortValidateInterruptPriority` 里的 `configASSERT`,而这个 `configASSERT` 是"关中断 + 死循环"—— 不是偶发,是每次都卡。要调就必须把优先级改成 ≥ 11。
4. **`vTaskDelay` 不该写**。`printf` 只是慢,`vTaskDelay` 会让守护任务主动阻塞 300ms,期间**所有**软件定时器全部延误。`printf` 的问题是"占 CPU 时间",`vTaskDelay` 的问题是"主动放弃 CPU 且别人也拿不到"。
5. **方案 B(软件定时器)**。关键在于"**立刻**"这两个字:现在的写法(方案 A)必须等到松手那一刻才拿 tick 差值去算,手指不松,事件永远不出现。B 的做法是按下 = `xTimerStart(一次性定时器, 0)`,松开 = `xTimerStop`,定时器周期就是阈值 —— 到点回调立刻触发,用户还按着就已经开锁了。

   注意时长本身不是理由:`api/key.c` 里已经是拿 `xTaskGetTickCount()` 的差值算毫秒,和扫描周期没有耦合。B 换来的只有"**事件提前到阈值那一刻产生**",顺带省掉松手后才判断的滞后感。

   代价:回调跑在守护任务里,和 `key_scan_task` 共享状态要加保护(哪次按下对应哪个定时器、松手时回调是不是已经跑过了 —— 这是典型的"竞态",要做成"回调里先 `xTimerStop` 自己"这类幂等写法)。
6. **方案 C(硬件定时器)**。频率20kHz ，周期是 50 微秒,而软件方案的尺子是 1ms,连一个周期都装不下。这种事通常还会直接上 PWM 模式,让硬件自己产生波形,CPU 完全不参与。
7. **两个现象**:① 100ms 那个定时器自己变慢,并且会**连着补课**(`dt` 接近 0 地连打好几行),因为 `prvReloadTimer` 会把落下的周期一次补齐;② 同时段的**其它**软件定时器也一起延误,因为它们共用这一个守护任务。最坏情况是补课又欠新账,滚动恶化。
8. **方案 C,如果它的抢占优先级 < 11 的话**。中断上下文里只能调 `...FromISR` 版本,而且优先级必须 ≥ 11 才有资格。方案 A 和 B 的回调都在任务上下文,`xQueueSend` 随便调。
9. **不能**。算一下:PWM 一个周期最少要"高一次、低一次",在 1ms 的尺子上就是 2ms,频率上限 500Hz;而且软件定时器的抖动是**毫秒级**的,占空比忽宽忽窄。这种波形接到 H 桥上,电机只会嗡嗡叫、驱动芯片发热。PWM 应该交给硬件定时器的 PWM 模式,让比较器自己产生方波,CPU 全程不参与。
