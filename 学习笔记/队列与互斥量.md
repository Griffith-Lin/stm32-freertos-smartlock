# 队列与互斥量(任务间通信上篇)

> 一句话定位:**队列传数据,互斥量护数据。**
> 传东西给别的任务 → 队列;多个任务要动同一份资源(串口/LED/共享变量)→ 互斥量。

---

## 1. 队列(Queue):任务间"传数据"的管道

### 1.1 本质

队列 = 一个有**深度**的 FIFO 管道,**把数据拷进、拷出**(不是传指针共享)。

```
         xQueueSend(q, &data, 超时)
数据 ──────────────────────────▶  ┌──┬──┬──┬──┬──┬──┬──┬──┐
(生产任务)                         │  │  │  │  │  │  │  │  │  ← 深度 8,每格存一份拷入的副本
                                 └──┴──┴──┴──┴──┴──┴──┴──┘
                                  xQueueReceive(q, &data, 超时) ─▶ 数据副本
                                                    (消费任务)
```

创建时定死两件事:**深度**(能存几份)和**元素大小**(每份拷几个字节):

```c
QueueHandle_t q = xQueueCreate(8, sizeof(uint8_t)); // 8 格,每格 1 字节
// 必须在 vTaskStartScheduler() 之前创建(从 heap 分配)
```

### 1.2 四个函数 + 阻塞语义

| 函数 | 干什么 | 满了/空了怎么办 |
|---|---|---|
| `xQueueSend(q, &d, t)` | 拷入一份 | **满**:阻塞最多 t 个 tick,等别人取走腾出格子 |
| `xQueueReceive(q, &d, t)` | 拷出一份 | **空**:阻塞最多 t 个 tick,等别人送来 |
| `xQueuePeek(q, &d, t)` | 偷看队头不取出 | 同上 |
| `xQueueSendFromISR(...)` | 中断里发 | 中断版,不能阻塞(下节课) |

超时三选一:
- `0` = 满/空就立即放弃(非阻塞)
- `portMAX_DELAY` = 永久等下去
- `N` = 最多等 N 个 tick,等不到就返回 pdFAIL 继续干别的

**阻塞时任务进 Blocked 睡大觉,不占 CPU** —— 和 vTaskDelay 睡的是同一个状态机。

### 1.3 对照你工程:key.c 的生产者-消费者

```c
// api/key.c —— 生产端(每 10ms 醒一次)
static void key_scan_task(void *arg)
{
    ...
    evt = keys[1].event_flag;              // 取走事件
    keys[1].event_flag = KEY_EVENT_NONE;
    xQueueSend(key_queue, &evt, 0);        // 超时 0:满了就丢,不等
    vTaskDelayUntil(&lastWake, 10);
}

// api/key.c —— 消费端(优先级 3 > 扫描的 2)
static void key_action_task(void *arg)
{
    if (xQueueReceive(key_queue, &evt, portMAX_DELAY) == pdPASS)  // 空就永久睡
    { ... 处理短按/长按 ... }
}
```

设计要点(面试常问的取舍):
- **深度 8 + 超时 0 = "满了丢新事件"**。按键事件丢了无损失,不值得让扫描任务干等 → 故意的设计取舍。反过来,如果丢事件会造成事故(比如电机指令),就要用阻塞/加深度。
- **消费任务优先级高于生产任务**:事件一到立刻处理,不积压。
- 生产与消费**节奏互相独立**:扫描固定 10ms,处理想睡多久睡多久,队列在中间做缓冲——这就是队列的核心价值:**解耦双方的节奏**。

### 1.4 四个必懂细节

1. **拷贝语义**:Send/Receive 是整份拷贝。元素越大越慢。拷结构体就能一次传多字段(如 `{事件号, 参数}`);你现在只拷 1 字节,只够传一个编号。
2. **大数据不拷,传指针**:队列传指向大缓冲的指针,只拷 4 字节。但要约定"谁用完谁 free"——指针所指内存的所有权,是 FreeRTOS 编程最常见的坑。
3. **中断也能发**:ISR 里必须用 `xQueueSendFromISR`(带 `xHigherPriorityTaskWoken` 参数),不能调普通版。
4. **队列锁存数据**:只要不满,数据放进去就不会丢——这是它和二值信号量(只记 0/1)的本质区别。

## 2. 互斥量(Mutex):保护共享资源的锁

### 2.1 为什么需要:你的 printf 交错问题

`printf("111\r\n")` 是**逐字符**经 fputc 输出,每发 1 个字符要等 TXE(约 87µs@115200)。两个任务同时在打印,1ms 的 tick 可能打断在**任意两个字符之间**,于是:

- 两行字符互相穿插(切碎);
- 更糟:task A 查完 TXE 被打断,task B 写完 DR,A 恢复后再写 DR → **B 的字符被覆盖丢掉**(USART 的 DR 一次只能存 1 个待发字节)。

**锁的粒度必须 = "一整行打印"的原子单位。** 锁在 fputc 里(每字符加锁)没用——行与行照样穿插;锁要包住整个 printf 调用。

### 2.2 你的 print_line(main.c 对照)

```c
static SemaphoreHandle_t print_mutex;  // 全局互斥量

static void print_line(const char *s)
{
    xSemaphoreTake(print_mutex, portMAX_DELAY);  // 拿锁;拿不到就睡,直到有人放锁
    printf("%s\r\n", s);                          // 临界区:一整行原子
    xSemaphoreGive(print_mutex);                 // 放锁(必须!)
}

// main() 里、调度器启动前:
print_mutex = xSemaphoreCreateMutex();
```

### 2.3 铁律

1. **Take/Give 严格配对**,而且**谁 Take 的谁 Give**(互斥量有"所有权"——这是它和二值信号量最大的区别)。
2. **创建必须在调度器启动前**(从堆分配)。
3. **中断里别碰互斥量**:Take 可能阻塞,ISR 不允许;共享资源若被中断和任务共用,用临界区(taskENTER_CRITICAL)而不是互斥量。
4. **持锁时间越短越好**,锁里别干耗时的活(否则所有等锁任务都陪你耗)。

### 2.4 为什么要 `xSemaphoreCreateMutex()` 而不是二值信号量当锁:**优先级继承**

先看灾难(优先级反转):task2(优先级 4)在等锁,锁被 task1(优先级 2)拿着;此时 task1 还没跑完,优先级 3 的 led_task 醒来——**3 > 2,task1 被 led_task 抢占**,它手里的锁迟迟放不掉 → 优先级 4 的 task2 被优先级 3 的 led_task 间接饿死。高优先级任务输给了中优先级任务,荒谬。

互斥量内置解法:**task2 等锁 → task1 被临时提升到 4** → led_task(3)再也抢不动 task1 → task1 快速打完放锁 → task1 降回 2,task2 拿到锁继续。

二值信号量没有所有权也没有继承,拿来当锁就会出现上面的反转。**所以:当锁 → 永远 xSemaphoreCreateMutex。**

### 2.5 坑清单

| 坑 | 后果 |
|---|---|
| Take 了忘 Give(比如某分支提前 return) | 死锁:所有等锁任务永久 Blocked,系统"假死" |
| 持锁任务自己又 Take 同一把锁 | 自己等自己,死锁(要用 `xSemaphoreCreateRecursiveMutex` 递归互斥量) |
| 两个任务互拿对方的锁 | 经典死锁(ABBA),设计时避免嵌套拿锁 |
| 锁粒度太小(fputc 里加锁) | 看似互斥,行照样穿插 |
| 把优先级继承当万能 | 继承只在"等锁"瞬间生效,不等锁就没有 |

## 3. 选型:什么时候用哪个

| 场景 | 用 |
|---|---|
| A 任务要把**数据/事件**交给 B 任务 | 队列(或下节课的任务通知) |
| 多个任务共用**同一份资源**,防止互相踩 | 互斥量 |
| 保护**中断和任务**共享的资源 | 临界区(不是互斥量) |
| 只喊一嗓子"有事了",不带数据 | 二值信号量(下节课) |
| 攒 N 件事 / 池化 N 个资源 | 计数信号量(下节课) |

判断口诀:**传数据吗?传 → 队列。不传数据、只是防踩踏 → 互斥量。**

队列和互斥量不是竞争关系,是**两个正交工具**:队列解决"我怎么把消息给你",互斥量解决"咱俩别同时碰它"。你的 key 模块用队列送按键事件,打印用互斥量护串口——两个都用上了,各管各的。

## 4. 验证实验:怎么证明互斥量在起作用

核心认知:**竞争要先造得出来,锁才有东西可锁。**

- 低优先级任务打印时,高优先级任务恰好醒来,才能"拦腰打断";
- 每行字符数必须 > 12(≈1ms,跨得过 tick 边界)才可能被打断。

对照组(你的 print_task1/print_task2 改法):

```c
// task1:优先级 2,去掉 delay → 永远在打印(低优先级"长工")
while (1) printf("111111111111111111111111111111111111111111111111\r\n");

// task2:优先级 4,每 100ms 插一次话(vTaskDelayUntil)
while (1) { printf("222222222222222222222222222222222222222222222222\r\n");
            vTaskDelayUntil(&lastWake, 100); }
```

- **无锁(直接 printf)**:预期 111 的句子被 222 拦腰截断,出现畸形行/混行。
- **加锁(print_line)**:每行完整纯色(优先级继承保证持锁方一口气打完)。
- 两轮之间**只改 printf ↔ print_line**,其他全不动。

⚠️ 用串口工具时别用中文测试内容:UTF-8 中文 3 字节,监视器按块读取,块边界切在汉字中间就显示 `�`——那是**显示端问题,不是互斥失效**。实验内容一律纯 ASCII。

⚠️ 优先级 2 vs 4、周期 500/1000ms 且相位对齐时,两个任务**永远排着队打**,根本不会竞争 → 无锁也"看起来干净",验证不了任何东西。竞争窗口要靠"低优先级长工 + 高优先级定期插话"造出来。

## 5. 自测(答案在本文件末尾,先别看)

1. 队列深度 8、Send 超时 0。生产端一口气发 10 个事件,消费端还没醒——最后几个事件怎么样了?为什么这是合理设计?
2. 互斥量和二值信号量都只能记 0/1,为什么锁必须用互斥量?
3. print_line 里如果忘了 xSemaphoreGive,会观察到什么现象?还能用串口打印出来吗?
4. 为什么 fputc 内部加锁(Take/Give 每个字符)挡不住两行穿插?
5. 你在 key.c 的 xQueueReceive 用了 portMAX_DELAY,如果改成超时 0,消费任务会变成什么样?对按键响应有何影响?

---

<details>
<summary>答案(点开)</summary>

1. 前 8 个进队列,后 2 个 Send 时队满、超时 0 → **直接丢弃**。按键事件丢了无损失:手速远慢于队列消化速度,且丢了顶多漏一次响应,不值得让 10ms 的扫描任务阻塞干等。
2. 互斥量有**所有权 + 优先级继承**:持有者被高优先级任务等锁时临时升频,快速释放;二值信号量没有,会出现"高优先级被中优先级饿死"的优先级反转。
3. 第一个拿到锁的任务打印完不放锁 → 第二个任务在 Take 处**永久阻塞**,打印从此只剩第一个任务在输出。而且 printf 本身不依赖锁,所以**还能打印**(如果是第一个任务),只是"多任务打印"退化成"单任务打印"。
4. 因为穿插发生在**两行之间**——A 打一行时在 fputc 内部频繁取放锁,B 的字符照样能插进 A 行中间(每字符都是合法临界区)。锁的粒度必须匹配"一整行"这个原子单位。
5. 消费任务变成**忙轮询**:每 10ms 检查一次队列,没事件就继续循环 → 白占 CPU、按键响应变慢(最坏延迟从"立刻"变成"扫描周期"),还饿死低优先级任务。
</details>
