# 开锁业务的架构:两个来源,一个出口

> 一句话定位:**密码和指纹是两条完全不同的输入路径,但"开锁"这件事只写了一遍。**
> 加第三种开锁方式(人脸、NFC、蓝牙)时,只需要在它的任务里调一下 `lock_open()`,
> 互斥、LCD、电机时序全部白送。

---

## 1. 硬件与职责分工

| 角色 | 器件 | 接口 |
| --- | --- | --- |
| 密码输入 | CY9CMBR3116 电容触摸板 | 软件 I2C,SCL=PB6 / SDA=PB7 |
| 密码存储 | AT24C04A EEPROM | 软件 I2C,SCL=PA8 / SDA=PC9 |
| 指纹输入 | MG200 指纹模块 | USART6(PC6/PC7),DETECT=PC0,电源使能=PC1 |
| 人机反馈 | LCD(240×320) | PB1 / PB10 / PB12~15 |
| 执行机构 | L9110S 电机驱动 | PB3=FOR / PB4=BAK |
| (独立业务) | PC13 物理按键 | 只做 LED 和进待机,**不参与密码** |

---

## 2. 总图

```
输入层(驱动)              事件层              业务层              执行层
──────────────────────────────────────────────────────────────────────────
PC13 物理按键
  key_scan_task ──→ key_queue ──→ key_action_task ──→ LED / 进 STANDBY
  (10ms 轮询)       (深8)         key.c
   prio 2                          prio 3              ← 这条路不做密码

触摸板 CY9CM
  cy9cm_scan_task ─→ cy9cm_key_queue ─┐
  (10ms 轮询)        (深8)            │
   prio 2                             ↓
                                 lock_task          ┐
                                  prio 2            │
                                                    ├─→ lock_open(title,color)
MG200 指纹                                           │    ↑ 唯一出口
  finger_task ───────────────────────────────────────┘    │ 互斥 s_unlocking
  (100ms 轮询 PC0)                                        │
   prio 2                                                 ↓
                                                   LCD 标题 + L9110S 电机
```

## 3. 任务与队列清单

| 任务 | 优先级 | 栈(字) | 触发方式 | 职责 |
| --- | --- | --- | --- | --- |
| `key_scan` | 2 | 256 | `vTaskDelayUntil` 10ms | PC13 状态机消抖(30ms) |
| `key_action` | 3 | 128 | 阻塞等 `key_queue` | 短按翻红灯 / 长按进待机 |
| `cy9cm_scan` | 2 | 256 | `vTaskDelay` 10ms | 读触摸板,产按键事件 |
| **`lock`** | **2** | **320** | 阻塞等 `cy9cm_key_queue` | **密码输入 / 校验 / 开锁** |
| `finger` | 2 | 256 | `vTaskDelay` 100ms | 轮询 PC0,采图比对 |

两个队列都是**深度 8、元素 1 字节**,且都是全局可见的:

```c
QueueHandle_t key_queue       = NULL;   // key_scan  → key_action
QueueHandle_t cy9cm_key_queue = NULL;   // cy9cm_scan → lock
```

> **注意 `lock` 和 `finger` 优先级都是 2** —— 它们会时间片轮转。
> 这一点是后面所有并发问题的根源。

---

## 4. 三个关键设计决策

### 决策一:`lock_open()` 是唯一出口 ← 最重要

密码路径和指纹路径毫不相干,但**最后都汇到 `lock_open()` 这一个函数**。

```c
// 密码路径(lock_task 里)
lock_open((uint8_t *)"UNLOCKED", GREEN);

// 指纹路径(finger_task 里)
lock_open((uint8_t *)FINGER_TITLE_OK, GREEN);
```

好处:**"开锁"这件事的语义只定义了一次**。
- 两条路自动共享同一套互斥
- 两条路自动共享同一套 LCD 提示和电机时序
- 以后改开锁时序(比如加个蜂鸣器),只改一个地方

如果一开始就把电机驱动直接写进 `lock_task`,那么加指纹时必然要复制一份,两份迟早会不一致。

### 决策二:仲裁靠临界区里的 check-and-set,不靠优先级

```c
taskENTER_CRITICAL();
if (s_unlocking)                    // ← 检查
{
    taskEXIT_CRITICAL();
    return 0;                       // 已有开锁流程,本次忽略
}
s_unlocking = 1;                    // ← 占用
taskEXIT_CRITICAL();
```

**为什么这两步必须裹在临界区里?**

如果分开写:

```
任务A: 读 s_unlocking → 0,判断"没人开锁"    ← 被 SysTick 切走
任务B: 读 s_unlocking → 0,判断"没人开锁"
任务A: s_unlocking = 1,开始推电机
任务B: s_unlocking = 1,也开始推电机          ← 两边同时驱动 L9110S!
```

而指纹任务和密码任务**优先级都是 2**,本来就会轮转,这不是理论风险。

> 这个模式叫 **check-then-act 竞态**,是并发编程最经典的坑。
> 凡是"先判断、再根据判断结果动作"并且判断和动作之间可能被切走的,都要这样处理。
>
> 同理,能不能只靠"优先级高就不会被打断"?**不能。** 同优先级会轮转,
> 而且这套代码以后加中断、加更高优先级任务时,假设就崩了。

### 决策三:「预检」和「真仲裁」分两层

```c
// finger_task 里 —— 预检,只是省点力气
if (lock_is_busy())
{
    continue;                       // 正在开锁,这轮不采指纹了
}
```

`lock_is_busy()` 存在的意义是**性能**:正在开锁时指纹这边直接跳过这一轮,省得白采一次指纹、白等几百毫秒再被拒。

但 `lock.h` 里写得很清楚:

> 真正的仲裁仍然是 `lock_open()` 自己,**不能只靠这个判断**。

而且指纹这条路的代码里还有一层更细的处理 —— 采完指纹到调 `lock_open()` 之间有一段窗口期,对方可能已经开始开锁了:

```c
if (finger_match(&id))
{
    lock_open(...);                 // 内部还会再判一次忙,这里不用自己防
}
else if (!lock_is_busy())           // ← 比对这段时间里对方可能已经开锁了
{
    lock_lcd_set_title(...);        // 那就别去盖它的界面
}
```

**记住这个层级关系:** 预检是优化,仲裁才是正确性。预检可以漏,仲裁不能漏。

## 5. `lock_open()` 的时序

```
进 临界区: if (s_unlocking) 拒绝; else s_unlocking = 1
      ↓
LCD 标题改成 "UNLOCKED"(绿) / "FINGER  "(绿)
清空输入行
      ↓
L9110S_control(MOTOR_FORWARD) ──vTaskDelay(500ms)── MOTOR_BRAKE
      ↓                                        ← 推锁舌出去
vTaskDelay(3000ms)                             ← 保持开锁
      ↓
L9110S_control(MOTOR_REVERSE) ──vTaskDelay(500ms)── MOTOR_BRAKE
      ↓                                        ← 收锁舌回来
LCD 恢复 "PASSWORD"(蓝) + 清输入行
      ↓
s_unlocking = 0
```

**全程 4 秒**(500 + 3000 + 500),每一步都让出 CPU。

两个实现细节:

**① 为什么用 `MOTOR_BRAKE` 而不是断电让它自由滑行**
刹车比滑行可靠,锁舌不会因为惯性溜回去。L9110S 的两个输入都置成相同电平就是刹车。

**② 为什么不用 `L9110S_move()`**

它内部长这样:

```c
while (GetTim10Tick() - start < ms);    // NOP 式忙等
```

直接调会把 CPU **整整占死 3 秒**,同优先级和低优先级的任务全部饿死 ——
现象就是"开锁期间触摸板完全没反应"。所以这里必须用 `vTaskDelay`。

> 这和 [AT24C04.c](../api/AT24C04.c) 里 `Delay_Ms` 要换成 `vTaskDelay`、
> [lock.c](../api/lock.c) 里 `lock_lcd_show_error()` 不用 `Delay_Ms` 是同一个道理。
>
> **判据很简单:调度器起来之后,任何超过 1ms 的等待都必须让出 CPU。**

## 6. 密码的存储与生命周期

### EEPROM 里的布局(只用前 8 字节)

| 地址 | 内容 |
| --- | --- |
| 0 | 初始化标志 `0xA5` |
| 1 | 密码长度 = 6 |
| 2 ~ 7 | 密码本体,存 **ASCII** |

**为什么存 ASCII 不存 BCD:** 触摸板返回的就是 `'0'`~`'9'` 字符,存 ASCII 可以直接比较,不用来回转换;用编程器读出来一眼就是明文,调试方便。

**为什么一个标志就够了:** 这 8 个字节都在 EEPROM 第 0 页(页大小 16 字节)之内,**一次 `AT24C04_page_write()` 就写完了**,器件只做一次内部写周期。标志和密码在同一个写周期里落盘,**不会出现"标志有效但密码是乱码"的中间态**。

> 如果数据跨页、要分多次写,就必须把"有效标志"安排成**最后一个写**,
> 否则中途掉电会留下半截数据。更专业的做法是再加一字节 CRC 校验整块。

### 生命周期:开机读一次,之后全在 RAM

```
锁存上电
   ↓
lock_init()  ← 在 vTaskStartScheduler() 之前
   ↓  读 EEPROM,载入 s_pwd[];没写过就写默认密码 666666
   ↓
[调度器起来]
   ↓
任务阶段只读 RAM 里的 s_pwd[],**再也不碰 EEPROM**
```

**为什么必须在调度器之前初始化?**

首次上电会走一次 EEPROM 写,而 `AT24C04_page_write()` 内部用的是 `Delay_Ms()` **忙等**(等 tWR 写周期)。裸机阶段无所谓;调度器起来之后调用,会把别的任务饿死。

**为什么之后就不再读 EEPROM?**

- 避开 I2C 总线的并发问题(同一条 I2C 上还挂着 CY9CM 触摸板吗?不是,是两条独立的 I2C,但代码复杂度一样)
- 不用在任务里等 tWR
- 代价:**改了密码要重新上电才生效** —— 对门锁来说完全可以接受

## 7. 界面约定

| 时机 | 标题行 | 颜色 |
| --- | --- | --- |
| 待机 | `"PASSWORD"` | 蓝 |
| 密码正确 / 指纹匹配 | `"UNLOCKED"` / `"FINGER  "` | 绿 |
| 指纹没匹配上 | `"NO MATCH"` | 红(闪 800ms) |
| 密码错误 | `"ERROR   "` | 红(闪 800ms) |

输入行:已输入的显示 `*`,还没输入的显示 `-`。

> ⚠ **所有标题必须凑够 8 个字符**,短的要用空格补齐(所以是 `"ERROR   "` 不是 `"ERROR"`)。
> 因为 `LCD_Font_Dis_Ascii()` 会把每个字符格子的**每一个像素**都写一遍(笔画写前景色、
> 其余写背景色),相当于自带清底 —— 但这只在"新文字不比旧文字短"时成立,短了右边会留残影。

### 触摸板按键约定

| 键 | 动作 |
| --- | --- |
| `0`~`9` | 输入一位,屏幕上一个 `*` |
| `*` | 清空重输 |
| `#` | 确认,校验密码 |

**输满 6 位之后再多按的数字直接丢掉** —— 必须按 `#` 确认或 `*` 清空,
避免"多按一下就把密码顶掉"这种别扭行为。

## 8. 目前的三个薄弱点(已知未修)

### ① 开锁期间按的键会"补输"进去

`lock_task` 在 `lock_open()` 里阻塞 4 秒,这期间按的键全堆在 `cy9cm_key_queue`(深 8)。
**开锁结束、`s_unlocking` 变回 0 之后,它才回来逐个消费** —— 那时标志已经是 0 了,
于是这些键被当成正经密码输入。

> 现象:开锁时手贱按几下,锁回来后屏上莫名多了几个 `*`。

注意 `lock_task` 里那个 `if (s_unlocking) continue;` **拦不住它** ——
因为拦截发生在**读出来之后**,而读出来的时候标志已经清了。

**修法:** `lock_open()` 返回后先把队列清空再继续。

### ② ERROR 红字那 800ms 有竞态

`lock_lcd_show_error()` 里 `vTaskDelay(800ms)` 期间 `s_unlocking` **还是 0**,
而 `finger_task` 优先级同为 2、可以轮转进来写标题行。两边都是"读-改-写"软件 SPI 的 LCD,
理论上会串。

**修法:** 给 LCD 加一个 FreeRTOS 互斥量,所有画屏的地方都过它。
(这也是 [队列与互斥量.md](队列与互斥量.md) 里讲的"保护共享资源"的典型场景。)

### ③ 语音播报还没接进来

`NV400F_Init()` 在 main 里是开着的,但 `NV400F_SendCmd()` 全工程没人调 ——
开锁成功/失败现在只有 LCD 反馈,没有声音。

**接的时候有个坑:** `NV400F_SendCmd()` 内部是约 **18ms 的忙等**,直接丢进
`lock_open()` 会把同优先级任务饿死 18ms。要么放在调度器启动前,要么改成
"发完起始信号就 `vTaskDelay` 让出"的写法。

## 9. 一句话总结

| 设计点 | 做法 | 为什么 |
| --- | --- | --- |
| 多来源 | 密码 + 指纹 → 都调 `lock_open()` | 语义只定义一次,加来源零成本 |
| 互斥 | 临界区里的 check-and-set | 同优先级会轮转,分开写必然双推电机 |
| 预检 | `lock_is_busy()` | 只是优化,真仲裁仍在 `lock_open()` 里 |
| 驱动解耦 | 触摸板只产事件,不决定谁处理 | `cy9cm_key_queue` 全局可见,业务层直接消费 |
| 长等待 | 一律 `vTaskDelay`,禁 `L9110S_move()` | 忙等会饿死同/低优先级任务 |
| 密码存储 | 开机读一次进 RAM,任务阶段不碰 EEPROM | 避开 I2C 并发和 tWR 等待 |
| 初始化时机 | `lock_init()` 在 `vTaskStartScheduler()` 之前 | 首次上电要写 EEPROM,内部是 `Delay_Ms` 忙等 |

**架构的核心就一句话:把"开锁"收敛成一个函数,让所有来源都排队走同一扇门。**
