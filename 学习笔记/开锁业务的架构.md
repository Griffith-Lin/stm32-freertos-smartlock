# 开锁业务的架构:三个来源,一个决策者

> 一句话定位:**密码、指纹、云端下发是三条毫不相干的输入路径,但"什么时候推电机"只由 `lock_task` 里的一个状态机说了算。**
> 加第四种来源(人脸、NFC、蓝牙)时,只需要"投递一个意图"——互斥、LCD、电机时序全部白送。

> ⚠ 这份笔记在接入 MQTT 远程控制时**大改过一次**。改动的原因比改动本身更值得看,
> 见 [§4 决策四](#决策四开锁不是一个阻塞函数而是一个状态机)。

---

## 1. 硬件与职责分工

| 角色 | 器件 | 接口 |
| --- | --- | --- |
| 密码输入 | CY9CMBR3116 电容触摸板 | 软件 I2C,SCL=PB6 / SDA=PB7 |
| 密码存储 | AT24C04A EEPROM | 软件 I2C,SCL=PA8 / SDA=PC9 |
| 指纹输入 | MG200 指纹模块 | USART6(PC6/PC7),DETECT=PC0,电源使能=PC1 |
| **云端输入** | **Ai-Thinker WB2(WiFi+BLE Combo)** | **USART2(PA2=TX / PA3=RX),AT 命令** |
| 人机反馈 | LCD(240×320) | PB1 / PB10 / PB12~15 |
| 执行机构 | L9110S 电机驱动 | PB3=FOR / PB4=BAK |
| (独立业务) | PC13 物理按键 | 只做 LED 和进待机,**不参与密码** |

## 2. 总图

```
 输入层(驱动)              事件层              业务层(唯一的决策者)        执行层
──────────────────────────────────────────────────────────────────────────────────

 触摸板 CY9CM
  cy9cm_scan ──→ cy9cm_key_queue ──┐
  prio 2, 10ms     (深8, 1字节)    │
                                   │
 MG200 指纹                        │
  finger_task ─────────────────────┤
  prio 2, 100ms                    │
                                   ├──→ ┌────────────────┐
                                   │    │   lock_task    │
 WB2 联网                          │    │    prio 2      │
  wifi_task ──→ lock_cmd_queue ────┘    │                │
  prio 1, 常驻    (深4, 1字节)          │  lock_tick()   │ ← 每 20ms 推一步
                                        └───────┬────────┘
                                                │
                                                └───────────────────↓
                                                             LCD 标题 + L9110S 电机
```

有两条入口,但它们只是"投递意图"的两种方式:

| 入口 | 谁在用 | 走什么 |
| --- | --- | --- |
| `lock_open(title, color)` | 密码(自己)、指纹(finger_task) | 直接调,内部抢 `s_unlocking` |
| `lock_post_cmd(cmd)` | 云端(wifi_task) | 进 `lock_cmd_queue`,由 `lock_task` 取 |

**两条路最后都收敛到 `lock_task` 的状态机** —— 这就是"一个决策者"的含义。

## 3. 任务与队列清单

| 任务 | 优先级 | 栈(字) | 触发方式 | 职责 |
| --- | --- | --- | --- | --- |
| `key_scan` | 2 | 256 | `vTaskDelayUntil` 10ms | PC13 状态机消抖(30ms) |
| `key_action` | 3 | 128 | 阻塞等 `key_queue` | 短按翻红灯 / 长按进待机 |
| `cy9cm_scan` | 2 | 256 | `vTaskDelay` 10ms | 读触摸板,产按键事件 |
| **`lock`** | **2** | **320** | **20ms 周期**(两个队列都轮询) | **密码输入 / 校验 / 远程命令 / 推状态机** |
| `finger` | 2 | 256 | `vTaskDelay` 100ms | 轮询 PC0,采图比对 |
| `wifi` | 1 | 512 | 常驻(等串口行) | AT 联网、MQTT 收发、解析下发 |

三个队列,全都是**全局可见、元素 1 字节**:

```c
QueueHandle_t key_queue       = NULL;   // 深 8,key_scan    → key_action
QueueHandle_t cy9cm_key_queue = NULL;   // 深 8,cy9cm_scan  → lock
QueueHandle_t lock_cmd_queue  = NULL;   // 深 4,wifi_task   → lock
```

`lock_cmd_queue` 深度只有 4:远程命令本来就很稀疏,4 条足够吸收"开锁期间连来几条"的突发;
满了 `lock_post_cmd()` 会**丢并打印**,因为锁控讲究时效,排队等不如让云端重发。

> **注意 `lock`、`finger`、`cy9cm_scan` 优先级都是 2** —— 它们会时间片轮转。
> 这一点是后面所有并发问题的根源。

## 4. 四个关键设计决策

### 决策一:谁都不能直接驱动电机,只能"投递意图"

一开始的想法很自然:`wifi_task` 收到 `{"DoorLock":1}` 就调 `lock_open()` 呗。

**不行。** 两个理由:

1. **优先级反了**。`wifi` 是优先级 1(最低),`lock` 是 2。让一个最低优先级的任务去驱动电机、
   再保持 3 秒,这 4 秒里 MQTT 自己的上报和下发全被堵住,USART2 的环形缓冲还可能溢出丢字节。
2. **决策者必须唯一**。谁在开锁、LCD 该显示什么,只能有一个人说了算。密码、指纹、云端
   三条路都去抢 LCD 和电机,迟早串。

所以架构收敛成:**任何人都只能"投递一个意图",由 `lock_task` 决定做不做。**

```c
typedef enum
{
    LOCK_CMD_OPEN = 0,      // 对应云端 {"DoorLock":1}
    LOCK_CMD_CLOSE          // 对应云端 {"DoorLock":0}
} lock_cmd_t;

uint8_t lock_post_cmd(lock_cmd_t cmd);      // 非阻塞,满了就丢
```

> **为什么 `lock_open()` 还留着让指纹直接调?**
> 因为它**没绕过决策者** —— 它内部抢 `s_unlocking` 之后,推进动作的还是 `lock_task` 里的
> `lock_tick()`。而且本地的开锁来源(finger_task,prio 2)和 `lock` 同级,不存在"低优先级
> 堵住高优先级"的问题,没必要多走一次队列、多等 20ms 才亮屏。
> 云端那条路优先级更低、又不能等,才必须走队列。

### 决策二:仲裁靠临界区里的 check-and-set,不靠优先级

```c
taskENTER_CRITICAL();
if (s_unlocking)                    // ← 检查
{
    taskEXIT_CRITICAL();
    return 0;                       // 已有开锁流程,本次忽略
}
s_unlocking = 1;                    // ← 占用
taskEXIT_CRITICAL();
```

**为什么这两步必须裹在临界区里?**

如果分开写:

```
任务A: 读 s_unlocking → 0,判断"没人开锁"    ← 被 SysTick 切走
任务B: 读 s_unlocking → 0,判断"没人开锁"
任务A: s_unlocking = 1,开始推电机
任务B: s_unlocking = 1,也开始推电机          ← 两边同时驱动 L9110S!
```

而指纹任务和密码任务**优先级都是 2**,本来就会轮转,这不是理论风险。

> 这个模式叫 **check-then-act 竞态**,是并发编程最经典的坑。
> 凡是"先判断、再根据判断结果动作"并且判断和动作之间可能被切走的,都要这样处理。
>
> 同理,能不能只靠"优先级高就不会被打断"?**不能。** 同优先级会轮转,
> 而且这套代码以后加中断、加更高优先级任务时,假设就崩了。

**`s_unlocking` 同时还是状态机的总闸**:从 `lock_begin_opening()` 起一直到
`LOCK_CLOSING` 结束才清 0。期间按键和远程开锁一律被拒。

### 决策三:「预检」和「真仲裁」分两层

```c
// finger_task 里 —— 预检,只是省点力气
if (lock_is_busy())
{
    continue;                       // 正在开锁,这轮不采指纹了
}
```

`lock_is_busy()` 存在的意义是**性能**:正在开锁时指纹这边直接跳过这一轮,省得白采一次指纹、白等几百毫秒再被拒。

但 `lock.h` 里写得很清楚:

> 真正的仲裁仍然是 `lock_open()` 自己,**不能只靠这个判断**。

而且指纹这条路的代码里还有一层更细的处理 —— 采完指纹到调 `lock_open()` 之间有一段窗口期,对方可能已经开始开锁了:

```c
if (finger_match(&id))
{
    lock_open(...);                 // 内部还会再判一次忙,这里不用自己防
}
else if (!lock_is_busy())           // ← 比对这段时间里对方可能已经开锁了
{
    lock_lcd_set_title(...);        // 那就别去盖它的界面
}
```

**记住这个层级关系:** 预检是优化,仲裁才是正确性。预检可以漏,仲裁不能漏。

### 决策四:开锁不是一个阻塞函数,而是一个状态机

**这是接云端时被迫做的一次重构,也是整份笔记里最值钱的一段。**

#### 改之前

`lock_open()` 长这样,一个函数从头管到尾:

```c
lock_open() {
    抢 s_unlocking
    LCD + MOTOR_FORWARD   ──vTaskDelay(500ms)──  MOTOR_BRAKE
    vTaskDelay(3000ms)                    ← 保持开锁
    MOTOR_REVERSE         ──vTaskDelay(500ms)──  MOTOR_BRAKE
    恢复 LCD
    清 s_unlocking
}
```

**问题在哪里?** 云端下发的 `{"DoorLock":0}` 意思是"关锁",可它被投进 `lock_cmd_queue` 之后,
`lock_task` **正卡在 `lock_open()` 里睡觉,根本回不来收队列**。等它 4 秒后睡醒了去收,
锁早就自动回锁了 —— **"关锁"这个命令等于从来没实现过。**

这不是加个 `if` 能补的。根本矛盾是:

> **一个阻塞 4 秒的函数,等于这 4 秒里这个任务聋了。**
> 任何"中途可能要打断 / 取消 / 改主意"的动作,都不能写成一次阻塞调用。

#### 改之后

把"一个阻塞动作"拆成"**状态** + **按节拍推进**":

```
       开锁 ┌──────────┐ 行程走完  ┌────────┐ 3 秒到 或 收到关锁 ┌──────────┐ 行程走完
     ───────►│ OPENING  │──────────►│  OPEN  │──────────────────►│ CLOSING  │──────────► IDLE
            └──────────┘           └────────┘                   └──────────┘
              s_unlocking = 1 ──────────────────────────────────────► s_unlocking = 0
```

对应的代码:

```c
static lock_state_t s_state = LOCK_IDLE;
static uint32_t     s_phase_start;      // 进入当前状态的时刻
static uint8_t      s_close_req;        // 1 = 有人要求立刻回锁

static void lock_tick(void)             // 每 20ms 调一次
{
    uint32_t now = xTaskGetTickCount();

    switch (s_state)
    {
        case LOCK_OPENING:
            if ((now - s_phase_start) >= LOCK_MOTOR_MS)
            {
                L9110S_control(MOTOR_BRAKE);
                if (s_close_req)        { lock_begin_closing(); }   // ← 打断点
                else                    { s_state = LOCK_OPEN; s_phase_start = now; }
            }
            break;

        case LOCK_OPEN:
            if (s_close_req)                            { lock_begin_closing(); }
            else if ((now - s_phase_start) >= LOCK_OPEN_MS) { lock_begin_closing(); }
            break;

        case LOCK_CLOSING:
            if ((now - s_phase_start) >= LOCK_MOTOR_MS)
            {
                L9110S_control(MOTOR_BRAKE);
                s_state = LOCK_IDLE;
                lock_lcd_set_title((uint8_t *)"PASSWORD", BLUE);
                lock_clear_input();
                s_unlocking = 0;                            // ← 到这里才放开
            }
            break;

        default: break;             // LOCK_IDLE:静止,没什么可推进的
    }
}
```

`lock_open()` 于是瘦成这样,**不到 1ms 返回**:

```c
uint8_t lock_open(uint8_t *title, uint16_t color)
{
    taskENTER_CRITICAL();
    if (s_unlocking) { taskEXIT_CRITICAL(); return 0; }     // 仲裁(决策二)
    s_unlocking = 1;
    taskEXIT_CRITICAL();

    lock_begin_opening(title, color);       // 推状态机 + 亮屏 + 电机正转,不等待
    return 1;
}
```

#### 关锁命令怎么打断

`lock_handle_remote()` **不直接动电机**,只是置一个标志:

```c
case LOCK_CMD_CLOSE:
    if (s_unlocking)
    {
        s_close_req = 1;            // 交给 lock_tick() 决定在哪一步收手
    }
    else
    {
        printf("远程关锁请求,但锁本来就是关着的,忽略\r\n");
    }
    break;
```

**为什么 OPENING 阶段不是"立刻反转",而是等刹车那一刻?**

见 `lock_tick()` 里那个 `if (s_close_req)` 的位置 —— 它在 `L9110S_control(MOTOR_BRAKE)` **之后**。
如果"推锁舌"的行程还没走完就直接反转,电机要带着惯性硬换向,
机械冲击大、电流尖峰也大。等刹车停稳再反转,是同一个状态机里顺手就做到的。

#### 这次重构顺带修掉的三个坑

**① 开锁期间按的键会"补输"进去**(老问题,已消失)

老代码里 `lock_task` 阻塞在 `lock_open()` 里 4 秒,这期间按的键全堆在 `cy9cm_key_queue`(深 8)。
等它回来逐个消费时 `s_unlocking` 已经清 0 了,于是**这些键被当成正经密码输入** ——
现象就是"开锁时手贱按几下,锁回来后屏上莫名多了几个 `*`"。

老代码里那个 `if (s_unlocking) continue;` 拦不住它,因为拦截发生在**读出来之后**。

现在 `lock_task` 每 20ms 就转一圈,键还在队列里的时候就被读出来丢掉了 —— 队列根本堆不满 4 秒。
**这个问题现在自然不存在了。**

**② 状态和标志的一致性**

重构后调试时踩到过一个坑:`s_unlocking = 1` 但 `s_state = 0`。

原因是 `lock_open()` 出了临界区之后,`lock_begin_opening()` 里先是**花几毫秒刷 LCD**
(8 个 32 号字,SPI 慢慢写),最后才推状态机。这几毫秒里两个变量自相矛盾,读到了能白查半天。

**修法:先推状态机,再动 LCD 和电机。** 这条不变量现在成立:

```
s_unlocking == 1  ⟺  s_state != LOCK_IDLE      (临界区之外)
```

**③ `now - s_phase_start` 要写成无符号差值**

```c
if ((now - s_phase_start) >= LOCK_MOTOR_MS)
```

不是 `now >= s_phase_start + LOCK_MOTOR_MS`。`xTaskGetTickCount()` 是 32 位的,
1kHz 下 49.7 天回绕一次。**无符号数的减法会自动跨过回绕给出正确的差值**,
而加法溢出了就永远等不到。这是嵌入式计时的通用写法。

#### 为什么 `lock_tick()` 不需要额外加锁

电机只在 OPENING / OPEN / CLOSING 三个状态里被操作,而 `lock_tick()` **只在 `lock_task`
一个任务里跑**;进入非 IDLE 状态又必须先在临界区里抢到 `s_unlocking`。
所以 L9110S 的 FORWARD / REVERSE / BRAKE 天然是串行的。

> ⚠ 有一个不那么直观的细节要记住:`lock_open()` 是**在调用者上下文里**跑的 ——
> 指纹触发时,`lock_begin_opening()` 里那次 `MOTOR_FORWARD` 是在 `finger_task` 里执行的,
> **不是** `lock_task`。之后的每一拍才归 `lock_task`。
>
> 之所以仍然安全,是因为 `s_state` 从 IDLE 变成 OPENING 这件事,必须发生在
> "原子地抢到 `s_unlocking`"之后;而 `lock_tick()` 只在非 IDLE 状态下才碰电机。
> 两个条件不可能同时成立。
>
> 换句话说:**`s_unlocking` 是电机唯一的门禁卡,谁拿着它谁才能推第一下。**

## 5. 云端下发怎么变成事务

`wifi_task` 在常驻循环里读到的每一行,先判断前缀:

```c
if (strncmp(line, WIFI_EVT_SUB, sizeof(WIFI_EVT_SUB) - 1) == 0)
{
    wifi_handle_sub_event(line);
    continue;
}
```

### 报文格式

```
+EVENT:MQTT_SUB,attributes/push,14,{"DoorLock":1}
└──── 前缀 ────┘└── topic ────┘└len┘└── payload ──┘
```

### 切分:只按前两个逗号

```c
topic = line + (sizeof(WIFI_EVT_SUB) - 1);      // 跳过前缀
comma = strchr(topic, ',');                     // 第 1 个逗号:topic 结束
...
len_str = comma + 1;
comma   = strchr(len_str, ',');                 // 第 2 个逗号:len 结束
payload = comma + 1;                            // 剩下全是 payload
```

> ⚠ **不能无脑 `strtok` 把整行按逗号劈开。** payload 是 JSON,天生带逗号
> (比如 `{"A":1,"DoorLock":1}`),劈开就毁了。这是这类 AT 模块最常见的翻车点。

### 三道检查,任何一道不过就整条丢弃

| 检查 | 为什么 |
| --- | --- |
| topic 必须等于 `attributes/push` | 模块里可能残留上一次跑留下的订阅,收到别的 topic 说明配置和预期不一致 |
| len 字段必须全是数字 | 自己判,不用 `atoi`(它遇到非数字的行为是实现定义的) |
| **声明的 len 必须等于实际收到的长度** | 抓"收行缓冲太小、载荷被截断"——**被截断的 JSON 有可能还能解析出一个错的值,那比直接失败更危险** |

第三条最值钱。`wifi_read_line()` 的缓冲是 128 字节,超长会**静默截断**。
现在截断了会打印:

```
!! 载荷长度对不上(平台声明 99,实际收到 14) —— 多半是收行缓冲 128 字节太小把载荷截断了,内容已不可信,整条丢弃
```

### 翻译成事务

```c
static void wifi_handle_downlink(const char *payload)
{
    p = strstr(payload, "\"DoorLock\"");        // ⚠ 引号一起找
    if (p == NULL) { ...放弃... }

    p += sizeof(WIFI_FIELD_DOORLOCK) - 1;       // 跳过 "DoorLock"
    while ((*p == ' ') || (*p == '\t') || (*p == ':')) p++;    // 跳过冒号空白

    q = (*p == '"') ? (p + 1) : p;              // 值可能带引号:"1" / 1 都认
    if ((*q != '0') && (*q != '1')) { ...放弃... }

    lock_post_cmd((*q == '1') ? LOCK_CMD_OPEN : LOCK_CMD_CLOSE);
}
```

三个细节:

- **引号一起找**:免得将来云端多一个 `DoorLockState` 之类的字段时被误命中
- **带引号的 `"1"` 也认**:有些平台前端会把开关量当字符串下发
- **认不出来就打印原文放弃,绝不瞎猜** —— 猜错的代价是误开锁

> **为什么不上 cJSON?** 载荷就一个字段,为它拉一个 JSON 库进来(还有 malloc 和栈的代价)
> 不划算。但**这种手写解析只在载荷形状完全可控时才成立** —— 一旦云端改字段名、
> 载荷里出现嵌套对象、或者要处理字符串转义,就必须换成真正的 JSON 解析器。

## 6. 密码的存储与生命周期

### EEPROM 里的布局(只用前 8 字节)

| 地址 | 内容 |
| --- | --- |
| 0 | 初始化标志 `0xA5` |
| 1 | 密码长度 = 6 |
| 2 ~ 7 | 密码本体,存 **ASCII** |

**为什么存 ASCII 不存 BCD:** 触摸板返回的就是 `'0'`~`'9'` 字符,存 ASCII 可以直接比较,不用来回转换;用编程器读出来一眼就是明文,调试方便。

**为什么一个标志就够了:** 这 8 个字节都在 EEPROM 第 0 页(页大小 16 字节)之内,**一次 `AT24C04_page_write()` 就写完了**,器件只做一次内部写周期。标志和密码在同一个写周期里落盘,**不会出现"标志有效但密码是乱码"的中间态**。

> 如果数据跨页、要分多次写,就必须把"有效标志"安排成**最后一个写**,
> 否则中途掉电会留下半截数据。更专业的做法是再加一字节 CRC 校验整块。

### 生命周期:开机读一次,之后全在 RAM

```
锁存上电
   ↓
lock_init()  ← 在 vTaskStartScheduler() 之前
   ↓  读 EEPROM,载入 s_pwd[];没写过就写默认密码 666666
   ↓
[调度器起来]
   ↓
任务阶段只读 RAM 里的 s_pwd[],**再也不碰 EEPROM**
```

**为什么必须在调度器之前初始化?**

首次上电会走一次 EEPROM 写,而 `AT24C04_page_write()` 内部用的是 `Delay_Ms()` **忙等**(等 tWR 写周期)。裸机阶段无所谓;调度器起来之后调用,会把别的任务饿死。

**为什么之后就不再读 EEPROM?**

- 避开 I2C 总线的并发问题
- 不用在任务里等 tWR
- 代价:**改了密码要重新上电才生效** —— 对门锁来说完全可以接受

## 8. 已知的薄弱点

### ① 云端开锁没有任何身份校验 ← 最严重

`{"DoorLock":1}` 一到就开门。**没有校验消息是谁发的、是不是重放、时间戳对不对。**

现在唯一的门槛是 MQTT 的连接凭据(用户名/密码),而那串东西是**明文躺在 `wifi.c` 源码里**的。
任何人拿到 broker 的 topic 写权限,就能开这把锁。

**真要上产品,至少要做:** 载荷里带 HMAC 签名(密钥存 EEPROM)、带时间戳防重放、
开锁后立刻上报状态让平台能对账。这已经不是"加密传输"能解决的问题了,是**消息本身的真实性**。

### ② LCD 全局没有互斥量

`lock_lcd_show_error()` 里 `vTaskDelay(800ms)` 期间 `s_unlocking` **还是 0**,
而 `finger_task` 优先级同为 2、可以轮转进来写标题行。两边都是"读-改-写"软件 SPI 的 LCD,
理论上会串。

**修法:** 给 LCD 加一个 FreeRTOS 互斥量,所有画屏的地方都过它。
(这也是 [队列与互斥量.md](队列与互斥量.md) 里讲的"保护共享资源"的典型场景。)

### ③ 载荷长度上限约 90 字节

`WIFI_LINE_BUF` 是 128,减去前缀 + topic + 长度字段的约 35 字节,载荷只剩 90 出头。
平台如果下发带多个字段的设备影子(比如 `{"DoorLock":0,"Online":1,"Fw":"1.2"}`),
超了会被截断 —— **不过会被 §5 那第三道检查抓出来并丢弃,不会拿半个 JSON 去瞎猜**。

### ④ 关锁命令没有确认和重试

`lock_post_cmd()` 队列满就丢,丢了只打印一行日志,云端不知道。
锁的真实状态也没有上报(现在发的 `{"hb":n}` 只是心跳,不含锁态)。

### ⑤ 语音播报还没接进来

`NV400F_Init()` 在 main 里是开着的,但 `NV400F_SendCmd()` 全工程没人调 ——
开锁成功/失败现在只有 LCD 反馈,没有声音。

**接的时候有个坑:** `NV400F_SendCmd()` 内部是约 **18ms 的忙等**,直接丢进
状态机里会把同优先级任务饿死 18ms。要么放在调度器启动前,要么改成
"发完起始信号就 `vTaskDelay` 让出"的写法。

## 9. 一句话总结

| 设计点 | 做法 | 为什么 |
| --- | --- | --- |
| 多来源 | 密码 / 指纹 / 云端 → 投递意图,不自己动手 | 语义只定义一次,加来源零成本 |
| 唯一决策者 | `lock_task` 里的状态机 | 三条路都抢 LCD 和电机,迟早串 |
| 互斥 | 临界区里的 check-and-set | 同优先级会轮转,分开写必然双推电机 |
| 预检 | `lock_is_busy()` | 只是优化,真仲裁仍在 `lock_open()` 里 |
| **长动作** | **拆成状态机,20ms 推一步** | **阻塞调用期间任务"聋了",收不到打断命令** |
| 打断 | 只置 `s_close_req` 标志 | 由状态机决定在哪一步收手,不在调用者手里乱动 |
| 计时 | `(now - start) >= N`,`xTaskGetTickCount()` | 无符号差值自动跨过 49.7 天回绕 |
| 驱动解耦 | 触摸板只产事件,不决定谁处理 | `cy9cm_key_queue` 全局可见,业务层直接消费 |
| 长等待 | 一律 `vTaskDelay`,禁 `L9110S_move()` | 忙等会饿死同/低优先级任务 |
| 密码存储 | 开机读一次进 RAM,任务阶段不碰 EEPROM | 避开 I2C 并发和 tWR 等待 |
| 初始化时机 | `lock_init()` 在 `vTaskStartScheduler()` 之前 | 首次上电要写 EEPROM,内部是 `Delay_Ms` 忙等 |

**架构的第一版核心是「把开锁收敛成一个函数」。**
**接上云端之后,核心变成了「把开锁收敛成一个能被随时打断的状态机」。**

> 判断一个动作该不该写成阻塞调用,只要问一句:
> **"它执行到一半的时候,会不会有人想改主意?"**
> 会,就必须拆成状态机。
