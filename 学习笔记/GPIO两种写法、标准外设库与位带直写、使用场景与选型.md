# GPIO 两种写法、标准外设库与位带直写、使用场景与选型

> 一句话定位:**标准外设库是"调个函数替你写寄存器",位带直写是"给寄存器里的某一位单独起一个 32 位地址"**。前者胜在语义清楚、改脚方便;后者胜在快、而且写的时候**只动那一位**,不会误伤同端口的邻居。**选哪个,取决于这段代码是给人看的,还是给时序看的。**

---

## 1. 两种写法长什么样

同一个动作 —— "把 PB8 拉低":

**写法甲:标准外设库**(`api/led.h`)

```c
#define LED_RED_ON()  do { GPIO_ResetBits(GPIOB, GPIO_Pin_8); } while (0)
LED_RED_ON();
```

**写法乙:位带直写**(`api/bitband.h`)

```c
#define PBout(bit)  MEMADDR((unsigned int)&GPIOB->ODR, bit)
PBout(8) = 0;
```

两种最后都在写 GPIOB,但**写的不是同一个寄存器**,代价也不一样。下面拆开看。

---

## 2. 原理一:标准外设库走的是 BSRR

看 `lib/src/stm32f4xx_gpio.c` 里三个函数的本体:

| 函数 | 本体 | 编译出来的汇编(-O0) |
|---|---|---|
| `GPIO_SetBits` | `GPIOx->BSRR = GPIO_Pin;` | `STR r1,[r0,#0x18]` |
| `GPIO_ResetBits` | `GPIOx->BSRR = (uint32_t)GPIO_Pin << 16;` | `LSLS r1,r1,#16` + `STR r1,[r0,#0x18]` |
| `GPIO_ToggleBits` | `GPIOx->ODR ^= GPIO_Pin;` | `LDR r2,[r0,#0x14]` + `EORS` + `STR r2,[r0,#0x14]` |

(0x18 是 BSRR 在 `GPIO_TypeDef` 里的偏移,0x14 是 ODR。`GPIO_WriteBit` 也是写 BSRR,只是多一个 if。)

### BSRR 是什么

**BSRR(Bit Set/Reset Register)** 是一个"只写生效、写 0 无效"的硬件寄存器,分两半用:

| 写哪一半 | 效果 |
|---|---|
| 低 16 位(bit0~15) | 写 1 → 对应脚**拉高**;写 0 → 不动 |
| 高 16 位(bit16~31) | 写 1 → 对应脚**拉低**;写 0 → 不动 |

关键在"**写 0 不动**"。所以想拉高 PB8:

```c
GPIOB->BSRR = 0x00000100;   // 只有 bit8 是 1,别的位全是 0 → 全都不动
```

**一条 STR 指令就够了,不需要先读回现值。** 这就是库函数注释里写的 "allow atomic read/modify accesses" —— 它指的是 BSRR 这个**硬件**帮你做了原子性,不是软件做了什么。

**推论:`GPIO_SetBits` / `GPIO_ResetBits` 天生原子**,不需要关中断、不需要临界区。

### 但 `GPIO_ToggleBits` 不是

ODR 没有对应的"翻转"硬件,所以只能:

```
读回整个 16 位 ODR  ──▶  异或一下  ──▶  把整个 16 位写回去
     LDR                  EORS                STR
```

这就是经典的**读-改-写(RMW)**。第 5 节讲它为什么会咬人。

---

## 3. 原理二:位带走的是"别名地址"

### 位带是什么

Cortex-M3/M4 把两个 1MB 的区域**逐位**映射了一遍:

| 原本的区域 | 别名区 | 别名区大小 |
|---|---|---|
| SRAM 0x20000000 ~ 0x200FFFFF | 0x22000000 ~ 0x23FFFFFF | 32MB |
| 外设 0x40000000 ~ 0x400FFFFF | 0x42000000 ~ 0x43FFFFFF | 32MB |

映射关系(以"某字节偏移处的第 b 位"为例):

```
别名地址 = 别名区基址 + (字节偏移 × 32) + (位号 × 4)
```

- **×32**:一个 32 位字有 32 个位,每一位都在别名区占一个"32 位字"
- **×4**:每个别名槽是 4 字节

于是**写这个别名,等于硬件替你"读-改-写"那一位**。你写 1 它就置位,写 0 它就清零,**全程只碰这一位**,同端口别的位纹丝不动。

### 这个公式,你会见到两种写法

它在别处被抄来抄去,写法五花八门。你工程里原来那两份实现,用的就是不同的写法:

**写法一(位运算)**:

```c
#define BITBAND(addr, bitnum) ((addr & 0xF0000000)+0x2000000+((addr &0xFFFFF)<<5)+(bitnum<<2))
```

**写法二(乘法)**:

```c
#define BITBAND(addr,bit) (((addr&0xF0000000)+0x2000000)+ ((addr&0xFFFFF)*8+bit)*4)
```

**两者完全等价**,别被写法骗了:

```
(x * 8 + b) * 4  =  x * 32 + b * 4  =  (x << 5) + (b << 2)
```

(你工程现在只留了**写法二**,在 `api/bitband.h` 里;写法一那份 `api/io_bit.h` 已经删掉了 —— 原因见第 6.1 节。)

`(addr & 0xF0000000) + 0x2000000` 那一项,就是把区基址搬到别名区基址:0x40000000 → 0x42000000,0x20000000 → 0x22000000。

**为什么要算地址而不是查表?** 因为参数都是编译期常量(`GPIOB_BASE` 是常量,`n` 是常量),整个地址编译器直接折成一个常数,连循环都省了 —— 第 4 节能看到。

## 4. 实测:各值几条指令

同样"拉低 PB8",在 `-O0` 下编译出来:

```asm
; ── 写法甲:LED_RED_ON() → GPIO_ResetBits ──
MOV      r1,#0x100
LDR      r0,=0x40020400      ; GPIOB 基址
B.W      GPIO_ResetBits      ; ── 跳出去 ──
; ...进到库里接着执行...
LSLS     r1,r1,#16
STR      r1,[r0,#0x18]
BX       lr                  ; ── 跳回来 ──
```

**6 条指令 + 一次跳出跳回**

```asm
; ── 写法乙:PBout(8) = 0 ──
LDR      r1,=0x42408000      ; 别名区基址(编译器拆出来的常量)
MOVS     r0,#0
STR      r0,[r1,#0x2a0]      ; 0x42408000 + 0x2A0 = 0x424082A0
BX       lr
```

**4 条指令,零跳转**

**好消息**:编译器做了尾调用优化 —— 用的是 `B.W` 而不是 `BL`,所以**没有额外的压栈/出栈**。两者就是 6 比 4,**差距不大**。

**所以"位带更快"这句话在你这种场景下几乎不成立。** 真正的差别在下面。

## 5. 四条真正的差别

### ① 语义:一个说"灯",一个说"引脚"

```c
LED_RED_ON();      // 红灯亮。不用查电路就懂
PBout(8) = 0;      // 把 PB8 拉低 —— 但这是啥?低电平是亮还是灭?
```

`PBout(8) = 0` **看不出它连的是个 LED**,更看不出极性。要读代码的人自己去对照原理图。

### ② 改一处 vs 改一片

LED 从 PB8 挪到 PB1:

- 写法甲:`api/led.h` 里改 **1 行**
- 写法乙:全工程搜 `PBout(8)`,还得小心别误改那些"确实是 PB8、但不是 LED"的地方

### ③ 位带不检查边界,越界了也不报错

`PBout(n)` 是个宏,`n` 是几它都认。**`PBout(48) = 1;` 编译 0 警告 0 错误**,但它写到了哪里?

实测这三个:

```asm
t16: STR r0,[r1,#0x2c0]    ; → 0x424082C0
t32: STR r0,[r1,#0x300]    ; → 0x42408300
t48: STR r0,[r1,#0x340]    ; → 0x42408340
```

对照 `GPIOB->BSRR` 的位带别名:

| 别名地址 | 等价于 | 后果 |
|---|---|---|
| 0x424082C0 | ODR 的 bit16 | 保留位,写了没用 —— **纯属运气** |
| 0x42408300 | **BSRR 的 bit0** | **把 PB0 拉高!** |
| 0x42408340 | **BSRR 的 bit16** | **把 PB0 拉低!** |

也就是说:

```c
PBout(32) = 1;   // 你以为在动 PB32(不存在),其实动了 PB0
PBout(48) = 1;   // 同上,而且方向相反
```

**一分警告都没有。** 而 `GPIO_SetBits(GPIOB, 0x100)` 至少库里有 `assert_param` 兜一道。

### ④ 原子性:`GPIO_ToggleBits` 会误伤同端口的邻居

```c
GPIO_ToggleBits(GPIOB, GPIO_Pin_8);   // = GPIOB->ODR ^= 0x0100;
```

它是"读回整个 ODR → 异或 → 写回整个 ODR"。如果 `LDR` 和 `STR` 之间来了个中断,中断改了 GPIOB 的**另一个脚**(比如 PB9):

```
LDR  r2,[r0,#0x14]   ; r2 = ODR,PB9 还是老值
      ← 中断插进来,把 PB9 拉高了
EORS r2,r2,r1        ; 只改了 bit8
STR  r2,[r0,#0x14]   ; 整个写回 —— 把中断改的 PB9 覆盖掉了!
```

**中断那次的改动丢了。** 这类 bug 叫"丢更新",查起来极难,因为它依赖中断恰好落在那两条指令之间。

**位带就没有这个问题。** `PBout(8) = 1` 写的是别名地址,硬件只动 ODR 的 bit8,PB9 想怎么变怎么变。

**代价对比**:

| | 原子? | 只动一位? |
|---|---|---|
| `GPIO_SetBits` / `GPIO_ResetBits` | ✅(BSRR 硬件保证) | ✅ |
| `GPIO_ToggleBits` | ❌(读-改-写) | ❌(整字回写) |
| `PBout(n)` 直接赋值 | ✅ | ✅ |
| `PBout(n) ^= 1`(翻转) | ❌(还是要先读) | ✅(只影响那一位) |

**注意最后一行**:位带翻转同样是读-改-写,不原子。但它**只影响那一位**,不会吃掉邻居的改动 —— 这仍然比 `GPIO_ToggleBits` 强。

## 6. 位带的三个坑

### 6.1 `volatile` 丢了,写操作会被编译器删掉

`api/bitband.h` 里现在是:

```c
#define MEMADDR(addr,bit)  *(volatile unsigned int *)BITBAND(addr,bit)
                        ↑ 这个 volatile 不能省
```

**它原本少了这个 `volatile`**,长这样:

```c
#define MEMADDR(addr,bit)  *(unsigned int *)BITBAND(addr,bit)
```

少了会怎样?把下面这段编译一下:

```c
PBout(8) = 1;
PBout(8) = 0;
PBout(8) = 1;
```

| 优化级别 | 有 `volatile` | 没有 `volatile` |
|---|---|---|
| `-O0` | 3 条 STR,全在 | 3 条 STR,全在 |
| `-O2` | 3 条 STR,全在 | **只剩 1 条 STR** ← 前两次被当"死写"删了 |

`volatile` 的意思就是"这块内存会自己变,别优化我"。没有它,编译器有权认为那两次写没人读、没有可观察的副作用,**直接删掉**。

**现象**:`-O0` 下一切正常,**一旦把优化开上去,时序类代码(软件 SPI、单总线)会随机乱掉**,而且编译器一句警告都不给。

**更麻烦的是:当时它还是"实际生效的那一份"。** 工程里原来有两个头文件都在做位带 —— `api/io_bit.h`(带 `volatile`,写对了)和 `api/bitband.h`(不带)。而 `api/lcd.h` 是先 `#include "io_bit.h"`,紧接着 `#include "w25qxx.h"` → `#include "bitband.h"`。**宏重定义以最后包含的那个为准**,所以在 `lcd.c` / `spi.c` / `w25qxx.c` 里,说了算的是**没 `volatile` 的那份**。写对的那份,一行都没用上。

> **这一段现在已经修好了**(改法和验证见第 9 节)。留着它是因为它示范了一个很典型的坑:**"两份实现定义了同一个宏"这种事,不能靠 include 顺序来裁决** —— 裁决结果没人预测得了,编译器给的又只是一条很容易被无视的警告。

### 6.2 越界不报错

见第 5 节 ③。`PBout(48)` 会静悄悄地把 PB0 拉低。

**怎么防**:永远不要裸写 `PBout(n)`,一律包成具名宏(见第 8 节)。包了之后,`LCD_SCK` 这种名字只有一处定义,写错的概率大幅下降。

### 6.3 Cortex-M7 根本没有位带

位带是 **Cortex-M3/M4** 的特性。**Cortex-M7(STM32F7 / H7)把它去掉了**,Cortex-M0/M0+ 也没有。

所以一旦你的工程要从 F4 换到 F7/H7,**所有位带代码全部得重写**。这是选型时不得不考虑的一条 —— 也是"为什么大厂的驱动库普遍用 BSRR 而不是位带"的原因之一。

## 7. 宏本身的坑:末尾那个分号

`api/led.h` 里原本是这样写的:

```c
#define LED_RED_ON()  GPIO_ResetBits(GPIOB, GPIO_Pin_8); // ← 这个分号
```

**现象** —— 这么用就编不过:

```c
if (x)
    LED_RED_ON();
else
    LED_GREEN_ON();
```

```
Error:  #127: expected a statement
      else
      ^
```

**原因** —— 分号是宏体的一部分,展开后多出一条空语句:

```c
if (x)  GPIO_ResetBits(GPIOB, GPIO_Pin_8); ;    // 多出来的空语句
else    GPIO_SetBits(GPIOB, GPIO_Pin_9); ;
```

那条空语句把 `else` 和 `if` 隔开了,C 语言里 `if (...) 语句; 语句; else ...` 是非法的。

**为什么之前一直没出事**:所有调用处都是单独一行、不带 `if/else`,雷一直没踩上。但这是个定时炸弹 —— 哪天想写 `if (key) LED_RED_ON(); else LED_RED_OFF();` 就炸。

**怎么改** —— 用 `do { ... } while (0)` 把整个宏包起来:

```c
#define LED_RED_ON()  do { GPIO_ResetBits(GPIOB, GPIO_Pin_8); } while (0)
```

**为什么这么改**:

- `do { ... } while (0)` 在语法上是**一条语句**,能安全跟在 `if` / `else` 后面
- 结尾要求调用者**必须**写分号(`LED_RED_ON()` 后面别漏),用起来和普通函数一模一样
- 不写成 `{ ... }` 是因为那样会引入一条空语句,同样会在 `if/else` 上翻车

> 这是 C 语言里"多语句宏"的标准写法,记住就好。

## 8. 选型:问三个问题

### 问 ①:这段代码是"给人看"还是"给时序看"?

| 情形 | 选 |
|---|---|
| 一秒动几十次以下(点灯、拉个使能脚、继电器) | **标准外设库**。省那 2 条指令毫无意义,可读性才是全部 |
| 每个字节要翻转十几次、跑在 μs 级(软件 SPI、I2C、单总线、WS2812) | **位带**。这时 2 条指令 × 成千上万次才划算 |

### 问 ②:有没有别的地方(尤其中断)在动同一个端口的其他脚?

- **有** → `GPIO_ToggleBits` 危险(整字回写会吃掉别人的改动)。改用位带,或改用 `GPIO_SetBits`/`GPIO_ResetBits`(走 BSRR,也原子)
- **没有** → 随便用

### 问 ③:这个引脚会不会换?

- **会** → 无论如何都要包一层具名宏。裸写 `PBout(8)` 意味着换脚要全工程搜

### 结论:不是二选一,是**分层**

| 层 | 用什么 | 理由 |
|---|---|---|
| **业务/应用层** | 具名宏 + **标准外设库** | 语义清楚、换脚改一处、不会误伤邻居 |
| **驱动/时序层** | **具名宏** 包着 **位带直写** | 要的是快,但可读性不能丢 |

**两条铁律**:

1. **永远不裸写 `PBout(n)`。** 哪怕在驱动层,也要先包成 `LCD_SCK` 这种名字 —— 既避免 6.2 的越界坑,也让代码能读
2. **位带代码要能用 `volatile`,而且只能有一份实现。** 两套头文件同时定义同一个宏,谁生效取决于 include 顺序,这是最坏的一种"能编译但没人能预测"

## 9. 对照你的工程

| 位置 | 属于哪层 | 用的是什么 | 评价 |
|---|---|---|---|
| `api/led.h` 的 `LED_RED_*` / `LED_GREEN_*` | 业务层 | 具名宏 + 库函数 | ✅ 分层正确。已加上 `do{}while(0)` |
| `api/lcd.h` 的 `LCD_SCK` / `LCD_MOSI` / `LCD_CS` / `LCD_DC` / `LCD_RST` / `LCD_BLK` | 时序层 | **具名宏**包位带 | ✅ 分层正确 —— 这正是规范用法 |
| `api/spi.h` 的 `SPI_CS` / `SPI_SCK` / `SPI_MOSI` / `SPI_MISO` | 时序层 | 具名宏包位带 | ✅ 同上 |

**这个工程其实是"两种写法的标准示范"**:慢的走库函数,快的走位带,而且快的那些都包了具名宏。

**修过的一个隐患(值得当活标本记下来)**:原来 `api/io_bit.h` 和 `api/bitband.h` 定义了一套完全同名的宏(`BITBAND`、`PAout`/`PAin` … `PGout`/`PGin`),内容不一样,所以 ARMCC 报 `#47-D: incompatible redefinition of macro`,`main.c` 一个文件就 15 条。

**这不是"重复定义所以无害"** —— 它是**两套实现撞车,胜者由 include 顺序决定**。同一个 `PBout(1)`,在不同 `.c` 里可能展开成不同的东西,而且从源码上完全看不出来。

**怎么修的**:

1. 给 `api/bitband.h` 的 `MEMADDR` 补上 `volatile`
2. `api/lcd.h` 的 `#include "io_bit.h"` 换成 `#include "bitband.h"`
3. 删掉 `api/io_bit.h`
4. `.eide/eide.yml` 文件列表里那一项同步换掉

**为什么留 `bitband.h` 而不是 `io_bit.h`**:它用 `&GPIOB->ODR` 这种 CMSIS 结构体取址,不依赖硬编码偏移,也不像 `io_bit.h` 那样带着一串抄错的 F1 地址注释;覆盖面还多一个 PH。代价是它原来少 `volatile`,所以**先补上才敢留**。

**验证**:

| | 改前 | 改后 |
|---|---|---|
| `user/main.c` | 15 warnings | **0** |
| `api/lcd.c` | 16 warnings | **1** |
| 全工程 15 个源文件合计 | **31 warnings** | **3 warnings, 0 errors** |

剩下 3 条跟位带无关(有符号移位溢出、两个未用变量)。`#47-D` 一条不剩。

另外单独验证了 `volatile` 真的生效:同一段三连写在 `-O2` 下三条 `STR` 全在(改之前只剩一条)。

## 10. 自测

**Q1.** `GPIO_SetBits` 和 `GPIO_ResetBits` 为什么不需要关中断保护?`GPIO_ToggleBits` 为什么需要?

<details>
<summary>答案</summary>

前两个写的是 **BSRR** —— 一个"写 1 生效、写 0 不动"的硬件寄存器,一条 STR 就完成,**硬件层面就是原子的**。

`GPIO_ToggleBits` 写的是 **ODR**,展开成 `ODR ^= pin`,是"读回整个 16 位 → 异或 → 写回整个 16 位"的**读-改-写**。中断落在这两步之间时,中断对同端口别的脚的改动会被写回操作覆盖掉。

</details>

---

**Q2.** `PBout(48) = 1;` 会发生什么?编译会报错吗?

<details>
<summary>答案</summary>

**不会报错,0 警告。** `PBout` 是宏,不检查范围。

实测它算出来的别名地址是 `0x42408340`,等价于 **BSRR 的 bit16** —— 也就是**把 PB0 拉低**。

原因:别名区里每个 32 位字对应原区一个字的 32 位。`bit=48` 溢出到了下一个字(`ODR` 的下一格就是 `BSRR`)。所以 `PBout(32)` 拉高 PB0,`PBout(48)` 拉低 PB0,全都是静悄悄的。

</details>

**Q3.** 为什么说"位带更快"在你这个工程里基本不成立?

<details>
<summary>答案</summary>

实测 `-O0` 下:`LED_RED_ON()` 六条指令,`PBout(8)=0` 四条。而且编译器做了尾调用优化,**没有额外的压栈出栈**。

差 2 条指令,在"一秒钟动一次"的 LED 上是完全无意义的开销。位带真正的价值不在这里,而在"**只动一位**"(不会吃掉邻居的改动)和"驱动层时序里成千上万次调用累积起来"。

</details>

**Q4.** `api/led.h` 原来的宏末尾多了个分号,会在什么情况下炸?怎么改?

<details>
<summary>答案</summary>

在 `if (...) LED_XXX(); else LED_YYY();` 这种写法下炸,报 `#127: expected a statement`,指着 `else` 那一行。

因为分号是宏体的一部分,展开后多出一条空语句,把 `if` 和 `else` 隔开了。

改法:用 `do { ... } while (0)` 把宏体包起来 —— 让整条宏在语法上等价于"一条语句"。

</details>

**Q5.** `GPIO_ToggleBits(GPIOB, GPIO_Pin_8)` 和 `PBout(8) ^= 1` 哪个更安全?为什么?

<details>
<summary>答案</summary>

**`PBout(8) ^= 1` 更安全,尽管两者都是读-改-写、都不原子。**

区别在**回写的粒度**:`GPIO_ToggleBits` 写回的是整个 16 位 ODR,会把中断对同端口其他脚的改动一起覆盖掉;`PBout(8) ^= 1` 写的别名地址,硬件只更新 ODR 的 bit8,PB9 变没变都不受影响。

结论:**要翻转、又可能和中断抢同一个端口时,用位带翻转而不是 `GPIO_ToggleBits`。**

</details>

**Q6.** 位带的解引用指针上,`volatile` 为什么不能省?省了会怎样?

<details>
<summary>答案</summary>

**省了,编译器会把"看起来没用"的写操作当死代码删掉。**

实测:同一段 `PBout(8)=1; PBout(8)=0; PBout(8)=1;`

| 优化级别 | 有 `volatile` | 没有 `volatile` |
|---|---|---|
| `-O0` | 3 条 STR,全在 | 3 条 STR,全在 |
| `-O2` | 3 条 STR,全在 | **只剩 1 条** |

编译器看不到"谁会来读这个地址",就认为前两次写没有可观察的副作用,直接删。

现象:低优化时一切正常,一开优化时序类代码(软件 SPI、单总线)就随机乱掉,而且不给任何警告。

(这条真实发生过:`api/bitband.h` 原来就少了 `volatile`,已经补上。详见第 6.1 节。)

</details>

**Q7.** 位带是 Cortex-M 所有型号都有的吗?

<details>
<summary>答案</summary>

**不是。** 位带是 **Cortex-M3/M4** 的特性。**Cortex-M7(STM32F7 / H7)去掉了位带**,Cortex-M0/M0+ 也没有。

从 F4 换到 F7/H7,所有位带代码都得重写 —— 这也是"为什么主流驱动库普遍用 BSRR"的一个原因。

</details>

**Q8.** 你手上这个工程,哪些地方该用哪种写法?各举一个例子。

<details>
<summary>答案</summary>

- **业务层用库函数**:`api/led.h` 的 `LED_RED_ON()` —— 一秒动一次,可读性和"换脚只改一处"才是重点
- **驱动层用位带(外面包具名宏)**:`api/lcd.h` 的 `LCD_SCK` (= `PBout(13)`)、`api/spi.h` 的 `SPI_CS` —— 软件 SPI 每字节翻转十几次时钟,这时才值得省那两条指令

**关键**:驱动层也没裸写 `PBout(13)`,而是包成了 `LCD_SCK`。这就是标准做法。

</details>
