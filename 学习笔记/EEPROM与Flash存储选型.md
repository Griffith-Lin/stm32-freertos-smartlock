# EEPROM 与 SPI Flash 存储选型(AT24C04A · W25Q64)

> 一句话定位:**EEPROM = 系统的小本子;SPI Flash = 系统的仓库。**
> 判断口诀:**这东西会不会"每次只改一点点,而且经常改"?会 → EEPROM。一次性灌进去、之后基本不动的大块数据 → Flash。**

---

## 1. 两颗芯片是什么

| | **AT24C04A**(I2C EEPROM) | **W25Q64**(SPI NOR Flash) |
|---|---|---|
| 容量 | 4 Kbit = **512 字节** | 64 Mbit = **8 M 字节**(16384 倍) |
| 接口 | I2C,2 根线(SCL/SDA) | SPI,4 根线(CS/SCK/MISO/MOSI) |
| 速度 | 100 ~ 400 kHz | 几十 MHz |
| **最小写入单位** | **1 字节** | 1 页(256 字节),但**必须先擦 4KB 扇区** |
| **最小擦除单位** | 不需要擦除 | **4 KB 扇区** |
| **写前要不要擦** | **不用**,直接覆盖 | **必须**,否则写进去是脏数据 |
| 单次写入耗时 | 5 ~ 10 ms | 页编程 0.7 ms;扇区擦除 **45 ms**(最坏 400 ms) |
| 擦写寿命 | **100 万次** | **10 万次** |
| 数据保持 | 100 年 | 20 年 |
| 每字节成本 | 贵 | 便宜 |
| 本工程里的角色 | (参考工程)存密码 | 存 LCD 字库 |

**一句话记法**:EEPROM 是"能随时涂改的小本子",Flash 是"要整页撕掉重写的大仓库"。

---

## 2. 差异的根源:Flash 只能把 1 改成 0

这不是设计取舍,是**物理特性**。

**EEPROM 的存储单元**:每个字节有自己的浮栅管,擦和写都能按字节来。想改第 100 个字节?直接对它写就行,旁边的字节纹丝不动。

**NOR Flash 的存储单元**:编程(写)只能把 bit 从 **1 变成 0**。想把 0 变回 1,唯一的办法是**擦除**——而擦除是加高压把一整片浮栅一起放电,**最小单位是一个扇区(4 KB)**。

于是,在 Flash 里改 1 个字节的真实代价是:

```
想改 addr 0x1234 这 1 个字节:
  ① 读出整个 4KB 扇区(0x1000 ~ 0x1FFF)到 RAM      ← 需要 4KB 的 RAM 缓冲区
  ② 在 RAM 里改掉那 1 个字节
  ③ 擦除整个扇区                                    ← 45ms,寿命 -1
  ④ 把 4KB 整块写回去                               ← 页编程,又一个几 ms
```

**改 1 个字节,动了 4096 个字节,花掉几十毫秒,还消耗一次擦写寿命。**

EEPROM 同样的活:

```
  ① 起始 + 从机地址 + 字节地址 + 数据 + 停止     ← 完事
```

这个对比就是选型的分水岭。

## 3. 所以怎么分工

| 存什么 | 选谁 | 为什么 |
|---|---|---|
| 密码 / 用户配置 | **EEPROM** | 小、用户随时可能改、改了就写一次 |
| 校准系数、零点偏移 | **EEPROM** | 几十字节,可能要反复微调 |
| 计数器(开机次数 / 累计运行时长) | **EEPROM** | 字节写、无擦除、无写放大;写勤了 Flash 寿命撑不住 |
| "首次上电"标志位 | **EEPROM** | 1 个字节,典型场景 |
| 点阵字库 / 图片 / 图标 | **Flash** | 几 MB,烧一次用一辈子 |
| 音频 / 语音提示 | **Flash** | 大块、只读 |
| 运行日志 | **Flash** | 量大;但要用"顺序追加 + 整扇区回收"的写法 |
| OTA 固件包 | **Flash** | 大,且是整块写入 |

⚠️ 反过来最容易犯的错:**拿 Flash 存"每次改一个字节的小配置"**。功能上能跑通,但每次都要擦 4KB,10 万次寿命会在你意想不到的时候耗光(尤其计数器那种"每次开机写一次"的)。

## 4. 对照两个工程的真实用法

### 4.1 参考工程(密码开锁):AT24C02 存密码

`D:\迅雷下载\0910_密码开锁` 里,`AT24C02` 挂在 **IIC3**(和触摸芯片的 IIC1 是两条独立总线),分配是这样的:

| 地址 | 内容 |
|---|---|
| 0 | 初始化标志位(0 = 出厂,1 = 已设过密码) |
| 1 ~ 21 | 密码本体 |
| 22 | 密码长度 |

全部加起来不到 30 字节,**却占用了一颗芯片**——这正是 EEPROM 的典型定位:容量小得可怜,但"随时可改、按字节改、擦写 100 万次"这三点无可替代。

### 4.2 你的工程:W25Q64 存 LCD 字库

你现在的 [api/w25qxx.c](../api/w25qxx.c) 是给**字库**用的:

```c
// api/lcd.c:349  —— 显示时按需读字模
W25Qxx_Read_Bytes(addr, buff, font_size * width);

// api/dma.c:78,89  —— 烧录字库:先块擦除,再跨页写入
W25Qxx_Block_Erase(i * 65536);
W25Qxx_CrossPage(font.addr, font.buff[font.flag], font.len);
```

字库是几 MB 的**只读定值数据**:出厂前烧一次,之后运行时只读不写。**这就是 Flash 的完美用例**——容量大、便宜、读取快,而它"不能按字节改"的缺点在这里完全不构成问题。

📌 **一句话区分这两个工程**:参考工程存的是"**用户会改的东西**"(密码),你的工程存的是"**出厂就定死的东西**"(字库)。

## 5. 如果给 train2 加 AT24C04A:三个具体的坑

参考工程的驱动是写给 **AT24C02(2Kbit)** 的,直接套到 **AT24C04A(4Kbit)** 上会踩三个坑。

### 5.1 A0 脚不是地址脚,是第 9 位地址(P0)

这是 24 系列最经典的一个坑。

| 型号 | 容量 | 从机地址(8 位) |
|---|---|---|
| AT24C02 | 256 B | `1010 A2 A1 **A0** R/W` |
| **AT24C04** | **512 B** | `1010 A2 A1 **P0** R/W` ← A0 脚悬空不用 |
| AT24C08 | 1 KB | `1010 A2 P1 P0 R/W` |
| AT24C16 | 2 KB | `1010 P2 P1 P0 R/W` |

**为什么?** 512 字节需要 **9 位**地址,但从机发完地址字节后只能再发 **8 位**字地址。差的那一位,就被塞进了从机地址里 —— 这就是 **P0**。

**后果**:AT24C04 的 512 字节被分成两块,各 256 字节:

```
   P0 = 0  →  从机地址 0xA0/0xA1  →  访问 0   ~ 255
   P0 = 1  →  从机地址 0xA2/0xA3  →  访问 256 ~ 511
```

如果直接拿参考工程那份"地址 0~255"的代码去驱动 AT24C04A,**高 256 字节永远访问不到**,而且不会报错——读回来的是低半区的旧数据,或者写进去的悄悄丢了。这种 bug 极难查。

### 5.2 页大小从 8 字节变成 16 字节

参考工程的跨页写是靠这个算边界的:

```c
les_len = 8 - addr % 8;   // AT24C02 一页 8 字节
```

AT24C04A 一页是 **16 字节**,这个 8 要改成 16。

⚠️ 页写的"回卷(roll-over)"特性:**一页内写超了不会进位到下一页,而是绕回本页开头覆盖掉前面的数据**。所以跨页拆分必须做对,否则数据会被自己覆盖。

### 5.3 写周期可能不止 5ms

参考工程写完 `delay_ms(5)` 然后走人。AT24C04A 的 **tWR 最坏标到 10ms**(不同版本数据手册有 5ms / 10ms 两种),5ms 可能不够。

更专业的做法是**应答查询(Acknowledge Polling)**,不用死等:

```
循环:
   发 起始 + 从机地址
   收到 ACK  ?  → 写完了,退出
   收到 NACK ?  → 还在写,继续循环
```

芯片在内部写周期里会对自己的地址回 NACK,写完了才开始 ACK。这样既不会等过头,也绝对不会等不够。

## 6. W25Q64 的坑

| 坑 | 说明 |
|---|---|
| **必须先擦后写** | 直接 `Page_Program` 到没擦过的区域,结果是旧数据和新数据按位**与**在一起,越写越乱 |
| **擦除单位是 4KB 扇区** | 想改 1 个字节要读出 4KB→改→擦→写回 |
| **擦除很慢** | 扇区 45ms(最坏 400ms)、64KB 块 150ms(最坏 2s)、整片擦除 20s 起 |
| **页编程 256 字节** | 一次最多写 256 字节,且跨页要自己拆(和你 `W25Qxx_CrossPage` 干的事一样) |
| **寿命 10 万次** | 比 EEPROM 少一个数量级 |
| **擦除期间不响应** | 靠读状态寄存器 SR1 的 BUSY 位等(`W25Qxx_Read_SR1_busy`) |

## 7. 和 FreeRTOS 的冲突(你正在踩的坑)

EEPROM 写完要等 **5~10ms**,Flash 擦除要等 **45~400ms**。这些等待**绝对不能**用 `Delay_Ms`:

```c
// ❌ 错的:Delay_Ms 是 NOP 忙等,会把整个 CPU 占死
AT24C02_WriteByte(addr, data);
Delay_Ms(5);

// ✅ 对的:让出 CPU,这 5ms 里别的任务照常跑
AT24C02_WriteByte(addr, data);
vTaskDelay(pdMS_TO_TICKS(5));
```

一个 400ms 的 Flash 扇区擦除如果忙等,整个系统的按键响应、串口打印全都要卡 400ms —— 用户按一下没反应,再按一下又没反应。

⚠️ 还有一个更隐蔽的:**I2C 总线是共享资源**。EEPROM 的写周期里它一直 NACK,虽然不影响别的器件(各自认自己的地址),但如果两个任务同时在总线上发起事务,波形会交织成一团。多任务访问同一条 I2C 总线,要**用互斥量把这整次事务包起来**(锁的粒度是"一次完整事务",不是"一个字节")。

## 8. 坑清单

| 坑 | 后果 |
|---|---|
| 用 Flash 存频繁改的小配置 | 擦写寿命(10 万次)悄悄耗尽 |
| Flash 写前忘了擦 | 新旧数据按位与,写进去的数据是错的 |
| 把 AT24C02 的代码直接套到 AT24C04 | 高 256 字节访问不到,且不报错 |
| EEPROM 跨页写没拆分 | 超出页边界的数据绕回本页开头,覆盖掉前面的 |
| 写周期用固定 `delay_ms(5)` 猜 | 最坏情况(10ms)没等够,下一次写丢失 |
| 写等待用 `Delay_Ms` 忙等 | 整个 FreeRTOS 被占死,所有任务卡顿 |
| 多任务同时访问一条 I2C 总线 | 波形交织,通信随机出错 |

## 9. 自测(答案在文末,先别看)

1. 要在 Flash 里把第 0x2000 个字节从 `0x0F` 改成 `0x1F`,一共要动多少个字节?为什么?
2. 同样是改 1 个字节,EEPROM 为什么可以直接写?
3. 一块板子要记录"开机总次数",每次开机 +1,你选 EEPROM 还是 Flash?为什么?
4. 拿一份给 AT24C02 写的驱动去驱动 AT24C04A,访问地址 300 会发生什么?
5. 页写时你往一页里连发了 20 个字节(AT24C04A 的页是 16 字节),最后 4 个字节写到哪儿去了?
6. `AT24C02_WriteByte()` 后面的 `delay_ms(5)` 现在要放进一个 FreeRTOS 任务里,你打算怎么改?为什么?

---

<details>
<summary>答案(点开)</summary>

1. 要动 **4096 个字节**。因为 Flash 只能把 1 改 0,要把 0 变 1 必须擦除,而擦除的最小单位是整个 4KB 扇区。流程是:读出整个扇区 → 改那 1 字节 → 擦除扇区 → 整块写回。
2. EEPROM 每个字节都有独立的浮栅管,**擦和写都能按字节进行**,不需要整块擦除,所以可以直接覆盖写。
3. **EEPROM**。理由三条,寿命只是其中之一:
   - **不需要擦除**:改 1 个字节就是一次字节写,不用在 RAM 里开 4KB 缓冲区,也没有那几十毫秒的"擦除窗口";
   - **没有写放大**:Flash 改 1 字节要擦掉整个 4KB 扇区 —— 放大 4096 倍,而且这个扇区里**别的数据也跟着一起消耗寿命、一起承担掉电风险**;
   - **寿命**:EEPROM 100 万次,Flash 10 万次。老实说,一天开 10 次的话两者都能撑几十年(Flash 约 27 年),**所以寿命本身不是决定性的**;但如果这个计数器写得勤(比如每分钟加一次),Flash 只能撑 69 天,而 EEPROM 能撑 1.9 年。真正压倒性的理由是前两条。
4. **访问不到真正想访问的地址**。AT24C04A 的高 256 字节(P0=1,从机地址 0xA2)必须靠从机地址区分,而那份代码固定用 0xA0。它会把你写的"地址 300"当成某个低半区地址(具体见代码里 addr 的类型截断)去访问,**不报错、读回来的却是错的数据**。
5. 最后 4 个字节**绕回了本页的开头**,把第 1~4 个字节覆盖掉了。页写的地址低位在页内循环进位,不会自动跳到下一页——这就是必须做跨页拆分的原因。
6. 改成 `vTaskDelay(pdMS_TO_TICKS(5))`。原因:`Delay_Ms` 是 NOP 忙等,在任务里用它等于占住 CPU 5ms 空转,把同优先级和低优先级的任务全饿死;`vTaskDelay` 会让出 CPU 进入 Blocked 态,这 5ms 里别的任务照常运行。更专业的做法是用应答查询替代固定延时。

</details>
