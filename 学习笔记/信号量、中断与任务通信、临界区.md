# 信号量、中断与任务通信、临界区(任务间通信下篇)

> 一句话定位:**队列传数据,互斥量护数据,信号量喊一嗓子**;而**中断要进这个圈子只有 FromISR 一扇门**,门卫是 `configMAX_SYSCALL_INTERRUPT_PRIORITY`。

---

## 1. 二值信号量:只喊"有事了",不带数据

### 1.1 本质:一个"退化成 0/1"的队列

FreeRTOS 里信号量不是独立实现。翻 `freertos/include/semphr.h` 能看到:

```c
#define xSemaphoreCreateBinary()  xQueueGenericCreate( ( UBaseType_t ) 1, semSEMAPHORE_QUEUE_ITEM_LENGTH, queueQUEUE_TYPE_BINARY_SEMAPHORE )
```

其中 `semSEMAPHORE_QUEUE_ITEM_LENGTH` 是 **0**。所以**二值信号量 = 深度 1、元素大小 0 的队列**——它只能记住"有没有",记不住"有几次""是什么"。

```c
SemaphoreHandle_t bin = xSemaphoreCreateBinary();
xSemaphoreGive(bin);                          // 置位
xSemaphoreTake(bin, portMAX_DELAY);           // 消耗掉,变回"空"
```

**⚠️ 反直觉点**:`xSemaphoreCreateBinary()` 创建出来是**空的**(拿不到),必须先有人 Give 一次。

### 1.2 它和队列的根本区别:**不锁存**

| | 队列 | 二值信号量 |
|---|---|---|
| 存什么 | 深度 N 份数据副本 | 只有 0 / 1 |
| 连续来 3 次没人取 | 3 份都在,排队等着 | 只记 1 次,**后两次 Give 白给** |
| 适合 | "把数据/事件交给别人" | "喊一嗓子:该醒了" |

**利**:极轻,创建时几乎不占内存(元素大小 0),Give/Take 比队列快。
**弊**:事件比消费者快时**静默丢失**,而且丢了没有任何报错。要"攒着慢慢处理"就得用队列或计数信号量。

### 1.3 二值信号量 ≠ 互斥量,别拿来当锁

| | 二值信号量 | 互斥量 |
|---|---|---|
| 所有权 | 无,谁都能 Give | **有**,谁 Take 谁 Give |
| 优先级继承 | 无 | **有** |
| 用途 | 任务/中断之间的"通知" | 保护共享资源 |

拿二值信号量当锁,会重现**优先级反转**:持锁的是低优先级任务,它被一个中等优先级的任务抢占了,等锁的高优先级任务就被间接饿死——因为二值信号量**不会把持锁者临时提权**,它压根不知道锁在谁手里。而且它没有所有权,任何任务都能"替别人开锁"。

## 2. 计数信号量:攒 N 件事,或池化 N 个资源

```c
SemaphoreHandle_t cnt = xSemaphoreCreateCounting(10, 0);  // 最大 10,初始 0
```

同一个 API,两种用法,靠**初始值**区分:

| 用法 | 初始值 | 语义 | 例子 |
|---|---|---|---|
| **事件计数** | 0 | 来一件事 +1,处理完 -1,能"欠账" | 统计一段时间内来了几次脉冲 |
| **资源池** | N | 表示有 N 份可用资源,借一个 -1,还一个 +1 | 3 个串口缓冲区的使用权 |

**利**:不像二值信号量那样丢事件,能攒。
**弊**:仍然**不带数据**——只知道"有几件事",不知道"是什么事"。要带内容还得用队列。

`freertos/FreeRTOSConfig.h` 里 `configUSE_COUNTING_SEMAPHORES` 已经打开,直接用。

## 3. 中断里怎么用:FromISR 家族

### 3.1 为什么中断里不能调普通版

三个理由,缺一不可:

1. **会阻塞**。`xQueueSend(q, &d, portMAX_DELAY)` 在队满时会把自己挂起——**中断不是任务,没有 TCB,挂起谁?**
2. **不能等**。ISR 必须尽快返回,在里面等 = 整个系统卡住。
3. **有所有权**。互斥量"把持锁者提升优先级"这套机制,在中断上下文里没有意义。

所以每条会在中断里用的 API,都有一个 `...FromISR` 分身:**它从不阻塞,满了/空了就返回失败。**

### 3.2 中断版长什么样

```c
BaseType_t xHigherPriorityTaskWoken = pdFALSE;

xQueueSendFromISR(key_queue, &evt, &xHigherPriorityTaskWoken);  // 不阻塞,发不进去返回 pdFAIL
portYIELD_FROM_ISR(xHigherPriorityTaskWoken);                    // 告诉内核:要不要现在就切
```

### 3.3 `xHigherPriorityTaskWoken` 到底是干嘛的

新手最懵的一个参数。拆开看:

1. 中断里 Give / Send,内核把等着的任务从 **Blocked 挪到 Ready**
2. 但**中断里不做上下文切换**——那是 PendSV 的活
3. 如果被唤醒的任务优先级**高于**当前被打断的任务,就应该"出中断时立刻切"。`xHigherPriorityTaskWoken` 就是这件事的回执
4. `portYIELD_FROM_ISR()` 内部**挂起 PendSV**,让切换在中断退出后立刻发生

**不调会怎样**:高优先级任务要**等到下一个 tick(1ms)** 才被调度。功能上"能跑",但中断响应性能白扔了。

**这就是"事件发生的瞬间立即抢占"的落地方式**:抢占的触发点不在 tick 里,而在 `portYIELD_FROM_ISR` 挂起的那次 PendSV 上。

**利弊**:`portYIELD_FROM_ISR` 让中断退出时多一次上下文切换开销,换来微秒级响应。实时系统里这笔交换永远划算。

### 3.4 对照你工程:`api/usart1.c` 的串口接收

`api/usart1.c` 的 `USART1_IRQHandler` 现在是**最原始的"中断打标记 + 主循环轮询"模型**:

- `USART1_IRQHandler` 把收到的字节塞进 `str_buf`,收到一整帧(检测到 IDLE)就把 `usart_flag` 置 1
- **而 `usart_flag` 全工程没有任何地方读它** —— 裸机轮询模型的残留,数据收进来了没人管

**现象**:串口助手发什么都不会有反应(除非你自己在别处轮询 `usart_flag`)。系统看起来"正常",但这个中断白跑了。

**怎么改**,三步:

1. 中断里不再直接往外暴露全局数组,而是**发一个信号量**(或把数据丢进队列——队列能带内容)
2. 建一个串口处理任务,用 `xSemaphoreTake(..., portMAX_DELAY)` 阻塞等着
3. 中断里改用 `...FromISR` 版本,并用 `xHigherPriorityTaskWoken` + `portYIELD_FROM_ISR` 触发切换

**为什么这么改**:中断服务时间从"填数组 + 判帧"缩短到"丢一个信号量",ISR 越短,系统对其它中断的响应越及时;而真正耗时的解析搬到任务里,可以随便阻塞、随便打印。

**代价**:多一个任务(多一份 TCB + 栈)、多一份队列/信号量内存。对 8KB 堆来说是要算一算的账。

## 4. 优先级天花板:整个工程最危险的一个数

### 4.1 规则

FreeRTOS 的中断版 API **不是随便哪个中断都能调的**。门卫在 `freertos/FreeRTOSConfig.h`:

```c
#define configMAX_SYSCALL_INTERRUPT_PRIORITY  ( 0xB0 )
```

`0xB0` 的高 4 位是 `1011` = **11**(配合 `configPRIO_BITS` 为 4)。规则:

> **抢占优先级数值 ≥ 11 的中断,才可以调 `...FromISR` API。
> 数值 0~10 的中断,一个 FreeRTOS API 都不许碰。**

### 4.2 为什么方向这么反直觉

Cortex-M 的优先级**数值越小越紧急**。`0xB0` 的含义是:"数值 11 是内核能屏蔽的最高紧急度"。

比它更紧急的中断(0~10),内核**关不掉**:

- `taskENTER_CRITICAL()` 关不掉它
- 调度器也拦不住它
- 如果它正在改内核链表,而内核自己也正改到一半 → **链表被撕坏**

所以这条规则不是"不建议",是**物理上做不到互斥**。

### 4.3 你工程现在的实际情况

`user/main.c` 的 `main()` 里设了 `NVIC_PriorityGroupConfig(NVIC_PriorityGroup_4)`——4 位全给抢占优先级。对照源码里三个 ISR 的配置:

| 中断服务函数 | 文件 | 抢占优先级 | 能否调 FromISR |
|---|---|---|---|
| `TIM1_UP_TIM10_IRQHandler` | `api/tim.c` | 1 | ❌ 禁止 |
| `DMA2_Stream5_IRQHandler` | `api/dma.c` | 1 | ❌ 禁止 |
| `USART1_IRQHandler` | `api/usart1.c` | 3 | ❌ 禁止 |
| —— 门槛 —— | | **≥ 11** | ✅ |

**现在没出事,纯属这三个 ISR 里一行 FreeRTOS 调用都没有。** 但它们恰恰是最想改造的三个:串口收指令、DMA 收完一帧、定时器到点——每一个的理想归宿都是"中断里 Give 一下,任务里处理"。

### 4.4 现象 / 怎么改 / 为什么

**现象**:在优先级 3 的 USART1 中断里调 `xQueueSendFromISR`,系统会**当场卡死**——不是"偶发出错",是直接停在 `freertos/port/port.c` 的 `vPortValidateInterruptPriority` 里那句 `configASSERT( ucCurrentPriority >= ucMaxSysCallPriority )`。而这个 `configASSERT` 在 `freertos/FreeRTOSConfig.h` 里被定义成:

```c
#define configASSERT(x)  if ((x) == 0) { taskDISABLE_INTERRUPTS(); for (;;); }
```

也就是**关中断 + 死循环**。串口不再有任何输出,LED 也不再动,在线调试时点暂停就能看到 PC 卡在这里。

**怎么改**:把要用 FromISR 的中断抢占优先级改成 **≥ 11**(常用 11 或 15)。改 `NVIC_InitTypeDef` 的 `NVIC_IRQChannelPreemptionPriority` 字段。

**为什么**:改成 ≥ 11 之后,这些中断就落进"内核能屏蔽"的区间,内核临界区能把它们挡在门外,内核数据结构的完整性才有保障。

**但要权衡**:代价是这个中断的响应延迟会变大——它现在会被临界区挡住。所以**真正要求极低延迟、且绝不碰 FreeRTOS API 的中断(比如电机紧急刹车),反而要故意留在 0~10**。这是"实时性"和"内核安全"之间的一次明确取舍,不是无脑调大。

## 5. 临界区:比互斥量更底层的保护

### 5.1 三个 API

```c
taskENTER_CRITICAL();     // 任务里进
/* 这里不许调任何会阻塞的 API */
taskEXIT_CRITICAL();      // 任务里出

portSET_INTERRUPT_MASK_FROM_ISR() / portCLEAR_INTERRUPT_MASK_FROM_ISR()   // 中断里用的版本
```

### 5.2 原理:BASEPRI,不是关总中断

`taskENTER_CRITICAL()` 做的是**把 `BASEPRI` 寄存器设成 `configMAX_SYSCALL_INTERRUPT_PRIORITY`**。

- 后果一:**优先级数值 ≥ 11 的中断全部被挡住**
- 后果二:**优先级 0~10 的中断照样冲进来** —— 你的 TIM10(1)、DMA(1)、USART1(3) 全在这个区间

**所以临界区护不住你的高速中断。** 如果临界区在改一个"高速中断也会改"的变量,光靠临界区不够——要么把中断优先级调到 ≥ 11,要么用关总中断的版本(`taskDISABLE_INTERRUPTS` / `portDISABLE_INTERRUPTS`)。

### 5.3 什么时候用哪个

| 场景 | 用什么 | 为什么 |
|---|---|---|
| 任务 ↔ 任务,共享一份资源 | 互斥量 | 能阻塞、有优先级继承 |
| 任务 ↔ **中断**,共享一个变量 | **临界区** | 中断里不能 Take 互斥量(会阻塞) |
| 改几行全局标志 | 临界区 | 开销比互斥量小得多(几十个周期 vs 一次上下文切换) |

### 5.4 利弊与坑

**利**:极快,不触发任务切换,中断上下文也能用。

**弊**:
1. **它不阻塞,它"屏蔽"**。临界区里等不到东西,只能空转或失败——所以**绝不能在临界区里调 `vTaskDelay` / `xQueueReceive`**,那等于把整个系统锁死几毫秒
2. **临界区越长,中断延迟越大**。所有 ≥11 的中断都得排队等你。原则:**只圈几行赋值,别圈循环**
3. **中断里必须用 `..._FROM_ISR` 版本**,任务里用普通版本,不能混用

## 6. 选型表(更新)

| 场景 | 用 |
|---|---|
| A 任务把**数据**交给 B 任务 | 队列 |
| 多个任务共用**同一份资源** | 互斥量 |
| 中断喊一声"有事了",不带数据 | **二值信号量** |
| 攒 N 件事 / 池化 N 个资源 | **计数信号量** |
| 保护**中断和任务**共享的资源 | **临界区** |
| 中断里发数据给任务 | **队列 / 信号量的 FromISR 版** |
| 只喊一嗓子,且只喊给特定一个任务 | 任务通知(更轻,但一对一) |

## 7. 验证实验:让串口接收走进 FreeRTOS

**起点**:`api/usart1.c` 的 `USART1_IRQHandler` 已经在收数据了,但 `usart_flag` 全工程没人读——等于白收。

**目标**:把"中断 → 信号量 → 任务处理"这条链路接起来。

1. `api/usart1.c` 的 `usart1_Config` 里,把 `USART1_IRQn` 的抢占优先级从 3 改成 **15**
2. 建一个二值信号量;`USART1_IRQHandler` 在 IDLE 分支里 `xSemaphoreGiveFromISR(...)` + `portYIELD_FROM_ISR(...)`
3. 建一个接收任务,`xSemaphoreTake(..., portMAX_DELAY)` 拿信号量,拿到就把 `str_buf` 打印出来
4. **故意做反面实验**:优先级改回 3,重跑

**观察点**:
- 优先级 15:一切正常,串口发一串字符,任务立刻打印
- 优先级 3:**这是重点**。预期是当场卡死(见 4.4 节)。亲手撞一次 `configASSERT`,比看十遍文档记得牢

## 8. 自测

1. `xSemaphoreCreateBinary()` 之后立刻 `xSemaphoreTake(bin, 0)`,会成功吗?
2. 中断里连发 3 次 `xSemaphoreGiveFromISR`,消费者只 Take 了 1 次。还剩几次?
3. 你的 `TIM1_UP_TIM10_IRQHandler` 优先级是 1,能不能在里面调 `xTaskGetTickCountFromISR()`?
4. `taskENTER_CRITICAL()` 执行期间,你那个优先级 3 的 USART1 中断能不能进来?
5. 为什么互斥量不能在中断里 Take?

---

<details>
<summary>答案(点开)</summary>

1. **不会**。`xSemaphoreCreateBinary()` 创建出来是空的(不可用),要先 Give 一次才能 Take 到。
2. **剩 1 次**。第一次 Give 置 1,后两次 Give 时已经是 1,无效。二值信号量不锁存——这是它和队列最大的区别。
3. **不能**。优先级 1 低于门槛 11,在那里调任何 FreeRTOS API(包括 `...FromISR` 版)都会撞 `configASSERT`。要调就得先把它改成 ≥ 11。
4. **能**。临界区靠 BASEPRI 只挡住优先级 ≥ 11 的中断,优先级 3 的中断内核管不着,照样冲进来。这是"临界区护不住高速中断"的直接证据。
5. 因为互斥量**有所有权、会阻塞**。中断没有 TCB 可以挂起,也不该在 ISR 里等锁。中断和任务之间要同步,用二值信号量或队列的 FromISR 版。

</details>
