# 优先级翻转、优先级继承、优先级天花板、互斥量与二值信号量的区别

> 一句话定位:**优先级翻转是"高优先级任务被低优先级任务堵住,还被中优先级任务插队"的现象;FreeRTOS 的解法是优先级继承 —— 它不是什么高级功能,而是"互斥量"这个东西和"二值信号量"唯一的、也是最要命的区别。**

---

## 1. 现象:翻转长什么样

### 1.1 三个角色的最小模型

只要有**三个不同优先级的任务**和**一把共享的锁**,翻转就能发生:

| 角色 | 优先级 | 干什么 |
|---|---|---|
| H(High) | 高 | 偶尔要用一下共享资源 |
| M(Middle) | 中 | 一个跟共享资源**毫无关系**的长工 |
| L(Low) | 低 | 平时抱着共享资源干活 |

### 1.2 时序

```
L 拿到锁,开始干活
        │
H 醒来,要这把锁 ──▶ 拿不到,进 Blocked
        │
        │   ★ 此刻 L 应该赶紧干完、把锁交出来 ★
        │
M 醒来(它跟这把锁一点关系都没有)
        │
        │   L 优先级比 M 低 ──▶ L 被 M 抢断,M 一直跑
        │
        ▼
   H 只能干等 —— 等 M 跑完,L 才捞得着 CPU,才轮到把锁还给 H
```

**H 的实际等待时间 = L 干完 + M 跑完。**

### 1.3 名字里的两层讽刺

1. **"翻转"(inversion)**:优先级关系被**倒过来了**。名义上 H > M > L,实际效果是 **M > H**(M 能插在 H 前面无限久)。
2. **"无界"(unbounded)**:H 等多久,取决于 M 跑多久。**这跟 L 和 H 都没关系了** —— 一个不相干的任务,决定了 H 的响应时间。

> **这是优先级翻转真正可怕的地方:它不是"慢了一点",而是"实时性保证整个失效了"。** 你按最坏情况算出来的响应时间,在这里被一个第三方任意拉长。

### 1.4 真实事故

1997 年火星探路者号(Mars Pathfinder)在火星上反复重启。原因就是优先级翻转:一个低优先级的气象任务抱着一条共享的 VxWorks 管道,中优先级的通信任务把它抢断了,高优先级的看门狗任务迟迟喂不上狗 → 系统复位。

**代码没有"错",错的是"没开优先级继承"。** 这个 bug 在实验室里几乎复现不出来,只有在真实负载下才偶发 —— 这也是为什么它值得单独记住。

## 2. 原理:为什么会发生

两个前提,缺一不可:

1. **有共享资源,且用锁保护**
2. **调度器是抢占式的**(本工程 `FreeRTOSConfig.h` 里 `configUSE_PREEMPTION` 为 1)

在抢占式调度下,"优先级"表达的是一句承诺:**高优先级任务一就绪,立刻拿到 CPU**。

锁打破了这句承诺 —— 因为**持锁的那个任务没就绪,别人拿到 CPU 也没用**(资源在 L 手里)。于是调度器陷入两难:

- 让 H 跑 → H 也用不了资源,白跑
- 让 L 跑 → 违反了"高优先级先跑"

FreeRTOS 默认选后者(L 继续跑),于是 H 被降格成"等 L"。**这是"锁"和"抢占"这两种机制天生的矛盾,不是实现缺陷。**

### 2.1 关键区分:翻转 vs 普通的"等锁"

| | 高优先级任务等一把锁 | 优先级翻转 |
|---|---|---|
| H 在等谁 | 就等 L 一个 | 等 L **+ 等 M(不相干的第三方)** |
| H 等多久 | L 干完剩下的活,有上界 | **无上界** —— 取决于 M |

**H 等锁是正常的、不可避免的(H 确实需要那个资源)。翻转是额外多出来的、本不该有的延迟。**

## 3. 解法一:优先级继承(FreeRTOS 的做法)

### 3.1 一句话原理

> **谁挡了高优先级任务的路,就把谁的优先级临时提到跟高优先级一样高 —— 让他赶紧干完、赶紧放锁。**

回到 §1.2 的时序,加上继承之后:

```
L 拿到锁
H 醒来要锁 ──▶ 拿不到,Blocked
        │
        ▼
   ★ L 的优先级被临时提到 H 的等级 ★
        │
M 醒来 ──▶ 此时 L 优先级 = H > M ──▶ M 抢不动了
        │
L 干完,把锁交给 H
        │
        ▼
   ★ L 的优先级掉回原来的等级 ★   M 这才轮到
```

**关键点:L 的优先级只在"抱着锁"的这一小段时间里被抬高。** 它不是"任务优先级被永久改了",是临时借的。

### 3.2 FreeRTOS 里到底怎么实现的

看源码 `freertos/src/queue.c` 和 `freertos/src/tasks.c`。整套机制是围绕**两个 TCB 成员**(`tasks.c` 里的 `TCB_t`)转的:

| 成员 | 作用 |
|---|---|
| `uxBasePriority` | **我本来是谁** —— 任务创建时/被 `vTaskPrioritySet` 改过之后,那个"真实"优先级 |
| `uxPriority` | **我现在是谁** —— 调度器实际按这个排座次 |

**正常情况下两者相等。继承就是把 `uxPriority` 临时改大,`uxBasePriority` 原封不动** —— 这就是"回得去"的凭据。

一次完整的继承-归还循环,涉及四个位置:

| 时机 | 位置 | 干了什么 |
|---|---|---|
| 拿到互斥量 | `queue.c` 的 `xQueueSemaphoreTake` | 把 `xMutexHolder` 记成自己(`pvTaskIncrementMutexHeldCount`) |
| 拿不到,要阻塞 | `queue.c` 的 `xQueueSemaphoreTake` | 调 `xTaskPriorityInherit( xMutexHolder )` |
| 等的人超时了 | `queue.c` 的 `xQueueSemaphoreTake` | 调 `vTaskPriorityDisinheritAfterTimeout(...)` |
| 归还互斥量 | `queue.c` 的 `prvCopyDataToQueue` | 调 `xTaskPriorityDisinherit(...)`,再把 `xMutexHolder` 清成 NULL |

`tasks.c` 里那三个函数的逻辑,值得逐条抠:

**`xTaskPriorityInherit( pxMutexHolder )`**

- 前提:`pxMutexHolderTCB->uxPriority < pxCurrentTCB->uxPriority` —— 只有"我比你好说话"才需要继承。**已经比我高了就什么都不做**(这是"只升不降"的保证)
- 抬完还要**把持锁者从旧的就绪链表挪到新优先级的链表**:`uxListRemove` + `prvAddTaskToReadyList`。**这一步不能漏** —— 优先级只是个数字,调度器真正看的是链表
- 有个特例:调用者不是任务(持锁者是 NULL)时不继承

**`xTaskPriorityDisinherit( pxMutexHolder )`**

- `configASSERT( pxTCB == pxCurrentTCB )` —— **"只有持锁者本人能还锁"**。这一句就是"互斥量不能在中断里 Give"的守卫
- `pxTCB->uxMutexesHeld` 这个计数器**减一**
- **只有减到 0 才降回去**:`if( pxTCB->uxMutexesHeld == 0 )`。也就是说,一个任务如果同时抱着两把锁,只有当**最后一把**还掉时才恢复原优先级 —— 否则会错误地提前降级,又在第二把锁上被翻转
- 降回去 = 把 `uxBasePriority` 抄回 `uxPriority`,同样要挪就绪链表

**`vTaskPriorityDisinheritAfterTimeout( pxMutexHolder, uxHighestWaitingPriority )`**

专门处理"等的人超时了"这个情况。**注意它降到的不是原始优先级,而是"还在等这把锁的人里最高的那个"** —— 因为持锁者可能同时还在被另一个中优先级的任务等着,直接降到底会制造新的翻转。这个参数由 `prvGetHighestPriorityOfWaitToReceiveList` 算出来。

### 3.3 为什么叫"继承"而不是"提升"

**优先级是从等待者那里"借"来的** —— 借多少,取决于当时**有多少人在等、等的最高是谁**。没人等了(或等的人超时了),就还回去。

这解释了实现里的一个细节:`xTaskPriorityInherit` 的开头判断是 `uxPriority <`,**不是 `uxBasePriority <`**。因为它要处理的就是"持续有人来等"的情况。

### 3.4 继承的局限(必须知道)

1. **只解决单层,不解决链式**。如果 **L 抱着锁 A,又去等 M 手里的锁 B**,而 **H 在等 L 的锁 A** —— H 的优先级只能传到 L,**传不到 M**。H 还是会被卡住。这种情况要么靠"锁的获取顺序全工程统一"来避免,要么用下文的优先级天花板。
2. **只在"要阻塞"的那一刻才提升**。如果高优先级任务用的是 `xSemaphoreTake(lock, 0)`(不等就走),它压根不会进阻塞,继承也不发生。
3. **代价是"优先级乱动"**。调试时看到某个任务优先级突然变成了 4,别慌,那是继承生效了 —— 这也意味着 `uxTaskPriorityGet` 拿到的**不一定是它真实的等级**。
4. **有微小开销**:继承时要进临界区、操作两个链表。对本工程这点量级完全无所谓。
5. **它保证不了"有界"** —— 它只是把 §1.2 里那个 M 从路上挪开。如果 L 抱着锁卡在别的地方(自己又去等别的锁、或被中断拖住),H 照样等。

## 4. 解法二:优先级天花板(Priority Ceiling)

### 4.1 原理

换个思路,不在"出事之后补救",而在"拿锁的时候就一劳永逸":

> **给每把锁预先规定一个"天花板优先级" = 所有可能用这把锁的任务里最高的那个。谁拿到这把锁,谁的优先级立刻被抬到天花板。**

回到 §1.2:L 一拿到锁,优先级**当场**就是 H 的等级。M 从头到尾就没机会插进来 —— **翻转在它发生之前就被堵死了**。

### 4.2 和优先级继承对比

| | 优先级继承 | 优先级天花板 |
|---|---|---|
| 什么时候提升 | **等出事了**(有高优先级任务真的来抢)才提 | **一拿锁就提**,不管有没有人来抢 |
| 提升到多高 | 当时**最高的等待者**的等级 | 锁的**预定义**天花板 |
| 要不要知道谁来抢 | 不用,运行时动态判断 | **要** —— 必须提前知道"谁会用它" |
| 一次场景要抬几次 | 每次有人来抢都可能要调整 | 一次(拿的时候),放锁时还原 |
| 能防住链式翻转吗 | **不能**(见 §3.4) | **能** —— 天花板一路顶到底 |
| 代价 | 运行时开销小;提升时机晚 | 提得早,**低优先级任务抱着锁时长期占着高优先级**,可能无谓地压制别人 |

**天花板更"稳"(从根上堵住),继承更"灵活"(只在需要时动)。**

### 4.3 FreeRTOS 有没有天花板?

**没有。** FreeRTOS 的互斥量(`xSemaphoreCreateMutex`)只实现优先级继承,不提供天花板的 API。

原因很实际:**天花板要求"锁的天花板优先级"这个信息由人手工算准**,算错了(漏了一个使用者、或者之后有人加了新的使用者)反而会出更隐蔽的问题。继承不需要这个先验知识。

所以在本工程里,**"怎么解决优先级翻转"的现实答案就是:用互斥量,别用二值信号量。**

## 5. 解法三:绕开它(最有效,也最常被忽略)

**最好的临界区是没有临界区。**

| 做法 | 说明 |
|---|---|
| 不共享 | 每个任务自己一份数据。RAM 够就最省心 |
| 缩短临界区 | 锁只包住"必须原子"的那几行。**本工程 `api/debug.c` 的 `print_line` 锁包住整个 `printf`,是对的** —— 因为打印的原子单位就是"一整行" |
| 降低使用频率 | 高优先级任务尽量少碰共享资源 |
| 换个结构 | SPSC 环形缓冲/单生产者单消费者结构**天然不需要锁** —— 见另一篇笔记的讨论 |

这一条优先级**高于**前两条:**能不共享就别共享,共享了就缩短窗口,实在不行才靠继承兜底。**

## 6. 核心结论:互斥量 ≠ 二值信号量

这是整篇笔记最实用的一条。

### 6.1 两者长得几乎一样

| | `xSemaphoreCreateBinary()` | `xSemaphoreCreateMutex()` |
|---|---|---|
| 底层 | 长度 1 的队列 | 长度 1 的队列(`queueQUEUE_IS_MUTEX`) |
| API | `Take` / `Give` | `Take` / `Give`(完全一样) |
| 初值 | **空**(要先 Give 一次) | **满**(建好就能 Take) |
| **优先级继承** | **没有** | **有** |
| **持有者概念** | **没有** | 有(`xMutexHolder`) |
| 递归 Take | 不行 | 不行(要用 `xSemaphoreCreateRecursiveMutex`) |
| 中断里 Give | **可以** | **绝对不行** |

**前四行看起来只是小差别,后三行才是本质。**

### 6.2 为什么二值信号量给不了继承

源码里写得很直白:`queue.c` 的 `xQueueSemaphoreTake` 里,那句记录持有者的

```
pxQueue->u.xSemaphore.xMutexHolder = pvTaskIncrementMutexHeldCount();
```

**外面套着 `if( pxQueue->uxQueueType == queueQUEUE_IS_MUTEX )`。**

也就是说:**只有互斥量才知道"现在是谁拿着我"。** 二值信号量根本没有 `xMutexHolder` 这个概念 —— 有这个概念,才谈得上"把持有者的优先级抬起来"。

这一句就是"二值信号量**不能**当锁用"的全部理由。

### 6.3 反过来:互斥量也不能当门铃用

**互斥量不能在中断里 Give。** 证据在 `tasks.c` 的 `xTaskPriorityDisinherit` 开头:

```
configASSERT( pxTCB == pxCurrentTCB );
```

这句断言的含义是:**"还锁的人必须就是当前正在跑的那个任务"**。

中断不是任务,所以从中断里 `xSemaphoreGive` 一把互斥量,这个断言就会炸。而且就算不炸,继承逻辑也无从下手 —— 该把谁降回去?

### 6.4 一句话判据

> **看你要的是"保护"还是"通知":**
>
> - **保护一块共享资源** → **互斥量**(`xSemaphoreCreateMutex`)。因为它带优先级继承
> - **任务之间 / 中断到任务的"有事发生"** → **二值信号量**(`xSemaphoreCreateBinary`)。因为它能从 ISR 里 Give

**两者的区别不在于"能不能互斥" —— 二值信号量也能凑合互斥。区别在于"互斥时会不会翻转"。**

## 7. 对照本工程

### 7.1 已经在正确使用的一处:`api/usart1.c` 的 `usart_rx_sem`

**这是二值信号量,而且是从 `USART1_IRQHandler` 里 Give 的 —— 用的完全正确。**

它的角色是**通知**(中断告诉任务"来了一帧"),不是**保护**。按 §6.4 的判据,这里**必须**用二值信号量:

- 用互斥量的话,ISR 里那句 Give 会撞上 `configASSERT( pxTCB == pxCurrentTCB )`
- 而且这里也确实没有"资源被谁占着"的问题 —— 它传递的是事件

### 7.2 另一处:`api/debug.c` 的 `print_mutex`

**这个是互斥量,也用对了** —— `xSemaphoreCreateMutex` 建出来的,保护的是"USART1 的发送通道"这块共享资源。

本工程 `user/main.c` 里的优先级分布,正好就是一个**潜在的翻转现场**:

| 任务 | 优先级 | 和 `print_mutex` 的关系 |
|---|---|---|
| `print_task1` | 2 | **抱着锁打印 48 字符(约 4.2ms)** |
| `led_task` | **3** | 不打印 —— **中间优先级** |
| `print_task2` | 4 | 每 100ms 来抢锁 |
| `usart_rx_task` | 4 | 回显时也要抢锁 |

把名字套进 §1.2 的模型:

```
L = print_task1(2)  ← 抱着 print_mutex 慢慢打印
H = print_task2(4)  ← 醒来要这把锁
M = led_task(3)     ← 跟打印毫无关系
```

**没有继承的话**:`print_task2` 醒来拿不到锁 → `print_task1` 被 `led_task` 抢断 → `print_task2` 只能等 `led_task` 睡着(它 `vTaskDelay(500)`)。

**有了继承**:`print_task2` 一进阻塞,`print_task1` 的 `uxPriority` 就被抬到 4,`led_task`(3)再也抢不动它,打印完立刻交锁。

### 7.3 一个诚实的补充:本工程现在基本观察不到翻转

原因很直接:**`led_task` 这个"中间优先级长工"不常驻**。它 `vTaskDelay(500)` 睡 500ms,醒来也没干什么实事(那行模拟栈溢出的 `die(5)` 是注释掉的)。

**翻转的窗口 = `print_task1` 还在打印的 4.2ms 里、恰好 `led_task` 醒了。** 概率极低。

**想亲眼看到翻转**,得把 M 造出来:比如再写一个优先级 3 的 `while(1)` 空转任务(不加 `vTaskDelay`),然后:

1. 把 `debug.c` 的 `xSemaphoreCreateMutex()` 换成 `xSemaphoreCreateBinary()` + 建好之后先 Give 一次(手动造一把"能互斥但没继承"的锁,`xSemaphoreCreateBinary` 初值是空的,不先 Give 会直接 Take 失败)
2. 观察 `print_task2` 的输出间隔 —— 会被拉长
3. 换回 `xSemaphoreCreateMutex()`,间隔恢复正常

这是本工程验证继承最直接的一个实验。

## 8. 陷阱清单

| 陷阱 | 现象 | 原因 |
|---|---|---|
| **用二值信号量当锁** | 平时挺好,一加个中间优先级任务就偶尔卡顿一下,负载越重越明显 | 没有优先级继承(§6.2) |
| **从 ISR 里 Give 互斥量** | `configASSERT` 触发 → `taskDISABLE_INTERRUPTS()` + `for(;;)` 死循环,整个系统停住 | `xTaskPriorityDisinherit` 要求持锁者 == 当前任务(§6.3) |
| **用互斥量做 ISR→任务的同步** | 同上 | 同上。同步请用二值信号量或任务通知 |
| **在一个任务里换优先级,又困惑于 `uxTaskPriorityGet` 的值** | 读到的是"临时值"不是真实值 | 继承改的是 `uxPriority`,`uxBasePriority` 才是本色(§3.2) |
| **持锁时长失控(锁里调用 `vTaskDelay`、`printf`、等别的锁)** | 继承也救不了,高优先级任务照样等很久 | 继承只能挪开第三方,不能缩短 L 本身的持锁时间(§3.4) |
| **锁的获取顺序不一致** | 两个任务互相等对方手里的锁,双双卡死 | 这是**死锁**,不是翻转。约定"全工程按同一顺序拿锁" |
| **用 `xSemaphoreTake(lock, 0)` 轮询** | 拿不到就忙等,继承不生效 | 不进阻塞就不会触发继承(§3.4) |

---

## 9. 一句话总结

**优先级翻转 = 高优先级任务被低优先级任务堵住,还被不相关的中优先级任务插队,导致等待时间无上界。**

它的根源是**"锁"和"抢占式调度"天生矛盾** —— 不是谁写错了代码。

FreeRTOS 的答案:**把锁做成"互斥量"而不是"二值信号量"**,让内核在有人来抢锁的瞬间把持锁者的优先级临时抬起来。

**记住那条判据就够了:保护资源用互斥量(带继承),传递事件用二值信号量(能在 ISR 里 Give)。**
