# WiFi 模块的架构:把一个模块当成"独立的小电脑"来指挥

> 一句话定位:**STM32 不跑 TCP/IP,也不跑 MQTT —— WB2 模块自己跑。MCU 这边只做一件事:
> 用 AT 命令行把模块的状态"问出来",再根据答案决定下一步做什么。**
> 所以 `wifi.c` 的本质不是网络编程,是一个**建立在字符串收发之上的状态机**。

> ⚠ 这份笔记里最值钱的不是"怎么连上 WiFi",而是第 3、4 节:
> **AT 命令的语义和直觉不一样("OK"不等于"办成了"),以及"配网成功"的判据一开始就是错的。**
> 这两条各花了一整轮上板调试才纠正过来。

> 相关:[开锁业务的架构.md](开锁业务的架构.md)(`wifi_task` 投递的 `lock_cmd_queue` 在那边)、
> [EEPROM与Flash存储选型.md](EEPROM与Flash存储选型.md)、[I2C通信与推挽开漏选型.md](I2C通信与推挽开漏选型.md)

## 1. 硬件与职责分工

| 角色 | 器件 | 接口 |
| --- | --- | --- |
| WiFi + BLE | Ai-Thinker **WB2**(Combo,跑 AT 固件) | USART2:PA2=TX / PA3=RX,AF7,115200 |
| 凭据存储 | AT24C04A EEPROM | 软件 I2C,SCL=PA8 / SDA=PC9 |
| 调试输出 | USART1 | PA9/PA10,115200,`printf` 重定向到这里 |

**分工的重点在于"谁跑协议栈"**:

```
   云端 broker
       ↑ MQTT over TCP
   ┌───┴────────────────┐
   │   WB2 模块          │  ← 这里面有 WiFi 协议栈、TCP、MQTT、TLS、BluFi 配网
   │  (一台独立小电脑)   │
   └───┬────────────────┘
       │ 串口,只有两种东西:命令字符串 和 应答字符串
   ┌───┴────────────────┐
   │   STM32F401         │  ← 没有 LwIP、没有 socket、没有 malloc 出来的报文缓冲
   │   只发 AT 命令       │
   └────────────────────┘
```

**为什么这样分:** 让 STM32 自己跑 TCP/IP + MQTT,光协议栈就要几十 KB RAM
(本工程堆一共才 12KB),还要处理证书、重传、心跳。模块已经把这些做完了,
串口这条线只要 115200 × 2 根线,代价小两个数量级。

**代价是什么:** 出问题的时候,你看不见 TCP 层发生了什么。模块只会告诉你
"连不上",不会告诉你"是 DNS 解析失败还是 broker 拒绝"。所以第 3 节那些
"把状态问出来"的手段,是这套架构能不能维护的关键。

## 2. 分层总图

从上到下六层,每层只干一件事:

```
┌─ 业务层 ────────────────────────────────────────────────────────┐
│  wifi_session()          常驻收发:收下发、发心跳                  │
│    ├─ wifi_handle_sub_event()  拆 +EVENT:MQTT_SUB,<topic>,<len>,<data>
│    │    └─ wifi_handle_downlink()  JSON → lock_post_cmd()        │
│    └─ 心跳 AT+MQTTPUB (10s 一条)                                 │
├─ 动作层 ────────────────────────────────────────────────────────┤
│  wifi_wifi_join()        连 WiFi(凭据来自 EEPROM)               │
│  wifi_mqtt_connect()     配 7 条参数 + 连接 + 等事件 + 订阅       │
│  wifi_ble_provision()    蓝牙配网(整机只自动做一次)              │
│  wifi_ap_creds_save()    配网成功后把凭据抄回 EEPROM              │
├─ 状态查询层 ────────────────────────────────────────────────────┤
│  wifi_is_wifi_up()       AT+WJAP?      → status == 3 ?           │
│  wifi_is_mqtt_up()       AT+MQTT?      → 连接在不在              │
│  wifi_is_subscribed()    AT+MQTTSUB?   → 话题在不在册            │
│  wifi_wifi_config_status() AT+WCONFIG? → 配网任务开没开          │
├─ 命令层 ────────────────────────────────────────────────────────┤
│  wifi_at_ex(cmd, watch, cap, size, timeout)                      │
│      发命令 → 逐行收 → 直到 OK/ERROR;顺带把 watch 关键字那行捞出来 │
│  wifi_at_cmd()   简化版:不关心内容,只想知道成没成               │
│  wifi_wait_event() 等模块**主动上报**某个事件                     │
├─ 行层 ─────────────────────────────────────────────────────────┤
│  wifi_read_line()  收到 '\n' 为止,去掉 '\r';超长只保留前面继续吞 │
│  wifi_get_byte()   从环形缓冲取一字节,取不到就 vTaskDelay 等      │
├─ 字节层 ───────────────────────────────────────────────────────┤
│  USART2_IRQHandler()  每来一字节塞进 256 字节环形缓冲             │
│  wifi_send_line()     发字符串 + CRLF,等 TC 标志                 │
└────────────────────────────────────────────────────────────────┘
```

**六层里,只有最上面一层的代码是"业务",下面五层都是"把串口包装成能用"的机械劳动。**
`wifi.c` 1300 多行里一半以上是这个包装 —— 这不是臃肿,是 AT 命令这种接口的固有成本。

## 3. 五个关键设计决策

### 决策一:必须中断收,不能轮询收

MG200 指纹模块用的是"发完命令再逐字节轮询收"的写法(见 [api/MG200.c](../api/MG200.c)),
这里**不能照抄**。

**为什么:** 轮询接收只在"正在等应答"的那一刻才看串口。而 WB2 会**主动上报**,
时机完全不可预测:

```
+EVENT:MQTT_CONNECT
+EVENT:MQTT_DISCONNECT
+EVENT:MQTT_SUB,attributes/push,14,{"DoorLock":1}   ← 云端下发的消息
+EVENT:WIFI_CONNECT
+EVENT:WIFI_GOT_IP
```

这些事件可能落在两条 AT 命令之间的**任何**时刻。用轮询,它们就永远丢了 ——
现象是"设备明明在线,云端发的开锁命令就是收不到",而且**没有任何报错**。

所以这里必须用中断收:

```c
void USART2_IRQHandler(void)
{
    if (USART_GetITStatus(USART2, USART_IT_RXNE) != RESET)
    {
        uint8_t  b    = (uint8_t)USART_ReceiveData(USART2);
        uint16_t next = (uint16_t)((s_rx_head + 1) % WIFI_RX_BUF_SIZE);

        if (next != s_rx_tail) { s_rx_buf[s_rx_head] = b; s_rx_head = next; }
        else                   { s_rx_drop++; }        // 满了丢**新**字节
    }
}
```

四个细节:

| 细节 | 为什么 |
| --- | --- |
| 用 `head + 1 == tail` 判满 | 永远留一个空位,这样"空"和"满"不会混成同一种状态 |
| 满了丢**新**字节,不覆盖旧的 | 覆盖会把一行 AT 应答从中间截断,比丢整行更难查 |
| `s_rx_drop` 计数器 | 静默丢字节是这类架构最阴的 bug,留个计数器至少能发现 |
| **只开 RXNE,不开 IDLE** | 环形缓冲不需要按"帧结束"切分;AT 命令本来就是按 `\r\n` 分行的 |

> ⚠ **USART2 全工程只有 ISR 读它,没有任何地方做轮询读。**
> ISR 会先把 RXNE 读走,轮询就永远等不到数据 —— 这是 CLAUDE.md 里记着的一条坑,
> 混用两种收法的现象是"轮询那里一直超时"。

### 决策二:**"OK" 不等于"办成了"** ← 这一条最容易翻车

AT 命令的应答是**两段式**的:

```
AT> AT+MQTT
AT< OK                        ← 只代表"命令收到了",不代表"连上了"
AT< +EVENT:MQTT_CONNECT       ← 过一会儿才来,这**才**叫连上
```

**只等 OK 就去干下一步,在大局域网里看不出问题**(连得快),一连云端 broker 就现形 ——
broker 握手要几秒,这中间订阅发出去必然失败。

所以凡是"要等结果"的步骤都得等事件:

```c
if (!wifi_at_cmd("AT+MQTT", WIFI_T_CONN_MS))            return 0;   // 命令收到
if (!wifi_wait_event("+EVENT:MQTT_CONNECT", WIFI_T_CONN_MS))       // 事情办成
{
    printf("!! 没等到 MQTT_CONNECT,核对主机/端口/用户名/密码/ClientID\r\n");
    return 0;
}
```

#### 连带的坑:`+ERROR` **带加号**

模块报错回的是 `+ERROR`,不是 `ERROR`。用 `strcmp(line, "ERROR")` 精确比会**漏判**,
命令就一直傻等到超时才失败 —— WJAP 那种 25 秒超时的,等于每次白等 25 秒。

```c
if (strstr(line, "ERROR") != NULL) { return 0; }    // ← 必须用包含匹配
```

副作用是 `+EVENT:MQTT_MALLOC_ERROR` 这类主动上报也会命中提前返回,但那本来就是真错误,
提前返回反而是对的。

#### 连带的坑:"确保 X 就绪"的函数,第一句要先查 X

`wifi_mqtt_connect()` 原来每次重试都无条件重发一遍 7 条配置 + `AT+MQTT`。手册原话:

> If the current MQTT task has been started, it will reconnect if it is executed again

也就是**已连接时重发会强制断开重连**。现象是"一直不停的连上又断开",模块被反复逼着做
最耗资源的"拆了重建",broker 也被骚扰个没完。

```c
if (wifi_is_mqtt_up())          // ← 先查,不为省时间
{
    if (!wifi_ensure_subscribed()) return 0;
    return 1;                   // 已经好了,一个字都别发
}
```

> **教训推广:很多 AT 命令在"已就绪"状态下执行会起反作用。**
> 凡是叫 `ensure_xxx` / `make_sure_xxx` 的函数,第一句都应该是查状态。

### 决策三:凭据存 EEPROM —— 不存源码,也不指望模块记

WiFi 名和密码有三个地方可以放,每个都有代价:

| 放哪 | 换网的代价 | 问题 |
| --- | --- | --- |
| 源码里 `#define` | **重新编译 + 烧录** | 用户根本改不了;而且这对值会过期(实测 Windows 移动热点后缀从 `4127` 变成 `4128`) |
| 模块自己的 flash | 配一次网就行 | 固件**看不见也验证不了**;而且模块电源独立于 MCU,状态不完全可控(见 §7) |
| **AT24C04 EEPROM** | **配一次网就行** | 固件完全掌握:能读、能写、能验证 |

选了 EEPROM。于是流程变成:

```
   开机 → 从 EEPROM 读凭据
            ├─ 有 → AT+WJAP=<ssid>,<pwd>
            └─ 无 → 直接进配网(不空等)
   连上 → MQTT → 常驻收发
   连不上 → 蓝牙配网(整机只自动做一次)
            配成功后 AT+WJAP? 把凭据抄回来 → 写 EEPROM
```

**这里有个关键问题:配网时用户在手机上把 WiFi 名和密码发给了模块,固件手里一个字都没有,
怎么知道自己该存什么?**

答案在 `AT+WJAP?` 的应答里 —— 它**明文带着密码**:

```
AT> AT+WJAP?
AT< +WJAP:3,DESKTOP-HTLNPUV 4128,88888888,c2:bf:be:e2:09:9c,WPA2 TKIP,a8:17:10:68:2e:51,11,192.168.137.217,192.168.137.1
       ↑  ↑────────────────┘  ↑──────┘
     status     SSID            密码(明文!)
```

字段依次是:`status, ssid, pwd, bssid, 加密方式, MAC, 信道, IP, 网关`。
`wifi_ap_creds_save()` 就是把第 2、3 个字段切出来存进 EEPROM。

> **为什么"抄模块的"比"让用户再报一遍"靠谱:** 模块手里这份是**已经连成功过**的,
> 一定是可用的;用户手输一遍多一次出错机会,而且 UI 上还得再加一个输入界面。

### 决策四:配网成功的判据是"连上 WiFi",不是"模块说它在配网"

**这条是错的,而且错得很隐蔽,花了一整轮上板调试。**

原来的判据是"等模块自己把配网任务关掉(`AT+WCONFIG?` 变 0)"。实机日志推翻了它:

```
AT< +EVENT:WIFI_CONNECT      ← 配网成功了
AT< +EVENT:WIFI_GOT_IP       ← 拿到 IP 了
AT< +WCONFIG:2               ← 模块却一直报 2,它根本没打算自己关
```

后果很难查:设备明明配好了,却在这儿干等满 3 分钟。这段时间 `wifi_task` **整个堵着**,
MQTT 一直连不上。用户看到的是 **"手机说配网成功了,设备没反应"**。

**修法:判据落在"联网结果"上,而不是"模块的任务状态"上。**

```c
if (wifi_is_wifi_up())              // ← 主判据:读 AT+WJAP 的 status == 3
{
    got_link = 1;
    break;
}
st = wifi_wifi_config_status();     // ← 辅助判据:模块主动关了窗口
if (st == 0) break;
```

#### 连带的一个:`AT+WCONFIG=2` 重复发会被拒,而错误码毫无信息量

`AT+WCONFIG=<n>` 是**"开一次"**配网。模块已经在配网状态时重复发,它回:

```
AT< +WCONFIG:63
AT< +ERROR
```

`63` 是手册里的"通用错误码,不带任何细节"。拿它当"启动失败"就错了 ——
**判据应该是再查一次 `AT+WCONFIG?` 看是不是 2**:

```c
if (!wifi_at_cmd("AT+WCONFIG=2," WIFI_PROV_NAME, WIFI_T_CONFIG_MS))
{
    if (wifi_wifi_config_status() != 2) { /* 这才是真失败 */ }
    /* 否则:命令报错,但模块已经在配网了,继续等 */
}
```

**为什么会撞上这个:** 模块的电源**不和 MCU 一起断**。用户配网配到一半板子复位,
MCU 从零重跑,模块那边的配网任务还开着,于是问出来是 2 而不是 0。

> **教训:`AT+XXX:<错误码>` 的语义是"这个模块这次操作没成",不是"你哪里写错了"。**
> 含义对不上时,以**当前状态**为准 —— 先查状态,再决定要不要慌。

### 决策五:15 秒窗口,而且只自动配一次

```
   开机 ──────────────────────────────────────────────────► t
         0        2s              15s
         │         │               │
         │  等模块就绪  │  最多连到这儿   │
         │         │               └──► 进蓝牙配网(180s 窗口)
         │         │                        └──► 配成功后:立即重试,而且**再也不自动进配网**
```

两个常量分工:

| 常量 | 值 | 管什么 |
| --- | --- | --- |
| `WIFI_PROV_DEADLINE_MS` | 15000 | 开机多久没连上就**转配网** |
| `WIFI_T_PROV_MS` | 180000 | 配网窗口本身等多久 |

**"15 秒"这个承诺要往下传,不能让每层各管各的超时** —— `AT+WJAP` 自己的超时是 25 秒,
不掐住它,配网就拖到 20 多秒才开:

```c
static uint32_t wifi_join_budget(uint32_t boot)     // 每次**现算**,不能进循环前算一次
{
    uint32_t used = GetTim10Tick() - boot;
    uint32_t left = (used >= WIFI_PROV_DEADLINE_MS) ? 0 : (WIFI_PROV_DEADLINE_MS - used);

    return (left < WIFI_MIN_TRY_MS) ? WIFI_MIN_TRY_MS : left;
}
```

**"只自动配一次"靠的是 `s_prov_tried`,不是"配成才置位"的标志。**
触发条件是 "开机过了 15 秒 && 还没连上",而这个条件**过点之后永远为真** ——
用一个只在成功时才置位的标志去拦,用户没掏手机就会无限循环进配网,每次卡 3 分钟。
(这个 bug 真发生过,见 §6。)

## 4. `wifi_task` 主循环

```c
boot = GetTim10Tick();
have_cred = wifi_cfg_load(ssid, pwd);       // ← 开机第一件事:从 EEPROM 读凭据

for (;;)
{
    if (!wifi_at_cmd("AT", WIFI_T_AT_MS))   { /* 10s 后重试 */ continue; }
    wifi_at_cmd("AT+WMODE=1,1", ...);       // 切 STA 模式

    // ① 连 WiFi
    if (have_cred) up = wifi_wifi_join(ssid, pwd, s_prov_tried ? WIFI_T_WJAP_MS
                                                               : wifi_join_budget(boot));
    else           up = wifi_is_wifi_up();  // 没凭据,只能寄希望于模块自己连上了

    // ② 通了就连 MQTT,连上就常驻收发
    if (up && wifi_mqtt_connect())
    {
        wifi_session();                     // 只有 MQTT 掉线才返回
        up = wifi_is_wifi_up();             // 重新问一次,免得把"MQTT 掉线"误判成"WiFi 连不上"
    }

    // ③ 还是没连上 → 开一次蓝牙配网
    if (!s_prov_tried && !up)
    {
        s_prov_tried = 1;
        if (wifi_ble_provision()) have_cred = wifi_cfg_load(ssid, pwd);
        continue;                           // 别等那 10 秒,马上按新状态试一次
    }

    vTaskDelay(pdMS_TO_TICKS(WIFI_RETRY_MS));
}
```

三个不显眼但重要的地方:

| 写法 | 为什么 |
| --- | --- |
| 探活失败也在循环里重试,**永不退出** | 模块可能比 MCU 起得慢;线没插好插上之后不该还要求重启板子 |
| ② 里 `wifi_is_wifi_up()` 是**重新问一次** | `wifi_session()` 返回只说明 MQTT 掉了,WiFi 未必也掉了。不复查就会把"MQTT 掉线"误判成"WiFi 连不上"而去开配网 |
| ③ **没有**"必须等满 15 秒"这个条件 | 没有凭据时(第一次上电)会立刻走到这里。这是对的:没什么可试的,直接让用户配 |

**为什么 `wifi_wifi_join()` 内部还要再查一次 `AT+WJAP?`:** 有些固件在"已连接"状态下
重发 `AT+WJAP` 会报错 —— 那就把好好的连接误判成失败,陷入"明明能用却一直重连"的死循环。
同理还有一个"确保"型函数要先查的案例(决策二)。

## 5. EEPROM 里的凭据布局与掉电安全

### 布局(EEPROM 共 512 字节,地址 0~7 是锁密码)

| 地址 | 内容 | 说明 |
| --- | --- | --- |
| 8 ~ 40 | SSID | 33 字节**定长**,内容后面补 0 |
| 41 ~ 104 | 密码 | 64 字节定长,同上 |
| 105 | 标志 `0xA6` | 前面两个字段有效 |

**为什么定长不存"长度 + 内容":** 读的时候不用先算长度,字段位置是死的,少一层出错的地方。
代价是每次写要写满 98 字节(7 个 EEPROM 页)—— 配网是极低频操作,无所谓。

**为什么标志用 `0xA6` 而不是 `0xA5`:** `0xA5` 是锁密码的标志。两个模块共用一片 EEPROM,
读串了地址时标志不一样,至少能**当场发现**,不会把锁密码当成 WiFi 名。

### 掉电安全:标志**最后**落盘

这是全篇最值得带走的一个模式。

写 98 字节要横跨 7 个 EEPROM 页,每页之间器件都要忙 **tWR ≈ 10ms**。这 7 个窗口里
断电是完全可能的(配网刚成功,用户可能正拿手碰板子)。

**如果标志和数据在同一次写里落盘**,掉电后可能读出:

```
SSID   = "新热点"        ← 写进去了
密码   = "旧密码"        ← 还没轮到就断电了
标志   = 0xA6            ← 有效!
```

**标志有效、内容是错的** —— 设备拿着一个不存在的密码反复连网,怎么配都配不好。
这种状态**没有任何自愈路径**,因为固件认为自己的凭据是对的。

所以顺序必须是:

```c
AT24C04_page_write(WIFI_CFG_FLAG_ADDR, &zero, 1);          // ① 先清标志
AT24C04_crosspage_write(WIFI_CFG_ADDR, s_buf, 97);         // ② 写数据(7 页)
AT24C04_page_write(WIFI_CFG_FLAG_ADDR, &flag, 1);          // ③ 最后落标志
```

任何时候掉电,要么标志还是 0(上层当没存过,重新配网),要么数据已经完整写完。
**中间态读不出来。**

> **代价:** 多两次单字节写(2 × 10ms 忙等)。
> **更专业的做法:** 加一字节 CRC 校验整块 —— 这里数据量小、页面结构简单,标志法够了。
>
> 注意 `AT24C04_crosspage_write()` 是从 **地址 8** 开始写的(不含标志那个地址 105),
> 所以第 ① 步清掉的标志不会被第 ② 步覆盖回来。

### 为什么写 EEPROM 忙等 90ms 是可以接受的

一次完整的 save 要等 **9 个 tWR**(7 页数据 + 2 次标志写),约 **90ms** 的 `Delay_Ms()` 忙等。

- `wifi_task` 优先级是 **1(最低)**,忙等期间更高优先级的业务任务(key/lock/finger,prio 2~3)
  照常被 SysTick 抢占,**不会被饿死**;
- 而且它**只在配网成功那一刻发生一次**。

> ⚠ **但如果以后加了"按键手动触发配网"**,这个前提就变了 —— 那时得把 `Delay_Ms`
> 换成 `vTaskDelay`,或者干脆把写 EEPROM 挪到一个专门的低优先级任务里。
> 见 [api/AT24C04.c](../api/AT24C04.c) 文件末尾那段说明。

**I2C 并发:** 调度器起来之后,`wifi_task` 是**唯一**碰这片 EEPROM 的任务 ——
锁只在裸机阶段 `lock_init()` 里读写一次。所以不需要互斥量。

## 6. 三次踩坑记录(全是自己写出来的 bug)

### 坑一:一个标志名两义 → 无限进配网

`s_prov_done` 在 `wifi_wifi_join()` 里是"配网成功了",在 `wifi_task()` 里被当"配网试过了"用,
而且**只在成功时置位**。

而触发条件是 `(开机到 15 秒的剩余预算 == 0)`,这个条件**过点之后恒为真**。
于是"用户没掏手机"这条最常见的路径变成:

```
配网超时(180s) → 标志还是 0 → 条件依然成立 → 下个循环又进配网 → 每次卡 3 分钟 → ...
```

**设备永远停在"可被配网"状态** —— 正好是这套设计最想避免的事(旁边随便谁装个 BluFi App
就能把设备改到别的 WiFi 上去)。

**修:** 拆成两个概念,用一个 `s_prov_tried`(**进门就置位**)。

### 坑二:过了 15 秒,设备再也不联网了 —— 比不加配网还糟

加了预算机制之后:

```c
wifi_wifi_join(wifi_budget_left(boot, WIFI_PROV_DEADLINE_MS))    // ← 错
```

15 秒之后 `wifi_budget_left()` **恒为 0**,函数在"剩余预算太少"那里直接返回 ——
**连 `AT+WJAP` 都不发**。现象:15 秒没连上,这台设备到重启为止再也不会尝试联网。
路由器晚起 20 秒就中招。

**修:** 配网窗口只用来说明"要不要转配网",**不能拿它去框住之后的每一次重试**。
`s_prov_tried` 置位后换成满超时:

```c
s_prov_tried ? WIFI_T_WJAP_MS : wifi_join_budget(boot)
```

> **教训:给"一串操作设总时限"时,总时限要和"放弃并转别的路径"绑定,
> 不能顺手拿它当每次重试的超时。** 预算型参数一不小心就变成"永远为 0"。

### 坑三:"配网成功但代码没反应" —— 判据从一开始就错了

见决策四。复盘时值得记的是**这个 bug 为什么难查**:

- 日志上每个环节单看都"正常":事件到了、命令回了 OK、循环在跑;
- 错的是**判据本身** —— 我在注释里写的假设("模块会自己关掉配网窗口")从没被验证过;
- 现象(设备没反应)和原因(判据错)隔了好几层,不是看代码能看出来的。

**修完之后我在注释里明确写了这句话,防止以后又退回去:**

> ⚠ 这个状态**只能说明模块的配网任务开没开,说明不了配网成没成**。

## 7. 一条**没能站住**的结论:`AT+WAUTOCONN`

这一节记的是**一次失败**,留着比删掉有用。

**背景:** 一度认为"每次重启都要重新配网"的根因是模块的"开机自动重连"开关默认关着,
于是加了 `wifi_enable_autoconn()`,连接成功后发一条 `AT+WAUTOCONN=1`,让模块自己记住。

**实测结果,只证明了一半:**

| 验证 | 结果 |
| --- | --- |
| 值存住了吗 | ✅ 跨 `AT+RST` 软重启后 `AT+WAUTOCONN?` 仍报 1 |
| 它会自动重连吗 | ❌ 没有。`AT+RST` 之后 `AT+WJAP?` 连续 9 次报 `74`(STA 没在跑) |

**排除掉的解释:**

- "热点关了" —— `ipconfig` 确认热点 192.168.137.1 在
- "SSID 变了" —— PowerShell WinRT `GetCurrentAccessPointConfiguration()` 确认仍是 `DESKTOP-HTLNPUV 4128`

**剩下的两种可能,区分不了:**

1. `AT+RST` 是**软重启**,不走"开机自动连"那条路径(只有真断电才走);
2. 这条路本身就不通,手册说的"开机自动重连"不是这个意思。

**为什么区分不了:** 模块的电源不和 MCU 一起断,烧录时的 `reset` 只复位 STM32。
控不了模块电源,就做不了"真断电重启"的对照实验。

**怎么绕开的:** 不去猜模块的行为 —— **凭据由固件自己存、自己主动连**(决策三)。
`wifi_enable_autoconn()` 已删除。

> **教训:凡是"模块侧状态"的判断,都不能假设它和 MCU 的生命周期对齐。**
> 由此引出的推论:能自己掌握的状态就别托付给模块。托付出去的东西,
> 你既验证不了它,也没法在出问题时把责任摘清楚。

## 8. 已知的薄弱点

### ① SSID 或密码里带逗号会切错字段

`AT+WJAP?` 的应答靠逗号分字段,`AT+WJAP=` 的参数也靠逗号分隔 —— 凭据里出现逗号,
切出来的东西就是错的。家用场景基本不会遇到,但**协议就是这样,不能假装不存在**。

**真要防:** 在 `wifi_cfg_save()` 里加一层"不含逗号"的校验挡住,让用户换个名字。

### ② MQTT 凭据明文躺在源码里

`WIFI_MQTT_HOST/USER/PASS/CLIENT_ID` 全是 `#define`。任何人拿到这份固件
(或者干脆拿到板子读出 flash)就能连上 broker,往 topic 里写开锁指令。

配合 [开锁业务的架构.md](开锁业务的架构.md) §8 ① —— **云端开锁没有任何身份校验** ——
这两个加在一起就是"拿到 broker 写权限 = 能开这把锁"。

**真要上产品:** MQTT 凭据也应该进 EEPROM(和 WiFi 凭据同一套路),
载荷带 HMAC 签名(密钥存 EEPROM),带时间戳防重放。

### ③ 配网那 3 分钟里 `wifi_task` 完全堵着

`wifi_ble_provision()` 是**阻塞**的(轮询 `AT+WCONFIG?` 最多 180 秒)。
这段时间 MQTT 心跳停了、下发也收不到。

现在能接受,因为配网只发生在开机阶段,锁还没开始用。但如果以后加"按键手动触发配网",
就必须改成非阻塞的 —— 和 [开锁业务的架构.md](开锁业务的架构.md) §4 决策四
(开锁从阻塞函数改成状态机)**是同一个道理**:

> **一个阻塞 180 秒的函数,等于这 180 秒里这个任务聋了。**

### ④ 收行缓冲 128 字节,`AT+WJAP?` 已经贴到边

`wifi_at_ex()` 里的 `line[128]`,超长会**静默截断**。

算一下最坏情况:`+WJAP:` (6) + `3,` (2) + SSID(32) + `,` (1) + 密码(63) = **104 字节**。
够,但**只剩 24 字节余量**。

> 云端下发的 `+EVENT:MQTT_SUB,...` 那条路有防护 —— `wifi_handle_sub_event()` 会拿平台声明的
> `len` 和实际收到的长度对账,对不上就整条丢弃(因为**被截断的 JSON 有可能还能解析出一个错的值,
> 那比直接失败更危险**)。但 `AT+WJAP?` 这条路**没有对账**,只是碰巧够用。

### ⑤ 配网时直接写 LCD,踩了 lock 的线

`wifi_ble_provision()` 里直接调 `lock_lcd_set_title()`。现在安全,因为配网只在开机阶段发生,
那时锁一定空闲(`s_unlocking == 0`)。

**但和 ③ 是同一个前提。** 一旦加了"手动触发配网",两个任务同时写软件 SPI 的 LCD,
画出来就是花屏。那时必须改成往 `lock_task` 投一条"显示这段文字"的命令,由它统一出图。

### ⑥ 心跳只是心跳

`{"hb":n}` 只证明链路活着,**不含锁的真实状态**(开/关、电量、最近一次开锁是谁触发的)。
云端没法对账 —— 发了开锁命令之后,平台不知道到底开没开成。

见 [开锁业务的架构.md](开锁业务的架构.md) §8 ④。

## 9. 一句话总结

| 设计点 | 做法 | 为什么 |
| --- | --- | --- |
| 收数据 | ISR + 256 字节环形缓冲 | 模块会主动上报,时机不可预测,轮询必然丢事件 |
| 满了怎么办 | 丢**新**字节 + 计数器 | 覆盖会把一行应答从中间截断,比丢整行更难查 |
| "OK" | 只当"命令收到",不当"办成了" | 两段式应答,不等事件就往下走,连云端必翻车 |
| 报错判断 | `strstr(line, "ERROR")` | 模块回的是 `+ERROR`,带加号,精确比会漏判 |
| `ensure_xxx` 型函数 | 第一句先查状态 | 很多 AT 命令在"已就绪"时重发会起反作用 |
| 凭据存哪 | AT24C04 EEPROM | 源码要重烧,模块 flash 看不见也验证不了 |
| 配网后凭据从哪来 | `AT+WJAP?` 明文带密码 | 用户只发给了模块,固件得自己抄回来 |
| 配网成功判据 | `AT+WJAP:3`,不是 `AT+WCONFIG?` | 前者是"联网结果",后者只是"模块的任务开没开" |
| 预算/超时 | 15s 窗口只用来决定"转不转配网" | 拿它当每次重试的超时 → 恒为 0 → 永远不再联网 |
| 防重复配网 | `s_prov_tried`,"试过"就算 | 触发条件过点后恒为真,用"成功才置位"的标志会死循环 |
| EEPROM 掉电安全 | 先清标志 → 写数据 → 最后落标志 | 标志有效但内容是错的,这种状态**没有自愈路径** |
| 模块状态 | 不假设它和 MCU 生命周期对齐 | 模块电源独立、`reset` 只复位 STM32;能自己掌握的就别托付出去 |

**这套代码的第一版核心是「怎么把 WiFi 连上」。**
**被实机打脸几次之后,核心变成了「怎么把一个不可见、不可控、状态还跨 MCU 复位存活的模块,
用一个可以验证的方式管起来」。**

> 判断一个状态该不该托付给外部模块,只要问一句:
> **"出问题的时候,我能不能自己验证它到底是对的还是错的?"**
> 答不上来,就自己存一份。
