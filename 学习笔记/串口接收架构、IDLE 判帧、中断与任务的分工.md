# 串口接收架构、IDLE 判帧、中断与任务的分工(usart1 的设计理念)

> 一句话定位:**中断只做"搬"和"喊",耗时活全部推给任务;帧边界借用硬件的 IDLE 标志,不在协议里自造结束符。**

---

## 1. 先把这条链上的角色分清

| 角色 | 是谁 | 职责 | 绝对不能干的事 |
|---|---|---|---|
| 硬件 | USART1 外设 | 收满一字节置 RXNE;总线空闲满一字节时间置 IDLE | —— |
| 中断层 | `api/usart1.c` 的 `USART1_IRQHandler` | **搬**(DR → 缓冲)、**喊**(Give 信号量) | 阻塞、打印、等锁、跑循环 |
| 交接区 | `api/usart1.c` 的 `rx_frame` | 存一帧的完整副本,给任务用 | 被两边同时写 |
| 任务层 | `api/usart1.c` 的 `usart_rx_task` | 等信号量、回显 | 直接碰 USART1 的 DR |

一条数据从串口助手走到你屏幕上的顺序:

```
串口助手发 "hello",发完停顿一下
  │
  ▼ ① 硬件
PA10(RX) ─▶ 移位寄存器 ─▶ 每收满 1 字节,置 RXNE 触发一次中断   ("hello" = 5 次)
  │
  ▼ ② 中断上下文 ── USART1_IRQHandler ──
RXNE? ─是─▶ 读 DR 取走字节 ─▶ str_buf[i++]
  │        (有边界检查,超长帧丢弃也不会写穿)
  ▼
IDLE? ─是─▶ str_buf[i]='\0'
            整帧拷进 rx_frame        ← 交接区
            i = 0
            xSemaphoreGiveFromISR(...)   ← "喊"
              └─▶ portYIELD_FROM_ISR(...)  挂 PendSV
  │
  ▼ ③ 中断退出 ─▶ PendSV ─▶ 上下文切换到 usart_rx_task
任务上下文 ── usart_rx_task ──
  │  平时睡在 xSemaphoreTake(usart_rx_sem, portMAX_DELAY),不占 CPU
  ▼  信号量到手
print_line(rx_frame)
  ├─ xSemaphoreTake(print_mutex)    ← 串口是全局资源,和别的任务共用一把锁
  ├─ printf ─▶ fputc ─▶ 逐字符写 USART1->DR
  └─ xSemaphoreGive(print_mutex)
  │
  ▼ ④ PA9(TX) ─▶ 串口助手显示 hello
```

**这张图就是整个设计的全部**。后面每一节都是在解释"为什么这么切"。

## 2. 为什么非要把活推给任务:ISR 越短越好

### 2.1 原理:中断上下文有三个先天限制

1. **不能阻塞**。中断不是任务,没有 TCB。`vTaskDelay`、`xQueueReceive(..., portMAX_DELAY)` 在中断里"挂起谁"?挂不起来。
2. **不能等**。ISR 执行期间,同级和更低优先级的中断全被硬件挡在门外。你在里面等 1ms,整个系统就少 1ms 的响应能力。
3. **不能调普通版 API**。所有会阻塞的 API 都有 `...FromISR` 分身,就是这个原因。

### 2.2 算一笔账

回显 99 字节,115200 8N1(每字节 10 位):

```
99 字节 × 10 位 ÷ 115200 ≈ 8.6ms
```

如果这 8.6ms 在 ISR 里干完(格式化 + 逐字符写 DR),那么这 8.6ms 内**其它所有中断都得排队**。放到任务里干,ISR 只花几微秒,剩下的 8.6ms 里别的中断照常响应。

**利**:系统对其它事件的响应延迟从"毫秒级"降到"微秒级";处理逻辑还能打断点、能单步、能用 `vTaskDelay` 模拟慢处理来测并发。
**弊**:代价是三份开销 —— 一个任务(TCB + 1KB 栈)、一个信号量(约 100 字节堆)、每次唤醒多一次上下文切换(几十个周期)。**只偶尔收几个字节的场合,这份开销不值,轮询反而更省。**

### 2.3 对比:另外两种常见写法差在哪

| 写法 | 中断做什么 | 致命问题 |
|---|---|---|
| 中断里直接处理(在 ISR 里 printf) | 全干 | 中断超长,其它中断被堵;而且不能调任何 FreeRTOS API(除非优先级 ≥ 11) |
| 中断置标志,任务里 `while(!flag);` 轮询 | 只置标志 | 任务 100% 烧 CPU 死等,比自己优先级低的任务全饿死,还费电 |
| **本方案:中断 Give,任务 Take** | 搬 + 喊 | 占一点内存换个任务,见上面"弊" |

轮询那个写法的隐蔽坑:任务里写 `while(!RXNE);` 等下一个字节时,**一旦被高优先级任务抢占超过一个字节的时间,新字节就覆盖了 DR,旧的那个静默消失**。中断版没有这个问题——字节到达的那一刻就被取走了。

## 3. 帧边界:为什么用 IDLE,而不是 `'\n'` 或定时器

### 3.1 IDLE 的硬件语义

IDLE 标志由硬件置位,条件是:**RX 线上连续空闲满一个字节的传输时间**。注意是"一个字节时间",不是"一段时间"——波特率一变,这个门槛也跟着变。

它回答的问题是"对方是不是发完了",而不是"发的是什么"。**这正是判帧需要的信息**。

### 3.2 三种判帧法对比

| 判帧法 | 怎么判 | 利 | 弊 |
|---|---|---|---|
| 协议结束符(`'\n'`) | 收到 `'\n'` 算一帧结束 | 跨平台、直观 | **数据里不能出现 `'\n'`**;要上位机配合改协议 |
| 软件定时器超时 | 每收一字节重置定时器,超时算帧尾 | 不改协议 | 要额外占一个定时器 + 一个中断,还得算超时阈值 |
| **IDLE 中断** | 硬件在总线空闲满 1 字节时间时置位 | 不占额外资源、不改协议、不用自己算时间 | 只能判"空了多久",判不了内容 |

**利**:几乎零成本——硬件本来就有这个标志,打开中断即可。
**弊**:帧边界完全交给了"对方的发送节奏"。

### 3.3 IDLE 判帧的两个固有坑(不是代码 bug)

- **粘包**:上位机把两帧连着发,中间不足一个字节时间的空闲 → 被当成**一帧**。
- **拆包**:上位机逐字节发、每个字节之间都停顿 → 被拆成**好几帧**。

**现象**:同一份数据,换个上位机、换个发送方式,回显结果就不一样,而且代码一行没改。
**怎么应对**:要么在上位机侧约束"一帧发完必须停顿";要么在帧内容里自带长度字段或校验,让任务层能二次切分。
**为什么不能靠改中断解决**:IDLE 的判据是电平空闲时间,这个是物理层的,软件改不了。

## 4. 交接区 `rx_frame`:它挡的是什么,挡不住什么

### 4.1 它挡的是什么

假设没有 `rx_frame`,ISR 直接写 `str_buf`,任务直接读 `str_buf`:

- 任务正在逐字符打印第 N 帧
- 中断收到第 N+1 帧,从 `str_buf[0]` 开始覆盖
- **现象**:回显打到一半突然变成新内容;或者前后两帧粘在一起。而且随发送速度时有时无,难复现。

加了 `rx_frame` 之后,ISR 在 IDLE 分支里**先把整帧拷走再 Give**,任务读的是那份拷贝,不再和 ISR 抢同一个数组。

### 4.2 它挡不住的是什么

`rx_frame` 也只有一份。如果任务还没开始读,第二帧就到了,`rx_frame` 照样被覆盖。

**这是单缓冲的固有极限,不是 bug。** 要根治只有三条路:

| 方案 | 内存代价 | 实现代价 |
|---|---|---|
| 双缓冲(两份 `rx_frame` 轮换) | ×2 | 要加"当前在用哪份"的指示变量 |
| 环形缓冲 | 取决于缓冲深度 | 要维护读指针/写指针 |
| 队列(`xQueueSendFromISR` 把整帧搬过去) | 每份都占一份副本 | 最省心,内核帮你管;代价是必须先定好"队列深度 × 帧长" |

**选型的分界线**:丢一帧无所谓(比如回显调试)→ 单缓冲够用;一帧都不能丢(比如接收控制指令)→ 必须上队列。

### 4.3 顺带:`usart_flag` 是历史残留

`api/usart1.c` 里的 `usart_flag` 现在全工程**没有任何地方读它**——通知任务的活已经交给 `usart_rx_sem` 了。留着只是方便调试器里观察。这类"置了没人读"的变量是改造遗留的信号,看到就该顺手确认一遍。

## 5. 中断优先级 15:不是随便挑的

### 5.1 规则

`freertos/FreeRTOSConfig.h` 里:

```c
#define configMAX_SYSCALL_INTERRUPT_PRIORITY  ( 0xB0 )
```

`0xB0` 的高 4 位 = **11**。规则:

> **抢占优先级数值 ≥ 11 的中断,才可以调 `...FromISR` API。数值 0~10 的中断,一个 FreeRTOS API 都不许碰。**

方向之所以反直觉,是因为 Cortex-M **数值越小越紧急**,而 `0xB0` 定义的是"内核能屏蔽的最高紧急度"。

### 5.2 为什么是物理上做不到,而不是"不建议"

内核的临界区靠 `BASEPRI` 实现。数值 0~10 的中断,内核**关不掉**:

- `taskENTER_CRITICAL()` 挡不住它
- 调度器拦不住它
- 如果它正在改内核链表,而内核自己也正改到一半 → **链表被撕坏**

所以不是风格问题,是没法互斥。

### 5.3 现象 / 怎么改 / 为什么

**现象**:把 `api/usart1.c` 里 `USART1_IRQn` 的抢占优先级改回 3,一旦中断里调 `xSemaphoreGiveFromISR`,会当场撞在 `freertos/port/port.c` 的 `vPortValidateInterruptPriority` 里那句

```c
configASSERT( ucCurrentPriority >= ucMaxSysCallPriority );
```

而 `configASSERT` 在 `freertos/FreeRTOSConfig.h` 里被定义成 `taskDISABLE_INTERRUPTS(); for(;;);` —— **关中断 + 死循环**。串口再无任何输出,LED 也不动,在线调试点暂停能看到 PC 卡在这句上。不是偶发,是每次都卡。

**怎么改**:把 `NVIC_InitTypeDef` 的 `NVIC_IRQChannelPreemptionPriority` 字段改成 ≥ 11(常用 15)。

**为什么**:改成 ≥ 11 后它落进"内核能屏蔽"的区间,内核临界区能把它挡在门外,内核数据结构的完整性才有保障。

**代价**:它现在会被临界区挡住,**响应延迟变大**。所以真正要求极低延迟、且绝不碰 FreeRTOS API 的中断(比如电机紧急刹车),反而要**故意留在 0~10**。这是"实时性"和"内核安全"之间的一次明确取舍。

## 6. 初始化顺序:对象先建,调度器后启

### 6.1 顺序

`user/main.c` 的 `main()` 里:

1. 外设初始化 —— 注意 `usart1_Config()` **在这一步就把 USART1 中断使能了**
2. 建 RTOS 对象 —— `debug_init()`(打印锁)、`usart1_tasks_init()`(接收信号量 + 任务)
3. `vTaskStartScheduler()`

**为什么必须先建再启**:所有 RTOS 对象都从 heap_4 分配。调度器一跑起来,任务可能立刻就要用,来不及现场建;而且多任务并发下建对象本身也要考虑安全。

### 6.2 一个几百毫秒宽的隐蔽窗口

`usart1_Config()` 使能中断 → `usart1_tasks_init()` 建信号量,中间隔着 `LCD_Init()` 等初始化,**几百毫秒**。这期间只要上位机发来一个字节,ISR 就会走到 Give 分支——而此时 `usart_rx_sem` 还是 `NULL`。

**现象**:`xSemaphoreGiveFromISR(NULL, ...)` 撞 `freertos/src/queue.c` 里的

```c
configASSERT( ( pxQueue != NULL ) && ( pxQueue->uxItemSize == 0 ) );
```

同样是关中断死循环。表现和 5.3 一模一样,但原因完全不同——**这是最难查的一类问题:偶发,而且和"你上电后多久开始发数据"有关**。

**怎么改**:在 ISR 里加 `if(usart_rx_sem != NULL)` 守卫。

**为什么这么改**:守卫的成本是一行判断,换来的是"初始化顺序不再是隐藏前提"。中断可以在任何时刻进来,不依赖"调用者必须按某个顺序初始化"这种口头约定。

**更彻底的做法**:把 `USART_ITConfig(...)` 那两行从 `usart1_Config()` 挪到 `usart1_tasks_init()` 的末尾,让"中断使能"和"处理者就绪"在时序上不可能颠倒。**代价**是外设初始化和 RTOS 初始化从此耦合在一起,再想单独用裸机方式跑串口就得多改一处。

### 6.3 一个更通用的教训

`freertos/FreeRTOSConfig.h` 里有句话值得记住:凡是链接报 `Undefined symbol`,而头文件里明明有声明,先怀疑是不是没开对应的 `INCLUDE_xxx` 开关。FreeRTOS 为了省 flash/RAM 做了大量裁剪,**编译器抓不到,只有链接器能抓到**。

## 7. 串口是全局共享资源:打印必须走统一入口

### 7.1 为什么

`api/usart1.c` 的回显走的是 `api/debug.c` 的 `print_line`,不是直接 `printf`。原因是 `printf` 最终经 `fputc` 逐字符写 `USART1->DR`,而串口同时被 `print_task1`、`print_task2`、`usart_rx_task`、空闲钩子用着。被抢断会造成两种破坏:

- **穿插**:两行字符互相切碎
- **丢字符(更隐蔽)**:任务 A 查完 TXE 被抢走,任务 B 写完 DR,A 回来又写一次 → **B 那个字节被覆盖丢失**(DR 一次只存一个待发字节)

### 7.2 锁的粒度必须等于"一整行"

**加在 `fputc` 里挡不住**——那样每个字符都是一段合法临界区,B 照样能插进 A 的行中间。锁必须包住**整个 printf 调用**。

### 7.3 为什么用互斥量而不是二值信号量

| | 二值信号量 | 互斥量 |
|---|---|---|
| 谁能 Give | 谁都可以 | **只有持有者** |
| 优先级继承 | 无 | **有** |

拿二值信号量当锁,会重现**优先级反转**:持锁的是低优先级任务,它被一个中等优先级的任务抢占了,等锁的高优先级任务就被间接饿死——二值信号量不会把持锁者临时提权,它压根不知道锁在谁手里。

**代价**:互斥量更重(要存持有者、多一套继承逻辑),而且**绝对不能进中断**——中断不是任务,没优先级可以继承,也没法"持有"。`freertos/src/queue.c` 里有专门的断言拦这个。这就是为什么 ISR 里只做"搬"和"喊",打印必须推给任务。

### 7.4 反面:Hook 里不能加锁

`user/main.c` 里的 `vApplicationStackOverflowHook`、`vApplicationMallocFailedHook` 内部的打印**不加锁**,是故意的:触发时系统已经不可信,如果某个任务正握着锁,Hook 再去 Take 就是**自己等自己**,永远出不来。

## 8. 这套设计的边界:什么时候不该这么写

| 场景 | 该不该用这套 | 更合适的选择 |
|---|---|---|
| 偶尔收几个字节,频率极低 | ❌ | 主循环里轮询,省一个任务和 1KB 栈 |
| 收一行指令、回显调试信息 | ✅ | 本方案 |
| 高速连续数据流(几十 KB/s) | ⚠️ 每字节一次中断太费 | **DMA + IDLE** |
| 一帧都不能丢 | ❌ 二值信号量会静默丢帧 | 队列 / 计数信号量 + 双缓冲 |
| 要求微秒级响应的紧急信号 | ❌ | 中断里直接执行(但就不能调 FreeRTOS API) |

判断的核心问题只有一个:**这是"通知型"需求,还是"搬运型"需求?**

- 通知型:只关心"有事发生",偶尔漏一次能接受 → 信号量
- 搬运型:每一份数据都要完整送达 → 队列

二值信号量只表达"有没有",不表达"有几次";它不锁存,连发两帧时第二帧的 Give 会返回 `pdFAIL` 被丢掉。**这是"通知型"的固有取舍,不是 bug。**

## 9. 演进方向:DMA + IDLE

现在的方案里,每个字节都要打断一次 CPU。改成 DMA 后:

- DMA 通道挂在 USART1 的 RX 上,字节由硬件直接搬进缓冲区,**CPU 完全不参与**
- IDLE 中断照旧判帧边界(这个思路不变)
- 中断次数从"每字节一次"降到"每帧一次"

**利**:CPU 占用趋近于零;高波特率下也不会因为"来不及取 DR"而丢字节。
**弊**:要理清 DMA 的 `NDTR`(剩余传输计数)和缓冲区地址的换算关系——中断触发时,`缓冲区长度 - NDTR` 才是这一帧接收到的字节数;还要处理 DMA 的循环模式与重新装载。调试难度比现在这套高一档。

**判断时机**:现在的方案在 115200 波特率、人类打字速度下完全够用。**等到发现 CPU 占用异常、或者波特率上到 460800 以上再考虑。**

1. **两个原因**。① `printf` 是逐字符写 DR,99 字节 @115200 要 8.6ms,这段时间中断回不去,其它同级/低级中断全被堵住;② 任何可能阻塞的调用在中断上下文里都没有意义,而 `print_line` 内部要 Take 互斥量——**互斥量在中断里 Take/Give 都是被内核断言禁止的**。
2. 前提是**对方发完必须停顿满一个字节的传输时间**。连着发、中间不足一个字节空闲 → 两帧被当成**一帧**收到,帧内容变成两帧的拼接。反过来,逐字节发且每字节都停顿 → 被拆成好几帧。
3. 解决的是"任务正在读 `str_buf` 时,ISR 把下一帧盖上去"——现在 ISR 先把整帧拷进 `rx_frame` 再唤醒任务。没解决的是"任务还没开始读,第二帧就到了"——`rx_frame` 也只有一份,照样被覆盖。根治要双缓冲/环形缓冲/队列。
4. **串口再无任何输出,系统静默卡死**。因为中断里调了 `xSemaphoreGiveFromISR`,而优先级 3 低于门槛 11,会撞在 `vPortValidateInterruptPriority` 的 `configASSERT( ucCurrentPriority >= ucMaxSysCallPriority )` 上;这个 `configASSERT` 被定义成"关中断 + 死循环"。不是偶发,是每次都卡。
5. 风险是**信号量还没建好,中断就来了**:`xSemaphoreGiveFromISR(NULL, ...)` 会撞 `queue.c` 里的 `configASSERT( ( pxQueue != NULL ) && ... )`,同样死循环。中间隔着 `LCD_Init()` 等初始化的几百毫秒,窗口很宽。代码里用 `if(usart_rx_sem != NULL)` 守卫挡住了。
6. 因为 `fputc` 粒度太小。加在 `fputc` 里,每个字符都是一段合法的临界区,高优先级任务照样能在两个字符之间插进来——**混行照旧发生**。锁的原子单位必须和"你想保护的东西"对齐,这里就是"一整行"。
7. 因为打印是**抢占共享资源**,不是传递通知。互斥量有所有权(只有持有者能 Give)和优先级继承(防优先级反转);二值信号量两条都没有,任何任务都能"替别人开锁",而且持锁者被中等优先级任务抢占时,等锁的高优先级任务会被间接饿死。
8. **至少两处**:① 把二值信号量换成**队列**(`xQueueSendFromISR` 把整帧数据本身搬给任务),因为二值信号量不锁存、连发两帧必丢一帧;② 把 `rx_frame` 单缓冲换成**双缓冲或环形缓冲**,否则任务还没取走时新帧会覆盖旧帧。另外帧长度上限 99 字节也要重新考虑——队列要先定好"深度 × 帧长",这个内存账得算清楚。
