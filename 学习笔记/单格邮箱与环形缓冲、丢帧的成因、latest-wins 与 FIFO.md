# 单格邮箱与环形缓冲、丢帧的成因、latest-wins 与 FIFO

> 一句话定位:**这两个方案保证的是不同的事 —— 邮箱保证"你看到的是最新的",环形缓冲保证"一条都不漏"。选哪个,取决于你更怕丢数据,还是更怕看到过时数据。**

---

## 1. 两种结构

### 1.1 单格邮箱(本工程 `api/usart1.c` 现在的做法)

四个角色,分工要分清:

| 名字 | 角色 | 谁碰它 |
|---|---|---|
| `str_buf` | ISR 私有的接收暂存,一帧一清 | 只有 `USART1_IRQHandler` |
| `i` | 已收字节数 —— 一个**长度计数器** | 只有 `USART1_IRQHandler` |
| `rx_str_buf` | **交接区,只有一格** | ISR 写,`usart_rx_task` 读 |
| `usart_rx_sem` | 门铃 —— 二值信号量 | ISR Give,`usart_rx_task` Take |

一次收帧的全过程:

```
字节到达 ──▶ RXNE 中断 ──▶ 读 DR 存进 str_buf[i++]
一帧收完 ──▶ IDLE 中断 ──▶ str_buf[i]='\0'
                          ──▶ 整帧拷进 rx_str_buf
                          ──▶ i = 0
                          ──▶ xSemaphoreGiveFromISR(usart_rx_sem)
任务被唤醒 ──▶ Take 到 ──▶ print_line(rx_str_buf)
```

**"邮箱"(mailbox)是这套结构的正式名字:容量为 1 的消息队列。**

- µC/OS 有专门的 `OSMboxPost` / `OSMboxPend`。
- FreeRTOS **没有** mailbox 这个 API 名,它把邮箱当作 `xQueueCreate(1, size)` 的特例。

所以"名词是通用的,API 名不是"。

### 1.2 环形缓冲

结构长这样(概念示意,`api/usart1.c` 里那段进阶注释有完整写法):

```
uint8_t  rx_ring[N][100];   // 每一格住一整帧
uint16_t rx_w;              // 写指针 —— 只被 ISR 改
uint16_t rx_r;              // 读指针 —— 只被任务改
```

写的时候不看"第几帧",只看"写指针现在指哪":

```
拷一帧到 rx_ring[rx_w]
rx_w 前进一格:if (++rx_w >= N) rx_w = 0;    ← 到末尾就绕回开头
```

读的时候:

```
while (rx_r != rx_w) {           ← 抽干,不是 if
    打印 rx_ring[rx_r]
    rx_r 前进一格并回绕
}
```

### 1.3 两者的对照

| | 单格邮箱 | 环形缓冲 |
|---|---|---|
| 容量 | 1 帧 | N-1 帧(牺牲一格,见 §3.2) |
| 写满时 | 拒绝写入 | 绕回开头覆盖,或按策略拒绝 |
| 需要几个游标 | 一个长度计数器 `i` | **两个**:读指针 + 写指针 |
| 数据的新旧 | 只有最新的 | 从旧到新排队 |
| 需要加锁吗 | 不需要 | **也不需要**(见 §3.3) |

## 2. 判据:凭什么说单格邮箱"不是"环形缓冲

三条判据,单格邮箱一条都不占:

| 环形缓冲的特征 | 单格邮箱 |
|---|---|
| 写满后**绕回开头**(`w = (w+1) % N`) | 写满后**拒绝写入**(`USART1_IRQHandler` 里那个 `else` 只把 DR 读走) |
| **两个游标**:读指针 + 写指针 | 一个长度计数器 `i` |
| 缓冲里同时住着**多帧**,新的接在旧的后面排队 | 只有**一份**,新的直接盖旧的 |

### 2.1 最容易误会的一处:复位 ≠ 回绕

`USART1_IRQHandler` 里那句 `i = 0` 长得很像"绕回开头",性质完全相反:

- **`i = 0`(复位)**:把缓冲当成"**从头再来**",里面剩下的东西**丢掉**
- **`w = (w+1) % N`(回绕)**:缓冲里的旧数据**原样留着**,新数据接在后面**排队**

> **复位是"清空重来",回绕是"排队接上"。**

这一句是理解两种方案的分水岭。**写指针一旦写成了"复位",排队排到一半的帧就全丢了,环形缓冲立刻退化回单格邮箱。**

## 3. 原理:为什么这样设计

### 3.1 丢帧的成因:瓶颈在"仓库",不在"门铃"

一个常见误解是"丢帧是二值信号量深度只有 1 造成的,换成计数信号量就好"。**不对。**

- 二值信号量只是**门铃**,它被合并了不会丢数据 —— 因为数据根本不在它手里。
- 真正丢数据的是 `rx_str_buf` **只有一格**:任务还没打印完,新帧就盖上来了。

推论:**换成计数信号量治不好这个病**。就算信号量老老实实记着"来了 3 帧",任务醒来读到的也只是最后一帧的内容,前两帧早被覆盖。

**要一帧不丢,必须让"数据"也排队 —— 也就是队列,或者环形缓冲。**

### 3.2 判空与判满:为什么必须牺牲一格

```
空:  r == w
满:  (w + 1) % N == r        ← 注意是"下一格等于读指针"
```

**满为什么不能也写成 `r == w`?** 那样"空"和"满"长得一模一样,分不出来。

两种解法:

- **(a) 牺牲一个槽位** —— 最省事,代价是 `N` 格实际只能存 `N-1` 帧
- **(b) 另加一个 `count` 变量** —— 但它**两边都要写**,又回到需要临界区的老路

所以环形缓冲通常选 (a)。这也解释了为什么"开 4 格只能存 3 帧"。

### 3.3 环形缓冲凭什么不用加锁(单生产者-单消费者)

核心洞察:**读指针只有任务写,写指针只有 ISR 写** —— 一人管一个,谁都不用"读-改-写"对方那个变量。于是整个结构**不需要临界区**。

这就是 **SPSC(单生产者-单消费者)** 模型,是 ISR↔任务之间最划算的结构。

前提是两条:

1. 两个指针都必须是 `volatile` —— 它们跨了两个上下文,编译器不许缓存到寄存器里。
2. 指针宽度要选**对齐读写是单条指令**的类型(如 16 位),保证不会读到"改了一半的指针"。

### 3.4 顺序:先写数据,再动指针

入队时必须:

```
先拷数据到 rx_ring[rx_w]
再 rx_w = next
```

**反过来的话**,任务可能立刻看到"有新帧了",但数据还在搬的途中 —— 它读到的就是半截帧。

### 3.5 任务侧为什么是 while 不是 if

任务醒来后要**把仓库抽干**,而不是只取一帧:

```
xSemaphoreTake(usart_rx_sem, portMAX_DELAY);
while (rx_r != rx_w) { ... }        ← while,不是 if
```

这一个字的差别,把"信号的丢"和"数据的丢"**彻底拆开了**:

- 信号量被合并(门铃没响第二声)→ 任务醒来一看 `rx_r != rx_w`,发现仓库里还有货,接着搬 → **通知丢了,不影响数据**
- 任务正在打印时新帧到达 → 插进环形缓冲排着队,等下一轮被搬

**数据安不安全,只取决于"仓库满没满",和"门铃响了几次"完全无关。**

> **信号量当门铃,环形缓冲当仓库。门铃可以听漏,仓库不会丢货。**

### 3.6 满的时候必须记数

满了无论是"丢新帧、保旧帧"还是反过来"覆盖最老的",**都必须选一个,并且记一笔**(比如 `rx_overrun++`)。

**关键不是选哪个,而是不能静默丢。** 静默丢数据是最难查的一类 bug —— 现象是"偶尔少一帧",没有任何线索。加一个计数器,它就变成了可观测的。

## 4. 利弊对照

### 4.1 环形缓冲买到了什么

1. **不丢帧(容量之内)**。能吸收 N-1 帧的突发,而邮箱只能吸收 0 帧。
2. **丢失从静默变成可观测**。有 `rx_overrun` 计数,丢了你知道。
3. **能扛突发**。上位机连续快发时不会立刻丢。

### 4.2 环形缓冲付出了什么

1. **RAM 线性增长**。N 格 × 每帧字节数。本工程每帧上限 100 字节(RX_Q 开 4 格就是 400 字节)。本工程可用 RAM 96KB(见 `project.uvprojx` 的 IRAM 配置),不算什么;但**如果改用 FreeRTOS 队列实现,这 400 字节要从 8KB 的堆里出**(见 `freertos/FreeRTOSConfig.h` 的 `configTOTAL_HEAP_SIZE`),那就占掉 5% 了。
2. **代码复杂度和踩坑面翻倍**。多出这一堆决策:回绕、判满、区分空和满、"先写数据再动指针"的顺序、"满了丢哪个"的策略、overrun 计数。**每一个都是一个 bug 温床**,而且症状更隐蔽 —— 出问题时要同时盯两个指针才能推出来。
3. **多一层间接**。调试时"任务现在读到第几帧了?`w` 和 `r` 差多少?"不再是看一眼就知道的事。

### 4.3 一条不成立的"优势"

网上常说"环形缓冲在 ISR 里更慢"。**在本工程这套结构上不成立。**

两个方案在 ISR 里**都要把整帧拷贝一遍**(邮箱拷进 `rx_str_buf`,环形拷进 `rx_ring[rx_w]`),拷贝量完全相同。环形缓冲多出来的只是几条算指针的指令,微秒级噪声。

真要说 ISR 更短,得是**另一种设计** —— 环形缓冲只存"帧的描述符",字节流由 DMA 直接搬。那才另当别论。

### 4.4 单格邮箱独有的、环形缓冲给不了的东西

**语义不同 —— 这是最本质的一条,不是取舍,是两种不同的保证。**

- **单格邮箱** = 最新覆盖最旧 → **latest-wins**,你看到的就是此刻的真实状态
- **环形缓冲** = 先来先服务 → **FIFO**,一条都不漏,但可能全是过时的

举一个一定会遇到的场景:上位机每秒发一帧状态(温度、位置、计数)。某次任务被别的高优先级活拖住了 500ms,期间来了 3 帧。

- **环形缓冲**:任务醒来把积压的 3 帧挨个打印 → 你看到**三行早已过时的数据**,而且是瞬间刷出来的,时间戳全乱
- **单格邮箱**:中间两帧直接扔了 → 你看到**当前这一帧**

**对回显、监控、实时状态显示这类场景,看到过时数据往往比丢掉它更糟。** 这是环形缓冲换不来的东西 —— 它俩优化的是相反的目标。

## 5. 怎么选

两条判据:

1. **丢了会怎样?** —— 只是"少看一帧" → 邮箱;"数据就错了" → 环形
2. **你要的是"最新"还是"全部"?** —— 最新 → 邮箱;全部 → 环形

| 场景 | 该用 |
|---|---|
| 串口回显、状态监控、实时曲线 | **单格邮箱** |
| 命令解析、协议帧、固件升级数据块 | **环形缓冲 / 队列** |

### 5.1 本工程为什么现在用邮箱是对的

按判据 1:串口助手后面坐着**人**,打字间隔是几百毫秒到几秒。这套方案开始丢帧的门槛是"**帧间隔 < 任务处理一帧的时间**",在回显场景下是 8.6ms 量级(回显 99 字节 @115200 8N1:每字节 87µs,共约 8.6ms)。人的手速离这个阈值差了三个数量级。

**换句话说:这个缺陷是真实存在的,但它在使用场景之外。** 方案本身没写错,是取舍 —— 用"高频连发会丢"这一条,换来了:

- 任务平时 0% CPU(睡在 `xSemaphoreTake` 上)
- 中断只有几微秒(读 DR + 存 + Give)
- 代码十几行,没有缓冲区管理

### 5.2 什么时候必须换

判据:**帧间隔会不会小于你处理一帧的时间**。会,就得换。典型触发场景:

- 上位机自动连续发(固件升级传数据块、Modbus 轮询)
- 帧里装的是命令或数据,丢了有后果
- 波特率往上提(921600 时一帧时间缩短 8 倍,窗口随之收紧)

**注意:换的时候换的不是"更好的实现",是换了一个语义** —— 从 latest-wins 换成 FIFO。

### 5.3 一个更省事的替代:直接用 FreeRTOS 队列

`xQueueCreate(N, 100)` + `xQueueSendFromISR` + `xQueueReceive`。

`queue.c` **内部本来就是环形缓冲**,送/收时的临界区、阻塞唤醒全都替你处理好了,连信号量都省了(队列自带阻塞)。

**代价:**

- 从堆(`heap_4`)分配,占 `configTOTAL_HEAP_SIZE`(本工程 8KB)
- `xQueueSendFromISR` 内部仍要做一次拷贝,退队时再来一次 —— 比手写多一次 `memcpy`

**怎么选:** 想搞明白"这东西到底怎么转起来" → 手写一遍;生产代码图省事、不差那点 RAM → 用队列。

## 6. 术语正名

手撕这套东西涉及的名词,逐个对上:

| 层面 | 本工程用的 | 换成别的会是什么 |
|---|---|---|
| 怎么收字节 | **中断驱动接收**(interrupt-driven) | 轮询 / DMA |
| 怎么判帧边界 | **IDLE 判帧 / 空闲线检测**(idle-line detection) | 帧头帧尾、长度字段、超时定时器 |
| 怎么交接数据 | **邮箱**(mailbox,容量 1) | 环形缓冲 / 队列 / 双缓冲 |
| 怎么通知任务 | **二值信号量**做同步 | 直接任务通知 / 事件组 / 队列自带阻塞 |
| 整体分工 | **中断延迟处理**(deferred interrupt processing) | 全在 ISR 里干完 |

### 6.1 上下半部(top half / bottom half)

`api/usart1.c` 的 `USART1_IRQHandler` 和 `usart_rx_task` 这一对,在操作系统教科书里叫**中断的上下半部**:

```
上半部(top half)    = USART1_IRQHandler —— 只做不能拖的事:读 DR、判帧、发通知
下半部(bottom half) = usart_rx_task     —— 做能拖的事:格式化、等锁、慢慢打印
```

Linux 内核也用同一个概念(所以有 `request_irq` 和 tasklet/workqueue 之分)。**本工程手撕出来的东西,是它在 RTOS 上的标准形态。**

### 6.2 "门铃"是比喻,不是术语

用"门铃"形容二值信号量,是为了记住"**它只表达有事发生,不表达发生了几次**"。

正式说法是:**用于同步(synchronisation)而非互斥(mutual exclusion)的二值信号量**。FreeRTOS 文档里就是这么区分的 —— 同步用途的信号量可以当"标志位"看。

### 6.3 现代 FreeRTOS 的等价物:直接任务通知

这个位置**可以不用信号量,改用直接任务通知**(`xTaskNotifyFromISR` / `ulTaskNotifyTake`)。

干的是同一件事 —— ISR 叫醒指定任务 —— 但:

- 每条通知只花 **4 字节**,存在 TCB 里,不用单独建队列结构
- **更快**:省掉队列的检查和临界区

**代价:它是一对一的**,只能指定一个任务,不像信号量谁都能等。本工程正好是"中断 → 唯一一个接收任务",对口。

---

## 7. 一句话总结

**单格邮箱和环形缓冲不是"简化版 vs 完整版",它们保证的是不同的事:**

- 邮箱保证 **latest-wins** —— 你看到的是此刻的真实状态
- 环形缓冲保证 **FIFO 不丢** —— 一条都不漏,但可能看到过时数据

选哪个取决于:**你更怕丢数据,还是更怕看到过时数据。**
