# 队列、生产者-消费者与拷贝语义(任务间通信上篇之一)

> 一句话定位:**队列是任务之间"传数据"的管道** —— 把数据**拷贝**进去、**拷贝**出来,而不是传个指针两头共享。生产端只管往里放,消费端只管往外取,两边的节奏由它**解耦**。
>
> 兄弟篇:《互斥量、优先级继承与临界区粒度》讲的是"**护**数据"。两者不是竞争关系,是两个正交的工具。

---

## 1. 本质

队列 = 一个有**深度**的 FIFO 管道,**把数据拷进、拷出**(不是传指针共享)。

```
         xQueueSend(q, &data, 超时)
数据 ──────────────────────────▶  ┌──┬──┬──┬──┬──┬──┬──┬──┐
(生产任务)                         │  │  │  │  │  │  │  │  │  ← 深度 8,每格存一份拷入的副本
                                 └──┴──┴──┴──┴──┴──┴──┴──┘
                                  xQueueReceive(q, &data, 超时) ─▶ 数据副本
                                                    (消费任务)
```

创建时定死两件事:**深度**(能存几份)和**元素大小**(每份拷几个字节):

```c
QueueHandle_t q = xQueueCreate(8, sizeof(uint8_t)); // 8 格,每格 1 字节
// 必须在 vTaskStartScheduler() 之前创建(从 heap 分配)
```

第一个参数是**项数,不是字节数**。存储区 = 深度 × 元素大小,再加上队列结构体本身,一次 `pvPortMalloc` 全拿走 —— **建队列是要吃堆的**。发一条 200 字节的结构体,8 格就是 1600 字节,别按 8 字节算账。

---

## 2. 四个函数 + 阻塞语义

| 函数 | 干什么 | 满了/空了怎么办 |
|---|---|---|
| `xQueueSend(q, &d, t)` | 拷入一份 | **满**:阻塞最多 t 个 tick,等别人取走腾出格子 |
| `xQueueReceive(q, &d, t)` | 拷出一份 | **空**:阻塞最多 t 个 tick,等别人送来 |
| `xQueuePeek(q, &d, t)` | 偷看队头不取出 | 同上 |
| `xQueueSendFromISR(...)` | 中断里发 | 中断版,不能阻塞(见《信号量、中断与任务通信、临界区》) |

超时三选一:
- `0` = 满/空就立即放弃(非阻塞)
- `portMAX_DELAY` = 永久等下去
- `N` = 最多等 N 个 tick,等不到就返回 pdFAIL 继续干别的

**阻塞时任务进 Blocked 睡大觉,不占 CPU** —— 和 vTaskDelay 睡的是同一个状态机。

## 3. 对照你工程:key.c 的生产者-消费者

```c
// api/key.c —— 生产端(每 10ms 醒一次)
static void key_scan_task(void *arg)
{
    ...
    evt = keys[1].event_flag;              // 取走事件
    keys[1].event_flag = KEY_EVENT_NONE;
    xQueueSend(key_queue, &evt, 0);        // 超时 0:满了就丢,不等
    vTaskDelayUntil(&lastWake, 10);
}

// api/key.c —— 消费端(优先级 3 > 扫描的 2)
static void key_action_task(void *arg)
{
    if (xQueueReceive(key_queue, &evt, portMAX_DELAY) == pdPASS)  // 空就永久睡
    { ... 处理短按/长按 ... }
}
```

设计要点(面试常问的取舍):
- **深度 8 + 超时 0 = "满了丢新事件"**。按键事件丢了无损失,不值得让扫描任务干等 → 故意的设计取舍。反过来,如果丢事件会造成事故(比如电机指令),就要用阻塞/加深度。
- **消费任务优先级高于生产任务**:事件一到立刻处理,不积压。
- 生产与消费**节奏互相独立**:扫描固定 10ms,处理想睡多久睡多久,队列在中间做缓冲 —— 这就是队列的核心价值:**解耦双方的节奏**。

---

## 4. 四个必懂细节

1. **拷贝语义**:Send/Receive 是整份拷贝。元素越大越慢。拷结构体就能一次传多字段(如 `{事件号, 参数}`);你现在只拷 1 字节,只够传一个编号。
2. **大数据不拷,传指针**:队列传指向大缓冲的指针,只拷 4 字节。但要约定"谁用完谁 free"——指针所指内存的所有权,是 FreeRTOS 编程最常见的坑。
3. **中断也能发**:ISR 里必须用 `xQueueSendFromISR`(带 `xHigherPriorityTaskWoken` 参数),不能调普通版。
4. **队列锁存数据**:只要不满,数据放进去就不会丢 —— 这是它和二值信号量(只记 0/1)的本质区别。

## 5. 选型:什么时候用哪个

| 场景 | 用 |
|---|---|
| A 任务要把**数据/事件**交给 B 任务 | 队列(或任务通知) |
| 多个任务共用**同一份资源**,防止互相踩 | 互斥量 |
| 保护**中断和任务**共享的资源 | 临界区(不是互斥量) |
| 只喊一嗓子"有事了",不带数据 | 二值信号量 |
| 攒 N 件事 / 池化 N 个资源 | 计数信号量 |

判断口诀:**传数据吗?传 → 队列。不传数据、只是防踩踏 → 互斥量。**

队列和互斥量不是竞争关系,是**两个正交工具**:队列解决"我怎么把消息给你",互斥量解决"咱俩别同时碰它"。你的 key 模块用队列送按键事件,打印用互斥量护串口 —— 两个都用上了,各管各的。

> 互斥量那一侧怎么用、有哪些坑,见《互斥量、优先级继承与临界区粒度》。

## 6. 自测

**Q1.** 队列深度 8、Send 超时 0。生产端一口气发 10 个事件,消费端还没醒 —— 最后几个事件怎么样了?为什么这是合理设计?

<details>
<summary>答案</summary>

前 8 个进队列,后 2 个 Send 时队满、超时 0 → **直接丢弃**。

按键事件丢了无损失:手速远慢于队列消化速度,且丢了顶多漏一次响应,不值得让 10ms 的扫描任务阻塞干等。

</details>

---

**Q2.** 你在 `api/key.c` 的 `xQueueReceive` 用了 `portMAX_DELAY`,如果改成超时 0,消费任务会变成什么样?对按键响应有何影响?

<details>
<summary>答案</summary>

消费任务变成**忙轮询**:每 10ms 检查一次队列,没事件就继续循环 → 白占 CPU、按键响应变慢(最坏延迟从"立刻"变成"扫描周期"),还饿死低优先级任务。

</details>

## 7. 附:queue.h 里还有哪些 API

上面只用了四个。剩下的按用途分五组,**不用背,知道"有这么个东西、什么时候该想起来"就够了**。

### 7.1 发送的三个变体 —— 都是同一个函数的马甲

`freertos/include/queue.h` 里它们全是宏,展开后都去调 `xQueueGenericSend(队, &数据, 超时, 位置)`,区别只在最后那个"位置":

| 你写的 | 位置参数 | 什么时候用 |
|---|---|---|
| `xQueueSend(q, &d, t)` | `queueSEND_TO_BACK` | 最常用 |
| `xQueueSendToBack(q, &d, t)` | `queueSEND_TO_BACK` | 和 `xQueueSend` **一模一样**,写哪个看心情 |
| `xQueueSendToFront(q, &d, t)` | `queueSEND_TO_FRONT` | **加急**:插到队头,下一个取到的就是它 |
| `xQueueOverwrite(q, &d)` | `queueOVERWRITE` | **只对"只有 1 格"的队列有效** |

**`xQueueOverwrite` 有个硬前提**,`freertos/src/queue.c` 里第一句就是:

```c
configASSERT( !( ( xCopyPosition == queueOVERWRITE ) && ( pxQueue->uxLength != 1 ) ) );
```

队列长度不是 1 就直接撞断言死循环。它**没有超时参数**,因为永远塞得进 —— 满了就把最旧那份盖掉。

> 深度 1 的队列 + `xQueueOverwrite` = 一个"永远保留最新一份"的信箱。和 `api/key.c` 那个深度 8 的队列是两种思路:那边要留住几秒内的按键流水,这边只要最新值。

### 7.2 中断里用的版本 —— 名字带 FromISR,多一个参数

| 任务里 | 中断里 |
|---|---|
| `xQueueSend` | `xQueueSendFromISR`(等价于 `xQueueSendToBackFromISR`)|
| `xQueueSendToFront` | `xQueueSendToFrontFromISR` |
| `xQueueOverwrite` | `xQueueOverwriteFromISR` |
| `xQueueReceive` | `xQueueReceiveFromISR` |
| `xQueuePeek` | `xQueuePeekFromISR` |

区别两条,别搞混:

1. **最后一个参数变成 `pxHigherPriorityTaskWoken`**(一个 `BaseType_t *`)。内核通过它告诉你"刚才这一下把某个更高优先级的任务唤醒了",你得在中断退出前调 `portYIELD_FROM_ISR()` 才会立刻切过去。传 `NULL` 也合法,代价是响应慢一个 tick。
2. **不能阻塞**,所有 `xTicksToWait` 参数都不见了。满了/空了立即返回 `errQUEUE_FULL` / `pdFAIL`。

另外还有三个"只看不改"的查询函数是专给中断用的:`uxQueueMessagesWaitingFromISR`、`xQueueIsQueueEmptyFromISR`、`xQueueIsQueueFullFromISR`。

> ⚠️ 能不能用 `FromISR` 版本,还取决于**这个中断的抢占优先级数值 ≥ `configMAX_SYSCALL_INTERRUPT_PRIORITY`**。你 `api/tim.c` 里 TIM10 设的是抢占优先级 **1**,而 `freertos/FreeRTOSConfig.h` 里门槛是 **0xB0(即 11)**,1 达不到要求 —— 在那个中断里调任何 FreeRTOS API 都会撞 `configASSERT` 死循环。

### 7.3 查询与维护

| API | 干什么 | 备注 |
|---|---|---|
| `uxQueueMessagesWaiting(q)` | 当前有几条 | 在临界区里读的,拿到的是准确值 |
| `uxQueueSpacesAvailable(q)` | 还剩几格 | 内核里就是"长度 − 现有条数" |
| `xQueueReset(q)` | **清空**所有数据 | 在临界区里重置环形缓冲;**不释放内存**,队列照常能用;顺带把一个"等着发送"的任务唤醒 |
| `vQueueDelete(q)` | 删除队列,内存还给堆 | 删完句柄作废,再碰就撞断言 |
| `xQueueCreateStatic(...)` | 静态分配版 | 存储区和结构体由你自己提供,不占 FreeRTOS 堆 |

`xQueueReset` 和 `vQueueDelete` 的区别值得记:**Reset 是"把传送带上的货卸光",队列还在;Delete 是"把整条传送带拆了"。**

### 7.4 队列集(Queue Set)—— 本项目没开

想让一个任务**同时等好几个队列/信号量**,谁先来就处理谁,不用挨个 `xQueueReceive` 轮询 —— 那是"队列集"干的活:

`xQueueCreateSet` → `xQueueAddToSet` → `xQueueSelectFromSet`

**但你工程里现在用不了**:`freertos/include/queue.h` 里这些全是 `#if ( configUSE_QUEUE_SETS == 1 )` 包着的,而 `freertos/FreeRTOSConfig.h` 里没定义这一项 → `freertos/include/FreeRTOS.h` 给的默认值是 **0**。要用得先把它改成 1。

### 7.5 给调试器看的(你这儿是开着的)

`freertos/FreeRTOSConfig.h` 里有 `configQUEUE_REGISTRY_SIZE 8`,意思是"最多给 8 个队列/信号量起名字登记"。配套三个 API:

| API | 干什么 |
|---|---|
| `vQueueAddToRegistry(q, "名字")` | 给队列挂个名字 |
| `pcQueueGetName(q)` | 查名字 |
| `vQueueUnregisterQueue(q)` | 注销 |

平时用不上,但用 Ozone / SystemView 这类**内核感知调试器**时,队列在界面上会显示成你起的名字,而不是一串地址 —— 想在里面看"这条队列现在压了几条",靠的就是它。
