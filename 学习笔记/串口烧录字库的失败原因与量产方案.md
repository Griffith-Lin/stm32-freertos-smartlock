# 串口烧录字库:为什么会失败,生产上怎么烧

> 一句话定位:**串口烧录 = 裸字节流 + 零校验 + 靠人卡时间,所以必然时好时坏。**
> 生产上的原则:**不信任"写完了",只信任"校验通过了"。**

本工程的字库:`font_all.bin`,1 913 716 字节(0x1D3374),烧进 W25Q64。

---

## 1. 实际失败现场(全量回读实测)

把板子上 flash 的 1.9 MB 通过 USART1 原样吐回 PC,和 `font_all.bin` 逐字节比对,结果分成四段:

| flash 区间 | 内容 | 性质 |
| --- | --- | --- |
| `0x000000` ~ `0x0003B3` | 与源文件**逐字节一致** | 正常 |
| `0x0003B4` | 应为 `00`,实为 `80` | **翻了一个 bit** |
| `0x0003B5` 起 | 变成 `flash[i] = file[i+1]` | **被吞掉 1 字节** |
| `0x000420` ~ `0x000428` | 9 字节乱码 `8A 14 14 11 09 09 09 11 E1` | **又吞掉 3 字节** |
| `0x000429` ~ `0x1D2FFF` | 恒定 `flash[i] = file[i+5]`,干净 | 位移被一路带下去 |
| `0x1D3000` ~ `0x1D3374` | **全是 `FF`,根本没写** | **确定性丢失 884 字节** |

两个结论:

- **前 1 KB 挨了一次噪声**(1 bit 翻转 + 5 字节吞掉),之后 1.9 MB 一路无误 → 这是**概率性**故障。
- **最后 884 字节必然丢失** → 这是**代码 bug**,不是概率问题。

### 位移为什么表现成"字左右反了"

字模按行存,一行 2 字节(24 号 / 32 号)。整体错位**奇数**个字节时,每行两个字节的配对就翻过来了 —— 屏幕上就是"格子的前半部分是字的右半部分"。

16 号字一行只有 1 字节,错 1 字节只表现为整体上移一行,基本看不出来。**这就是为什么小字号"看着还行"、大字号一塌糊涂。**

## 2. 为什么会失败:四个独立原因

### ① DMA 从初始化起就在自由跑,没人对齐起点 ← 成功率不稳的头号来源

```c
void DMA_Font_Config(void)
{
    ...
    dma_InitTypeDef.DMA_Mode = DMA_Mode_Circular;   // 循环模式
    DMA_Cmd(DMA2_Stream5, ENABLE);                   // main 里就打开了
}
```

从 `DMA_Cmd(ENABLE)` 那一刻起,DMA 的**缓冲区指针**和**剩余计数**就是"随缘"状态。用户在串口助手上点"发送"的瞬间它停在哪儿,**代码根本不看**。

擦除要 4.5 秒,这期间线上静默 —— 没有数据就没有 DMA 请求,指针会老实停在 buffer0 开头,所以**大多数时候对得齐**。但只要发送文件前线上多冒出一个字节(串口助手打开端口时的换行、手滑敲的回车、USB 转串口上电毛刺),整幅图就整体错位,**错多少完全随机**。

> 这正是"有时候成功有时候失败"的根源:它不是每次都坏,而是**每次的初始条件不一样**。

### ② 整条链路零校验

```
串口 → DMA → flash
```

没有帧头、没有序号、没有 CRC、没有 ACK。线上任何一个毛刺都被当成正常数据写进去,而且**没人知道**。

上面的实测数据里,1 bit 翻转 + 5 字节丢失,一路悄无声息地写进了 flash —— 直到屏幕上出现乱码才被发现。

### ③ 最后一个不满一包的数据必然丢失 ← 确定性 bug

```c
void Font_Load(void)
{
    while(1) {
        switch(font.sta) {
            case DMA_IT:                     // 中断里每次都固定 len = BUFFSIZE
                W25Qxx_CrossPage(font.addr, font.buff[font.flag], font.len);
                font.addr += font.len;
                break;
            case Usart_IT:                   // ← 死代码:全工程没有任何地方给 sta 赋这个值
                W25Qxx_CrossPage(font.addr, font.buff[font.flag], font.len);
                return;
        }
    }
}
```

DMA 按 4096 字节整包触发中断,`font.len` 永远是 4096。文件尾巴不满 4096 怎么办?**原来的设计是靠 `Usart_IT` 分支收尾的,但那个分支永远进不去。**

算一下:

```
1913716 = 467 × 4096 + 884
                  └─ 467 包正常写入,最后 884 字节永远不写
```

**每次烧录都丢最后 884 字节**(HZK32 最后约 7 个字模),而且 `Font_Load()` 永不返回。

### ④ 双缓冲靠 `font.flag` 猜,不看硬件状态

```c
font.flag = !font.flag;      // 假设中断一定按 0、1、0、1 交替来
```

代码从没读过 `DMA2_Stream5->CR` 的 **CT 位**(当前正在用哪个缓冲区)。万一丢一次中断或中断重入,写的就是**正在被 DMA 覆盖**的那块,那一片全废。

## 3. 怎么减小失败率

### 立即可做的(不改代码)

| 手段 | 效果 |
| --- | --- |
| 发文件**前**先给板子复位,等 `擦除完成,请上传文件` 打印完再点发送 | 保证 DMA 起点对齐 |
| 别让串口助手"打开端口就自动发" | 避免起始垃圾字节 |
| 缩短 USB 转串口线,确保共地 | 减少噪声 |
| 发送后**校验**一遍(回读比对 CRC) | 坏了自己知道,而不是等屏幕出乱码 |

### 改代码(按优先级)

**1. 修尾巴 —— 接 USART1 的 IDLE 中断**

IDLE 中断在"总线空闲一个字节时间"时触发,正好用来判断一包收完了。在 ISR 里算出**本包实际收了多少字节**:

```c
void USART1_IRQHandler(void)
{
    if (USART_GetITStatus(USART1, USART_IT_IDLE) != RESET)
    {
        volatile uint32_t tmp = USART1->SR;   // 清 IDLE 标志:先读 SR
        tmp = USART1->DR;                     // 再读 DR
        (void)tmp;

        /* 本包实收字节数 = 4096 - DMA 剩余计数 */
        font.len = BUFFSIZE - DMA_GetCurrDataCounter(DMA2_Stream5);
        font.sta = Usart_IT;                  // 这才让那个分支活过来
    }
}
```

**2. 发送前把 DMA 状态归零**

打印"请上传文件"**之前**重新武装,而不是在 main 里一开了之:

```c
DMA_Cmd(DMA2_Stream5, DISABLE);
DMA_DoubleBufferModeConfig(DMA2_Stream5, (uint32_t)font.buff[1], DMA_Memory_0); // 指回 buff[0]
DMA_SetCurrDataCounter(DMA2_Stream5, BUFFSIZE);
font.flag = 0;
font.addr = 0;
DMA_Cmd(DMA2_Stream5, ENABLE);
printf("擦除完成,请上传文件\r\n");
```

**3. 加 CRC32 校验,写完回读自检**

烧完把整片字库读回来算 CRC32,和 PC 端对源文件算的值比对,串口打 `OK` / `FAIL`。**这一步是量产的硬门槛。**

**4. 看 CT 位,别猜缓冲区**

```c
font.flag = (DMA2_Stream5->CR & DMA_SxCR_CT) ? 1 : 0;
```

**5. PC 端写成脚本,别手动发**

`等 ready → 发 → 收结果 → 失败重发`,自动化掉。

### 更省事的替代:用现成的协议

**XMODEM / YMODEM-CRC** —— 串口烧录用了几十年:

- 128 / 1024 字节一包,每包带 CRC16
- 收方校验通过回 `ACK`,失败回 `NAK`,发方重传
- 自带序号,乱序 / 丢包能发现
- 很多串口助手直接支持,不用自己写 PC 端

**它天然同时解决"错位"和"偶发噪声"两个问题**,代价是速度慢一些。

## 4. 实际生产中怎么烧

核心思想一句话:**不保证"写"一定成功,而是保证"每次都能查出来没成功"。**

### 做法 A:先烧后焊(最常用)

SPI Flash 在**贴片之前**用烧录座 / 治具批量烧好,烧录器自带 verify,坏片当场挑出来。

- 优点:不占用产线节拍,一次烧一托盘
- 缺点:需要额外的烧录工位和适配座

### 做法 B:编进固件映像,交给编程器

资源文件直接编进 MCU 的固件映像,交给 SWD / JTAG 编程器烧。

- **所有编程器(J-Link、ST-Link、量产型)都默认 program + verify**,烧完给 pass/fail
- 前提:资源能塞进 MCU 内部 flash。本工程 1.9 MB 塞不进 512 KB 的 F401
  - 但**只留 ASCII + 常用汉字子集**或**压缩后**是可行的

### 做法 C:产线治具 + CRC 自检

产线末端,板子上电后自己读 flash 算 CRC,通过串口 / 调试口报给测试程序,和金标准值比对:

```
板子上电 → 读整片字库 → 算 CRC32 → 串口上报 → 测试程序比对
                                        ├─ 一致 → 过站
                                        └─ 不一致 → 返修(重烧或报废)
```

### 做法 D:固件开机自检

flash 里存一条 **"字库版本 + 长度 + CRC32"** 的记录,固件开机校验一次。

- 校验不过就**不显示 / 报错**,而不是显示乱码
- **乱码比黑屏难查得多** —— 本工程这次绕了一大圈才定位,就是活例子

### 四种做法怎么选

| 场景 | 推荐 |
| --- | --- |
| 小批量 / 打样 | 做法 B 或 D,顺手加个开机自检 |
| 中大批量 | 做法 A(先烧后焊)+ 做法 C(产线 CRC 过站) |
| 资源塞得进 MCU | 做法 B,最省事 |

---

## 5. 一句话总结

| 问题 | 根因 | 解法 |
| --- | --- | --- |
| 时好时坏 | DMA 起点没对齐 + 无校验 | 握手 + 发送前重新武装 DMA |
| 偶发乱码 | 线上噪声无人发现 | 分帧 + CRC + 重传(XMODEM) |
| 尾巴总丢 | `Usart_IT` 是死代码 | IDLE 中断算实收长度 |
| 写完不知道对不对 | 没有回读校验 | 写完算 CRC32 比对 |

**裸串口 + 无校验 = 靠运气。生产上从不靠运气,靠的是"写完必须校验"。**
